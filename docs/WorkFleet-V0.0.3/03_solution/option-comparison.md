## Q-01 主技术栈
| 方案 | 优点 | 缺点 |
|---|---|---|
| ★A TypeScript / Node | ACP TS SDK 1.9.0 领先 Python 0.12.1（F-07）；`claude-agent-acp`、`codex-acp`、acpx、OR、PC、OpenClaw 渠道插件（飞书/微信/QQ/钉钉官方）都是 TS，可移植可依赖；前后端同语言，契约类型一处生成；Node 24 自带 `node:sqlite` | Windows 下子进程与 `.cmd` 需小心；长期运行内存高于 Go |
| B Python | 用户既有 Python 项目经验；asyncio 成熟；HS/WCB 为 Python | ACP SDK 落后；OR/PC 代码要转写；中文 IM 官方插件多为 TS，需重写 |
| C Go | 单二进制、资源省；cc-connect、WeClaw 同栈 | 六个参考项目无一可直接复用；前端仍需 TS；生态最薄 |
- 推荐 A。唯一反转条件：用户 Python 明显更熟且愿意承担 SDK 落后与转写成本。

## Q-02 公开与许可
| 方案 | 优点 | 缺点 |
|---|---|---|
| ★A 公开 + Apache-2.0 | 与 MIT/Apache 依赖兼容；含专利授权；可收社区贡献 | 失去闭源；需清理旧文档中对旧内部项目代码的引用（已完成，DEC-036） |
| B 公开 + MIT | 最宽松 | 无专利条款 |
| C 转私有（闭源） | 符合原 A-45 | 失去外部贡献；仍需处理已公开的历史 |
| D 公开但不加许可 | 无 | 法律上他人不能用，等于“看得见的闭源”，最不清晰 |
- 注意：若选 A/B，BF（GPL+禁商用）、PA（EULA）、WCB（无许可）只能 clean-room，已在 DEC-009 约束。

## Q-03 渠道入口归属（重构版，2026-10-17）
**原问题的错误**：原 Q-03 只从“我一个人、一个微信”出发，问“独占还是共存”。用户补充两类真实场景后，这个二选一不成立：
- 画像 P1（用户）：微信 + 本机开发 CLI（Claude Code / Codex / Cursor）。这些 CLI 没有自己的 IM，只能由 WorkFleet 以 ACP 客户端身份拉起。
- 画像 P2（朋友）：飞书 + 其他智能体（如 OpenClaw）。这些智能体本身就是网关，自带飞书等渠道，是“同级系统”而不是子进程（F-16）。

**真正的约束是“一个 Bot 身份只能有一个消费者”（F-17）**，而不是“一个微信只能接一个工具”：
| 渠道 | Bot 身份是否稀缺 | 结论 |
|---|---|---|
| 微信 ClawBot | 稀缺：同一微信用户只认最新授权（F-13） | WorkFleet 必须是该微信唯一入口；其他工具的微信功能改由 WorkFleet 经 ACP 转发。这不是偏好，是平台约束 → DEC-034 |
| 飞书 | 不稀缺：可建多个应用（F-14），但同一应用多连接会被随机分流（F-15） | 不需要“独占”。WorkFleet 用自己的飞书应用；OpenClaw 等可保留各自的飞书 Bot；唯一禁止的是两个程序共用同一个飞书应用 → DEC-034 |

**对 P2 的接法（推荐）**：WorkFleet 新建一个“管理 Bot”作为跨智能体的统一入口（管理 / 通知 / 团队 / 总控都走它），通过 `openclaw acp` 把 OpenClaw 当作输入端；朋友原有的 OpenClaw 飞书 Bot 不强制下线，单聊仍可直接用。代价：同一智能体在飞书会有两个对话窗口，历史分属两处（WorkFleet 只能看到经它转发的那部分）。

**由此暴露的新待定项 Q-19：部署形态**——开发 CLI 必须跑在有代码的那台电脑上；朋友的智能体跑在他的机器或云上。所以先要定 WorkFleet 是每人各装一套，还是一套服务两人。

## Q-19 部署形态
| 方案 | 优点 | 缺点 |
|---|---|---|
| ★A 每人一套：你在你的电脑上跑，朋友在他的机器上跑；同一份代码，按画像预设配置 | 单用户即可，无需多租户隔离、登录与权限；各自凭据只留本机；任一方宕机不影响另一方 | 两套实例之间不共享数据；如需“你给朋友的 Agent 派活”，要另做实例互联（后续） |
| B 共用一套：跑在一台常开机器上，两人共用，朋友的 OpenClaw 经 `openclaw acp --url wss://…` 远程接入 | 一处管理；可跨人协作、统一总控 | 必须做多用户、租户隔离、权限与审计（Q-12 被迫选 A）；朋友的飞书消息与凭据经过你的机器；你的电脑关机则朋友也不可用 |
| C 共用一套，部署在云服务器 | 可用性高 | 本机 CLI 无法直接拉起（代码在各自电脑上），需要再加“本机代理”组件；成本与安全面最大 |
- 推荐 A。反转条件：你们明确需要“一个人的总控给另一个人的 Agent 派活”，且愿意承担多用户改造。

## Q-04 运行设备与网络
| 方案 | 优点 | 缺点 |
|---|---|---|
| ★A Windows 原生常驻（任务计划程序自启） | 与用户本地 E:\ 环境一致；无需 WSL | 需处理 `.cmd` 启动、进程树（Job Object）、GBK/CRLF、DPAPI、休眠断线 |
| B WSL2 | Linux 工具链 | 与 Windows 上的 Cursor/Claude 桌面环境隔离，路径与凭据不通 |
| C 常开的 Linux/Mac 小主机 | 稳定 | 多一台设备；Agent 需在该机器登录 |
- 另需确认：设备是否在中国大陆网络（决定 Telegram/Discord/海外模型是否要代理）。

## Q-05 第二渠道 / 备用渠道
| 方案 | 优点 | 缺点 |
|---|---|---|
| ★A 飞书 | 长连接无需公网；卡片流式、审批原生；场景 2 本就用飞书 | 需企业自建应用权限（U-04） |
| B Telegram | 最简单（BotFather）；群发能力强（S4 首选） | 大陆需代理 |
| C 钉钉 | Stream 模式无需公网；企业内群发 | 需企业应用；官方插件为外部包 |
| D QQ | 个人用户多 | 配额与用户开关限制 |

## Q-06 MVP 输入端（拍板）
Claude Code + Codex + Cursor：三者 ACP 均已核实（F-08、`30/02`）；ZCode 无 ACP、Coze 为云 API，放 S7 之后 → DEC-025。

## Q-07 docs 组织方式
| 方案 | 优点 | 缺点 |
|---|---|---|
| A 继续按版本目录（WorkFleet-V0.0.x） | 符合用户“递进到下一版本”指令；历史一目了然 | 违反仓内规范“不按阶段组织、不得有版本副本”（文档体系:162-192，目录结构:250）；同一事实散落多版 |
| ★B 研究版本归档 + 正式文档迁 `00_governance…09_archive` | 符合仓内规范；单一事实源；任务卡、ADR、契约有固定位置 | 一次性迁移工作；版本改用 front-matter `version` + git tag 表达 |
| C 两套并行 | 过渡期灵活 | 双份维护，最易漂移 |
- 本版（V0.0.3）按 A 落盘，待裁定后执行。

## Q-08 总控上线时机与成本上限
| 方案 | 优点 | 缺点 |
|---|---|---|
| ★A 后置到 MVP 之后（P1），先定每日 token 预算与默认模型 | MVP 提前约 44–64 人日（`40-综合/09`）；先把路由与账本做稳 | 场景 3 晚到 |
| B 与 MVP 同期 | 场景 3 早可用 | 工期与风险最高；把关 LLM 成本难控 |
| C 先做“轻总控”：只做把关分级，不做会议 | 场景 3 部分早到 | 需二次重构会议协议 |

## Q-09 MVP 是否启用 Hindsight（拍板）
否。MVP 只做会话检索（FTS + 中文 trigram）；HS 在总控阶段作为可选外部服务接入，不可用时降级 → DEC-015。

## Q-10 场景 4 受众与规模
| 方案 | 优点 | 缺点 |
|---|---|---|
| ★A 企业内部 + 少量公开订阅（≤1 万），Telegram/飞书/钉钉 | 合规风险低；渠道限额可承受 | 微信不可用于群发 |
| B 面向公众大规模（>1 万） | 商业价值高 | 需公众号/服务号等合规渠道、内容审核、退订与隐私条款，超出本项目定位 |
| C 只给自己和团队 | 最简单 | 场景 4 价值有限 |

| 方案 | 影响 |
|---|---|

## Q-13 节假日与调休（拍板）
采用国务院办公厅每年公布的放假调休安排作为数据源，内置当年数据 + 控制台手动修正；下一年数据缺失时降级为“周一至周五为工作日”并告警 → DEC-026。

## Q-14 分身数据采集范围
| 方案 | 优点 | 缺点 |
|---|---|---|
| ★A 只采用户在 IM 中对 Agent 的指令、审批、纠正 | 隐私面最小；价值最高的信号 | 画像较窄 |

## Q-15 执行 Agent 分档
规划指令中出现 haiku / sonnect / opus / fable 四档。sonnect 推定为 sonnet 笔误；fable 含义未知。需用户定义各档职责与预算口径（按 token、按任务数或按时长）。

## Q-16 与旧内部项目的关系（拍板）
完全独立，不迁移代码；旧内部项目将来可作为一个普通输入端接入 → DEC-027。

## Q-17 契约唯一源与迁移（拍板）
JSON Schema（必要时 OpenAPI/AsyncAPI 包装）为唯一源，生成两端类型；迁移用纯 SQL 序号文件 `NNN_name.sql`，不用 alembic → DEC-028。

## Q-18 端口映射（拍板）
见 DEC-016。

## Q-20 云中转服务器归属（DEC-037 之后）
中转持有 IM 凭据（微信授权、飞书应用密钥），且 IM 平台把消息明文推给中转，中转必然能看到消息内容；本机节点只向中转发起出站 WSS 连接。
| 方案 | 优点 | 缺点 |
|---|---|---|
| ★A 共用一台（你部署），按账号租户隔离 | 一台机器、一处运维、成本最低；同一套代码 | 朋友的飞书凭据和消息明文经过你的服务器；需做租户隔离与各自的节点令牌 |
| B 各自一台 | 凭据与消息互不经过对方；故障互不影响 | 两份运维与费用；朋友需自己会部署 |
- 推荐 A。反转条件：朋友的飞书是公司租户、有合规要求，或朋友不接受消息经过你的服务器 → 选 B。
