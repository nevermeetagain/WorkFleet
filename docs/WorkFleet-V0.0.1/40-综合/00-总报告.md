# AideanFleet V0.0.1 · 总报告（执行摘要 + 研究包索引）

> 撰写：2026-10-16（Asia/Shanghai），综合架构师。
> 研究对象：多对多 ACP 网关——把多个编码智能体/CLI（Claude Code、Codex CLI、Cursor、OpenClaw、ZCode、Coze）与多个 IM（飞书、微信 ClawBot、QQ、钉钉、Discord、Telegram）连起来，支持管理 / 通知 / 团队 / 总控四种模式，以及定时任务、`/clear`、按 session/resume ID 查历史、分身 loop、知识库。
> 方法：`00-原始需求.md` 规定的 5W1H → 苏格拉底追问 → 双向钢人 → 带前提与局限的最终判断；证据标签 `已确认 / 部分确认 / 证据不足 / 待确认 / 存在缺陷 / 暂不执行`。

---

## 1. 一页结论

1. **没有现成开源项目能满足“大部分”需求**（统一加权 ≥80%）。最高的是 OpenClaw ≈68%、cc-connect ≈65%；AionUi+AionCore 58%、Paperclip ≈50–54%、Orca ≈39–45%（原报告值与统一口径值区间）。`部分确认`（`01`）
2. **七项需求所有候选都没有**，而它们正是 AideanFleet 的价值所在：单个 IM 绑定被多个输入端复用、订阅者广播、中国法定节假日与调休调度、总控会议、强制把关与分级上报、目录结构图谱、两端统一事件库。（`01 §3.2`）
3. **微信是限制最严的渠道**：1 个微信号 ↔ 1 个 ClawBot，只路由到最新扫码绑定；`context_token` 24 小时失效；每次入站后约 10 条主动消息额度（均为 `部分确认`）。因此网关必须**独占这唯一绑定再多路复用**；**微信不能做群发**（场景 4 改用 Telegram / 飞书 / 钉钉 / Discord）。（P3 §1、`07 §4`）
4. **六个 IM 都支持长连接或长轮询**，网关可以完全跑在设备上，不需要公网 IP。`已确认`（P3 §0）
5. **输入侧以 ACP v1 为主**（stdio JSON-RPC；`session/new|load|resume|list|close`；ACP 没有 `/clear`，“新开对话”= `session/new`）。ZCode 官方 app-server 不是 ACP，Coze 是云端 HTTP（有 `/conversations/{id}/clear`），需要专用适配器。v2 仍是草案。（P1、P2）
6. **本轮新发现**：用户的 `aideanew/AideanFleet` 仓库已经是一个 Python + SQLite 的多 CLI 编排器（v0.4.0）：单写者内核、事件 outbox、LLM 规划器、DAG、门禁、审批、预算、Vue 控制台（:3100）、Windows 安装器；端口约定 ADR-005 把 **AideanFleet 定在 3100–3200**（Aidean 3000–3100、aideanbot 3300–3400）。它没有 IM、没有 ACP。`已确认`（文档+目录+grep，未运行）
7. **推荐方案 C2**：在现有 AideanFleet Python 仓内新增 Gateway 层，自研路由/广播/总控/节假日调度/事件库；ACP 走官方 Python SDK（不行则 Node 旁车 C2′）；按许可证规则移植 Orca、Paperclip、AionCore、OpenClaw 的设计与模块，PentAGI 只借设计；Hindsight 作为外部记忆服务。回退：cc-connect 作通道旁车（A′，需作者补 LICENSE）。加权比较：C2 83 / C1 72 / A 63 / B 57 / D 41（判断性打分）。（`03`）
8. **工作量**：缺口 29 项约 197–286 人日；含 PoC 与加固约 207–301 人日（单人约 9.5–14 个月，双人约 5.5–8 个月）。**先做 2–3 周 PoC**（P0 现有仓体检、P1 微信单绑定多输入、P2 Python ACP 冒烟为必做），过三个决策闸门后再进 MVP。（`02`、`08`）
9. **端口**：本项目只用 3100–3200；**不使用 3000/3333**（属于 Aidean/AideanBot，`待确认`由用户拍板）；现有代码里的 `MANAGER_PORT=9900` 不在段内（`存在缺陷`）；Paperclip 默认 3100 与本段冲突（桥接时需移走）。（`04 §16`）

**是否进入下一阶段**：允许进入 **V0.1 PoC**；正式开发 **暂不执行**，等待用户确认 `08 §4` 的 U1–U4 与 PoC 结论。

## 6. 最终判断（四轮方法的收口）

1. **明确结论**：不 fork 任何大项目；在用户现有 AideanFleet Python 仓内自研 Gateway 层（C2），按许可证规则借鉴各项目；先 PoC 后开发。
2. **结论依据**：`01` 覆盖矩阵与“无人实现”清单；`02` 缺口成本；`03` 双向钢人与加权比较；P1–P3 协议与渠道硬约束。
3. **具体代码证据**：cc-connect `cmd/cc-connect/main.go:361-421`、`core/cron.go:23-41`；OpenClaw `src/routing/resolve-route.ts:405-424`；Paperclip `chat-channels.ts:9-18`、`chat_channels.ts:50`；Orca `coordinator.ts:146,226`；WechatClawbot `app.py:131-139`；AideanFleet `fleet/core/ports.py`、`docs/架构.md`。
4. **具体命令证据**：`01 §0.3`（9 条核查）、`02 §0`（7 个 SDK 仓库元数据）、DDL 在 SQLite 3.46.1 中执行通过（`04 §6` 34 张表含 FTS 影子表、`05 §7` 14 张表）。
5. **成立前提**：PoC-0/1/2 通过；用户确认 U1–U4。
6. **局限**：未运行任何候选与 AFX；匹配度与加权比较是判断性打分；工作量为估算。
7. **尚未验证**：微信真机约束；Python ACP SDK；飞书卡片回调长连接；QQ 配额；Hindsight 中文；全部性能数字。
8. **可能风险**：微信政策变化；ACP v2；总控效果；单人工作量；合规。
9. **下一步**：用户回复 `08 §4` U1–U4 → 执行 P0、P1、P2（约 1 周）→ 其余 PoC → 决策闸门 → V0.2。
10. **是否允许进入下一阶段**：**允许进入 V0.1 PoC**；V0.2 及之后 **暂不执行**。
