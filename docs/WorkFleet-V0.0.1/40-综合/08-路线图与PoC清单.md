## 5. 5W1H / 追问 / 钢人 / 最终判断

- **What**：7 个里程碑、12 个 PoC、3 个决策闸门、11 个开放决策。
- **Why**：把最大不确定性（微信约束、Python ACP、平台限额、总控效果）放在最前面验证，避免在错误前提上写 200+ 人日代码。
- **Where/When**：PoC 2–3 周（单人约 10–15 人日，可并行压缩）。
- **Who**：用户拍板 U1–U11；开发者执行 PoC。
- **How**：§2 方法与通过标准。
- **What if**：P1 失败 → DG1；P2/P3/P6 多项失败 → DG2；P0 失败或 U1 选新仓 → DG3。

**追问**：“为什么 MVP 要 70–100 人日这么多？”——因为管理模式的“可用”包含单绑定复用、额度降级、审批、会话/历史、密钥加密、控制台页面、契约测试；去掉任何一项都会在真实使用中暴露（例如没有额度降级，长任务一多微信就静默丢消息，P3 §1.3）。反方：可先做“只读通知版”（30–40 人日）尽快可用。→ 可作为 V0.2-alpha：只有 G01/G03/G05/G10 + 最简命令，先让用户用起来，再补审批与控制台。

**最终判断**：
1. 结论：先做 V0.1 PoC（P0、P1、P2 为必做），通过后进入 V0.2 管理模式 MVP。
2. 依据：`02` 缺口工作量、`03` 选型前提、`07` 场景验收。
3. 代码证据：见各 PoC 引用。
4. 命令证据：`01 §0.3`、`02 §0`。
5. 前提：用户确认 U1–U4。
6. 局限：工作量为估算；PoC 可能暴露新问题。
7. 未验证：所有 PoC 问题本身。
8. 风险：§3。
9. 下一步：用户回复 U1–U4（至少），然后启动 P0/P1/P2。
10. 是否进入下一阶段：**允许进入 V0.1 PoC**；V0.2 **暂不执行**，待 DG1–DG3 有结论。
