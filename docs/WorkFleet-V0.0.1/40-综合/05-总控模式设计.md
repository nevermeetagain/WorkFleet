# 40-综合 · 05 总控模式设计（职业经理人 Supervisor）

> 撰写：2026-10-16（Asia/Shanghai）。状态：设计稿。
> 需求原文（`00-原始需求.md` §拓展功能）：总控必须运行在设备上；在团队模式基础上增加“职业经理人”，负责各大小事务、统一汇报；用户提需求后组织各输入端开会、各自扮演员工分析需求，由总控明确需求、分析得失、统一意见、分配任务（可只给一个输入端）；各输入端每次输出都必须经总控把关、归纳、回复，非必要信息直接回复，回复不了的/重大决策/资源申请再交给输出端；支持自定义模型与 skill；支持随时与总控对话且不影响正在执行的任务。
> 借鉴来源与许可证处理：PentAGI（**只借设计**，EULA）、Orca（MIT，schema/状态机移植）、AionCore Team（Apache-2.0，设计）、Paperclip（MIT，org chart/审批/指令版本）、OpenClaw broadcast groups（MIT，轮次上限思路）、AFX 现有内核（自有，直接复用）。

## 0. 核心设计决定

| # | 决定 | 理由 / 证据 |
|---|---|---|
| D1 | **员工 = 外部 ACP 会话**（Claude/Codex/Cursor/OpenClaw…），不是内部 LLM 角色 | 需求“各输入端扮演不同员工”；与 PentAGI 的根本差别（R3 §3.4：PentAGI 员工是内部 LLM 工具） |
| D2 | **会议与把关全部在网关层编排** | ACP 没有 Agent↔Agent 语义（P1 §2、§12 反对⑤） |
| D3 | **经理“大脑”可二选一**：(a) 直连模型（OpenAI 兼容 / Anthropic / 本地），(b) 一个 ACP Agent 以只读/计划模式充当经理 | 需求“支持自定义模型”；AFX 已有 OpenAI 兼容模型池（`fleet/models/router.py`、`pool.py`） |
| D4 | **任务存储复用 AFX 内核**（goal/todo/claim/lease/attempt/gate/needs_user），总控新增会议、邮箱、上报、策略表 | AFX `docs/架构.md §2–§4`（`部分确认`：未运行） |
| D5 | **员工通过 Fleet MCP 工具与经理通信**（`fleet_ask`、`fleet_done`、`fleet_status`、`fleet_handoff`） | AionCore“Team MCP Server 以 MCP 工具形式暴露团队能力”（L3 §4）；Orca worker 契约（R4 §3.2：恰好一次 `worker_done`） |
| D6 | **旁路对话 = 独立经理会话 + 受控工具**，不共享执行 worker 的锁 | PentAGI Assistant + flow_manager（R3 §3.5）；AION mailbox |
| D7 | **护栏三闸**：输出格式闸、行为异常闸、预算闸 | PentAGI reflector / mentor / 迭代上限（R3 §3.3） |
| D8 | **上报分级：规则优先，LLM 兜底，可解释** | Orca escalation/priority/decision_gates（R4 §3.3）；PentAGI ask 屏障 |

## 2. 状态机

### 2.1 运行（Run）级

```
            ┌────────────┐  用户提需求（IM/控制台/定时）
            │  intake    │──────────────────────────────┐
            └─────┬──────┘                              │
                  ▼                                     │
            ┌────────────┐  信息不足 → 上报澄清问题(p1) → 等用户 → 回到 clarify
            │  clarify   │◀─────────────────────────────┘
            └─────┬──────┘
         需要会议？│是                         否（小需求、单员工可完成）
                  ▼                                     │
            ┌────────────┐                              │
            │  meeting   │ 轮次 1..R：并行征询 → 汇总分歧 → 二轮（仅分歧点）
            └─────┬──────┘                              │
                  ▼                                     ▼
            ┌────────────┐  重大决策/资源申请 → decision gate → 等用户
            │  decide    │◀───────────────(gate resolved)──────────┐
            └─────┬──────┘                                          │
                  ▼                                                 │
            ┌────────────┐  生成 DAG 写入 AFX kernel（goal + todos）  │
            │  plan      │                                          │
            └─────┬──────┘                                          │
                  ▼                                                 │
            ┌────────────┐  ready todo × 空闲员工；并发上限；心跳      │
            │  execute   │──── 员工输出 → review（把关）──→ 自答/归纳/上报
            └─────┬──────┘        ▲          │ 失败≥3 → circuit_broken → 上报
                  │               └── 返工（successor todo）
                  ▼
            ┌────────────┐
            │  report    │ 阶段/最终汇报（按绑定的输出端，受额度约束）
            └─────┬──────┘
                  ▼
     done | cancelled | failed | paused(预算/用户暂停)
```

### 2.2 任务（Todo）级——复用 AFX 内核

`open → claimed → running → verifying → done | blocked | needs_user | superseded`（AFX `docs/架构.md §2`）。总控只增加两个映射：
- `needs_user` → 生成 `sv_escalation`，由 Reporter 推送到输出端；用户在 IM 回复即调用 `kernel.reopen` 或注入回答（PentAGI “有 Waiting 任务时新消息视为回复”，`flow.go:1354-1365`）。
- `blocked` 连续 ≥ N 次或 attempt 轮数超限（AFX 默认 4）→ `circuit_broken` 上报（参考 ORC 3 次熔断）。

### 2.3 员工派工（Dispatch）级

`pending → dispatched → working → (asked ↔ answered)* → done | failed | stale | circuit_broken`；心跳超时 → `stale` 告警（ORC `warnStaleDispatches`）；“absence ≠ death”：员工进程断开不等于任务失败，先重连 `session/resume`（ORC AGENTS.md SSH 用例思路）。

## 3. 会议协议（自研；无现成实现）

### 3.1 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `participants` | 绑定中 tag 命中的员工，或经理挑选 ≤5 个 | 可在 IM 用 `/ask 开会 @claude-main @codex-a` 指定 |
| `mode` | `plan`/只读 | 会议期间员工只分析不改文件：ACP `session/set_mode`（若 Agent 支持计划/只读模式，如 Cursor `plan`/`ask`，P2 §3.1）；不支持则在提示中约束 + 权限策略 `deny` 所有写工具 |
| `rounds_max` | 2（上限 4） | 参考 OCL broadcast groups `maxRounds ≤ 4`（L2 §2） |
| `turn_budget` | 每人每轮 1 turn，`max_tokens`/时长上限 | 防成本失控 |
| `timeout_s` | 每轮 300 s | 超时者记“缺席” |
| `persona` | 每位员工一个角色卡（架构师/后端/前端/测试/产品…） | 由经理分配或用户 skill 指定 |
| `share_policy` | 二轮只共享“分歧摘要”，不共享全文 | 控制上下文长度；ACP 不共享上下文，必须由网关转述（P2 §8 What-if） |

### 3.2 流程

1. **议题包**：经理把澄清后的需求整理成“议题包”（目标、约束、验收、已知风险、相关知识检索结果）。
2. **第一轮（并行）**：同一议题包 + 各自角色卡 → 每位员工返回**结构化发言**：
   ```json
   {"stance":"支持|有条件支持|反对","understanding":"…","proposal":"…",
    "risks":[{"desc":"…","severity":"low|med|high"}],"estimate_hours":6,
    "needs":["资源/权限/信息"],"questions":["…"],"can_own":["子任务A"]}
   ```
   无法解析时由“输出格式闸”要求重答一次（PentAGI reflector 思路，最多 1 次）。
3. **归纳**：经理生成“分歧矩阵”（议题点 × 员工立场），若所有关键点一致或分歧不影响决策 → 结束；否则进入第二轮，只针对分歧点征询。
4. **决策**：经理产出**决策记录**（采纳方案、理由、放弃的选项及原因、风险与缓解、需要用户拍板的事项）。含“需要用户拍板”→ `decision gate`（上报）；否则直接进入 plan。
5. **纪要**：会议纪要 + 决策记录写入事件库，并 retain 到 Hindsight 的 `project:<id>` bank（若启用）。
6. **分配**：经理自行决定只派给一个员工还是拆给多人（需求原文允许），产出 DAG。

### 3.3 会议的成本与质量控制
- 会议是可选的：需求复杂度评分（文件范围、跨仓库、预计工时、风险词）低于阈值时直接单员工执行。
- 每次会议有预算（token/时长/人数），超预算转为“经理单人决策 + 上报说明”。
- 质量无法事前保证（`证据不足`）：PoC-8 用 3 个真实需求做 A/B（有会议 vs 无会议）评估返工率与用户满意度。

## 4. 任务拆解与分派

| 步骤 | 做法 | 复用 |
|---|---|---|
| 拆解 | 经理输出计划 JSON（id、title、role、depends_on、allowed_files、verify、done_when、assignee_hint） | **直接复用 AFX Planner 的计划 schema 与硬校验**（verify 必须真实命令、依赖无环、id 唯一、白名单必填，`docs/架构.md §4`） |
| 写入 | `kernel.create_goal_with_plan` | AFX `docs/架构.md §8` |
| 选员工 | 规则：`assignee_hint` > 角色匹配（skill/标签）> 空闲度 > 历史成功率（`sv_worker_stats`） | Paperclip org chart（`agents.reports_to`）思路 |
| 并行 | DAG ready × 空闲员工，默认并发 4；`allowed_files` 顶层目录不相交才可并行；推荐每任务一个 git worktree | AFX allowed_files 并行互斥；ORC `MAX_CONCURRENT_DEFAULT = 4`（`coordinator.ts:36`）、stale-base 拒绝 |
| 下发 | 生成“任务包”（AFX `packet_for`）→ ACP `session/prompt`（员工会话按 `(profile, project)` 复用或新开） | AFX packet；P4 InputAdapter |
| 回收 | 员工调用 `fleet_done{outcome, summary(≤3 句), evidence}` 或 turn 结束后由 gate 跑 verify 命令 | ORC worker_done 恰好一次；AFX gate 真实执行 verify |
| 返工 | gate 失败 → successor todo（同 lineage）；超限 → needs_user | AFX |

## 5. 把关（Gating）与上报（Escalation）

### 5.1 所有员工输出必经总控
绑定 `mode=supervisor` 时，Router 把员工 `turn.end / perm.request / error / msg.final` 一律送 `Supervisor.review()`，**不直接发给 IM**（`04 §7.3`）。

### 5.2 分类

| 类别 | 判定（规则优先） | 动作 | 默认优先级 |
|---|---|---|---|
| `auto_reply` 可自答 | 员工提问可由知识库/上下文/既定决策回答（检索命中且置信度≥阈值） | 经理直接回复员工，不打扰用户 | — |
| `digest` 归纳 | 普通进度、成功完成、低风险变更 | 合并进阶段汇报/日报 | p3 |
| `decision` 重大决策 | 命中“决策词表”（架构变更、对外接口变化、数据迁移、删除、发布）、会议有未决分歧、偏离已批准计划 | `decision gate`：选项 + 推荐 + 理由 → IM 按钮/口令 | p1 |
| `resource` 资源申请 | 需要新账号/密钥/付费 API/额度提升/新机器/人手 | 上报，附预估成本 | p1 |
| `risk` 风险/安全 | 高风险工具审批、密钥外泄迹象、测试大面积失败、预算将超 | 立即上报 | p0 |
| `blocked` 阻塞 | 熔断、反复 needs_user、员工长时间无心跳 | 上报，附已尝试措施 | p0/p1 |

- 规则引擎读取 `sv_policy`（可在后台编辑）；规则未覆盖时由“分类器模型”（可用便宜模型）给出类别 + `gate_reason`，并记录以便复盘。
- 硬规则可存于 Hindsight `directives`（按优先级注入经理提示，R5 §6）。
- **审批类**（ACP `request_permission`）：低风险 + 已有 `permission_rule` → 经理代批并记录；中风险 → 经理按策略代批或上报；高风险 → 一律上报 owner。

### 5.3 上报的渠道约束
- 上报走绑定的输出端，受额度约束：微信窗口额度紧张时，p0/p1 优先，p3 合并成日报；p0 额度耗尽走 fallback 渠道（`04 §8`）。
- 上报消息必须**可直接决策**：一句结论 + 选项（≤4 个）+ 推荐项 + 影响说明 + 回复口令。

## 6. 自定义模型、Skill 与旁路对话

### 6.1 模型配置（按角色，参考 PentAGI `pconfig`）

| 角色 | 用途 | 建议 |
|---|---|---|
| `manager` | 澄清、会议主持、决策、拆解 | 强推理模型；或 ACP Agent（D3-b） |
| `summarizer` | 纪要、日报、归纳 | 中等模型 |
| `classifier` | 把关分类兜底 | 便宜/本地模型 |
| `side_chat` | 旁路对话 | 同 manager 或中等 |

配置项：provider、model、base_url、secret_ref、temperature、max_tokens、预算（日/运行）、回退链；复用 AFX `fleet/models`（OpenAI 兼容池、重试、路由）。

### 6.2 Skill
- 形态：目录 `skills/<name>/SKILL.md`（说明 + 触发条件 + 步骤 + 可用工具）+ 可选 `templates/`、`policies.yaml`。
- 作用域：`manager`（经理技能：如“需求评审”“发布审批口径”“周报格式”）、`worker`（下发给员工的约定：如“代码规范”“提交信息格式”）。
- 注入：经理技能进入 manager 系统提示；员工技能随任务包下发，或写入员工工作区的约定文件（`AGENTS.md`/`CLAUDE.md`）——**写入前须用户确认**（避免覆盖用户文件）。
- 版本化与校验：保存时做模板渲染校验（PentAGI `pkg/templates` 机制，R3 §7）；版本历史（Paperclip `agent_instruction_revisions` 思路）。

### 6.3 旁路对话（随时对话不打断执行）
- 用户在任何时刻发 `/ask …`（或在 `reply_target=supervisor` 的绑定里直接发言）→ 进入**独立的经理会话** `sv_side_session`，与执行流的锁、队列完全分离。
- 经理在旁路会话中只能调用受控工具（参考 PentAGI 五个 flow_manager 工具，`registry.go:49-53`）：

| 工具 | 作用 | 约束 |
|---|---|---|
| `sv_status(run?)` | 读运行/任务/员工状态 | 只读 |
| `sv_send_input(todo, text)` | 给某任务/员工追加说明（在其下一个检查点读取） | 不打断当前 turn |
| `sv_patch_plan(diff)` | 修改未开始的任务 | 运行中任务不可改；生成 PlanDiff 需用户确认（AFX steer：step 模式 needs_user） |
| `sv_pause/sv_resume(run)` | 暂停/恢复派工 | 不杀进行中的 turn |
| `sv_stop(todo|run)` | 停止 | 需显式确认，调用 `session/cancel` |
| `sv_wait(run, timeout)` | 等待完成 | 上限 1h（PentAGI `waitFlowMaxTimeout=1h`） |

- 员工侧：在检查点（每个 turn 结束/固定间隔）调用 `fleet_status` 读取 follow-up（ORC worker obligations 3）。

## 7. 数据模型（追加到 `gateway.db`；任务表复用 AFX `kernel.db`）

```sql
CREATE TABLE sv_config (
  id TEXT PRIMARY KEY, name TEXT NOT NULL,
  binding_id TEXT NOT NULL,                       -- 对应 binding(mode='supervisor')
  brain_kind TEXT NOT NULL CHECK (brain_kind IN ('model','acp')),
  models_json TEXT NOT NULL,                      -- {manager:{provider,model,...}, summarizer:…, classifier:…, side_chat:…}
  manager_profile_id TEXT,                        -- brain_kind='acp' 时的 agent_profile
  meeting_json TEXT NOT NULL DEFAULT '{"rounds_max":2,"timeout_s":300,"max_participants":5}',
  budget_json TEXT NOT NULL DEFAULT '{}',         -- 日/运行 token 与金额上限
  concurrency INTEGER NOT NULL DEFAULT 4,
  enabled INTEGER NOT NULL DEFAULT 1, created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE TABLE sv_skill (
  id TEXT PRIMARY KEY, config_id TEXT NOT NULL REFERENCES sv_config(id),
  scope TEXT NOT NULL CHECK (scope IN ('manager','worker')),
  name TEXT NOT NULL, version INTEGER NOT NULL, path TEXT NOT NULL, sha256 TEXT NOT NULL,
  enabled INTEGER NOT NULL DEFAULT 1, created_at TEXT NOT NULL, UNIQUE(config_id, name, version)
);
CREATE TABLE sv_policy (
  id TEXT PRIMARY KEY, config_id TEXT NOT NULL REFERENCES sv_config(id),
  category TEXT NOT NULL CHECK (category IN ('auto_reply','digest','decision','resource','risk','blocked')),
  match_json TEXT NOT NULL,                       -- {keywords:[],tools:[],paths:[],kinds:[],risk:'high'}
  action_json TEXT NOT NULL,                      -- {prio:'p1',require_owner:true,...}
  priority INTEGER NOT NULL DEFAULT 100, enabled INTEGER NOT NULL DEFAULT 1
);
CREATE TABLE sv_worker (                          -- 员工花名册
  config_id TEXT NOT NULL REFERENCES sv_config(id), profile_id TEXT NOT NULL,
  persona TEXT, skills_json TEXT NOT NULL DEFAULT '[]', max_parallel INTEGER NOT NULL DEFAULT 1,
  PRIMARY KEY (config_id, profile_id)
);
CREATE TABLE sv_run (
  id TEXT PRIMARY KEY, config_id TEXT NOT NULL REFERENCES sv_config(id),
  objective TEXT NOT NULL, origin TEXT NOT NULL,  -- im:<acct>:<peer> | console | schedule:<id>
  kernel_goal_id TEXT,                            -- AFX kernel goals.id
  phase TEXT NOT NULL CHECK (phase IN ('intake','clarify','meeting','decide','plan','execute','report','done','cancelled','failed','paused')),
  budget_used_json TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE TABLE sv_meeting (
  id TEXT PRIMARY KEY, run_id TEXT NOT NULL REFERENCES sv_run(id),
  agenda_json TEXT NOT NULL, participants_json TEXT NOT NULL,
  round INTEGER NOT NULL DEFAULT 0, status TEXT NOT NULL CHECK (status IN ('open','round_running','synthesizing','closed','aborted')),
  divergence_json TEXT, decision_json TEXT, minutes_event_id TEXT,
  created_at TEXT NOT NULL, closed_at TEXT
);
CREATE TABLE sv_meeting_turn (
  meeting_id TEXT NOT NULL REFERENCES sv_meeting(id), round INTEGER NOT NULL, profile_id TEXT NOT NULL,
  fleet_session_id TEXT, persona TEXT,
  statement_json TEXT, status TEXT NOT NULL CHECK (status IN ('asked','answered','invalid','timeout')),
  tokens INTEGER, asked_at TEXT NOT NULL, answered_at TEXT,
  PRIMARY KEY (meeting_id, round, profile_id)
);
CREATE TABLE sv_dispatch (                        -- 借鉴 ORC dispatch_contexts
  id TEXT PRIMARY KEY, run_id TEXT NOT NULL REFERENCES sv_run(id),
  kernel_todo_id TEXT NOT NULL, profile_id TEXT NOT NULL, fleet_session_id TEXT,
  status TEXT NOT NULL CHECK (status IN ('pending','dispatched','working','asked','done','failed','stale','circuit_broken')),
  failure_count INTEGER NOT NULL DEFAULT 0, last_heartbeat_at TEXT,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE TABLE sv_message (                         -- 邮箱：经理↔员工、经理↔用户（借鉴 ORC messages）
```

## 8. 时序示例（场景 3：主项目 + 子项目）

1. 用户在飞书：“给主站和两个子项目统一接入新的登录方式，下周三前上线。”
2. `intake` → `clarify`：经理检索知识库（项目结构、既有认证方案），缺“是否保留旧登录” → 上报澄清（p1）→ 用户回“保留 30 天”。
3. `meeting`：参与者 claude@主站（架构师）、codex@子项目A（后端）、cursor@子项目B（前端），只读模式；第一轮 2 人支持、1 人提出“子项目B 使用的 SDK 版本过旧”风险 → 第二轮只讨论该分歧 → 结论“先升级 SDK”。
4. `decide`：涉及对外接口变化 → `decision gate`（选项：A 先升级再接入（推荐）/ B 并行 / C 推迟）→ 用户点 A。
5. `plan`：写入 AFX kernel：5 个 todo（DAG），并行度受 allowed_files 互斥约束。
6. `execute`：派工；codex 请求执行 `npm publish` → 高风险 → 上报 owner；其余低风险审批由经理按策略代批并记录。
7. 用户中途 `/ask 子项目B 进度？`：旁路会话调用 `sv_status`，即时回复，不打断执行。
8. `report`：每完成一个里程碑合并汇报；最终汇报含验证证据路径与遗留风险。

## 9. 5W1H / 追问 / 钢人 / 最终判断

- **What**：一个设备端经理，复用 AFX 内核做任务，新增会议、把关、邮箱、旁路对话、上报。
- **Why**：需求要求“统一向我汇报、只上报重要事项、随时对话不打断”；现有项目只有零件（R2 6.9、R3 R10、R4 `coordinator.ts:146,226`）。
- **Where/When**：Edge；依赖 Gateway 的会话、审批、出站（V0.5 里程碑）。
- **Who**：总控 owner；用户定义策略与技能。
- **How**：§2–§7。
- **What if**：经理模型太弱 → 会议质量差：会议可关、阈值可调、经理可换成 ACP Agent；成本超限 → BudgetGuard 暂停并上报；员工不调用 `fleet_done` → turn 结束后由 gate 判定；AFX 内核不适配 → 回落为 ORC 式独立 `sv_task` 表（schema 已有先例，R4 §3.3）。

**追问**：“经理 LLM 的把关会不会漏报重大事项？”——会。所以规则优先（关键词/工具/路径/风险等级可审计），LLM 只兜底；所有 `sv_review` 留痕，每周可在后台复盘“被归为 digest 的事项”。反方：规则过严会骚扰用户 → 用额度与合并策略限制推送频率，且 digest 每日一次。

**钢人反方**：“直接让一个强 Agent（如 Claude Code）当经理，用 skill 驱动其他 Agent（ORC 做法）更简单。”——支持：零引擎开发，ORC 已证明可行。反对：无法强制“必经把关”（ORC 外部上报为空钩子），无法在网关层控制额度与审计，经理会话本身也会被长任务占用。裁决：**D3-b 允许 ACP Agent 当经理大脑，但把关、上报、额度、旁路仍由网关引擎强制执行**。

**最终判断**：
1. 结论：按本设计实现总控；会议与把关为自研，任务内核复用 AFX。
2. 依据：§0 决定表证据。
3. 代码证据：PTG `flow.go:1288-1406`、`task.go:341-380`、`performer.go:36-38,611`、`helpers.go:165-191`、`assistant.go:355-431`；ORC `coordinator.ts:36,146,159-305`、`create-core-tables-sql.ts:23-49`、`create-graph-tables-sql.ts:115-218`；AION `crates/aionui-team/src/{mailbox,task_board}.rs`、`mcp/tools.rs:29`；AFX `docs/架构.md §2–§4`。
4. 命令证据：`sed -n 144,150p`、`224,228p orca/.../coordinator.ts`（本轮复核）。
5. 前提：Gateway V0.2–V0.4 已交付；AFX 内核可被 Gateway 调用（PoC-0）。
6. 局限：会议效果、分类准确率无数据。
7. 未验证：员工 ACP 只读/计划模式在各 Agent 上的可用性；AFX planner 对外部 ACP 员工的适配。
8. 风险：成本、误报/漏报、单人工作量（约 38–56 人日，对应 `02` G16–G19）。
9. 下一步：PoC-8（会议 A/B）；V0.5 实施。
10. 是否进入下一阶段：允许进入详细设计；实施排在管理/团队/通知模式之后。
