## 1. 定时任务（“和手机闹钟大体一致”）

### 1.1 需求拆解

| 需求原文 | 规则类型 | 现有项目支持 | 设计 |
|---|---|---|---|
| 只运行一次 | `once` | CCC timer、OCL `at`、AION `At`、ASB `run_once`（`01` CR-1） | `{type:"once", at:"2026-10-20T09:00"}` |
| 每日 | `daily` | 全部 cron | `{type:"daily", time:"09:00"}` |
| 每周 | `weekly` | 全部 cron | `{type:"weekly", days:[1,3,5], time:"09:00"}`（1=周一） |
| 每月 | `monthly` | cron 可表达日号 | `{type:"monthly", day:15 | "last" | {nth:2, weekday:1}, time, overflow:"skip"|"clamp"}` |
| 工作日 | `workday` | **只能 cron `1-5`，无节假日/调休** | 中国法定工作日：周一至五非放假日 + **调休上班日** |
| 休息日 | `restday` | 无 | 周六日非调休上班日 + 法定放假日 |
| （补充）高级 | `cron` | 全部 | 5 段 cron + `calendar_filter:"workday"|"restday"|null` |

闹钟式附加项：`skip_next`（跳过下一次，手机闹钟常见）、`until`（截止日期）、`count`（次数）、`paused_until`。

### 1.2 节假日数据

- 数据源：`NateScarlet/holiday-cn`（MIT，2,222★，“自动每日抓取国务院公告”）；每年一个 JSON，字段 `date / name / isOffDay`；`isOffDay:false` 即调休上班日。例：2026 年 2026-01-04（周日）、02-14、02-28、05-09（周六）、09-20（周日）、10-10（周六）共 6 天为调休上班（`raw…/2026.json`，引用 gov.cn 公告 `202511/content_7047091.htm`）。`已确认`
- 同步：每日一次拉取当年与次年 JSON → upsert `holiday_calendar`，记录 `holiday_year_status`；离线安装包内置当时最新数据。
- **次年数据缺失**（国务院通常在上一年 11 月前后发布次年安排，以 2026 数据引用 2025-11 公告为例，`部分确认`）：
  - `holiday_year_status=missing` 时，`workday/restday` 退化为“周一至五/周六日”，并对该规则打 `calendar_degraded` 标记；
  - 后台与 IM（owner）提示“次年节假日未发布，按周一至五计算”；
  - 数据到达后**重算所有受影响规则的 `next_run_at`**，并对已排入但未触发的计划做一次差异提示。
- 手工覆盖：后台可添加 `source='manual'` 的日期（公司自定假期），优先级高于公开数据。

### 1.3 判定函数

```python
def is_workday(d: date, cal) -> bool:
    rec = cal.get(d)                 # holiday_calendar
    if rec is not None:
        return not rec.is_off_day    # 放假日→False；调休上班日→True
    return d.isoweekday() <= 5       # 无记录：周一至五为工作日

def is_restday(d: date, cal) -> bool:
    return not is_workday(d, cal)
```

### 1.4 下次触发计算

```python
def next_fire(rule, tz, after_utc, cal):
    local = after_utc.astimezone(ZoneInfo(tz))
    for d in day_iter(local.date(), horizon_days=800):           # 跨年与月末都覆盖
        if not matches_date(rule, d, cal): continue
        for t in rule.times:                                      # 支持一天多次
            cand = combine(d, t, tz)                              # 处理夏令时不存在/重复时刻（中国无夏令时，但订阅者可能在别的时区）
            if cand > local and not skipped(rule, cand): return cand.astimezone(UTC)
    return None   # once 已过 / until 已到

def matches_date(rule, d, cal):
    match rule.type:
      case "once":    return d == rule.at.date()
      case "daily":   return True
      case "weekly":  return d.isoweekday() in rule.days
      case "monthly": return month_match(rule, d)                 # day / last / nth weekday / overflow
      case "workday": return is_workday(d, cal)
      case "restday": return is_restday(d, cal)
      case "cron":    return cron_date_match(rule.expr, d) and calendar_ok(rule.calendar_filter, d, cal)
```

### 1.5 调度循环（借鉴 ORC 60s tick + PPC catch-up）

- Tick：默认 15 s（比 ORC 60 s 更细，保证 9:00 准点；`schedule.next_run_at` 有索引，扫描成本低）。
- 抢占：`UPDATE schedule SET next_run_at=? WHERE id=? AND next_run_at=?`（乐观并发，PPC `routines.ts:3199` 同思路），写 `schedule_run(schedule_id, planned_at)` 唯一键防重复触发。
- 错过（设备休眠/关机）：`catch_up = skip | run_once | run_all_capped`（PPC `catch_up_policy`）；超过宽限（默认 10 分钟）记 `missed`（ORC `missedBeyondGrace`）。
- 并发：`skip_if_running | queue | parallel`（PPC `concurrency_policy`）。
- 动作 `action_json`：
  - `prompt_agent`：向某 AgentProfile 发 prompt（`session_mode: reuse | new_per_run`，借鉴 CCC `CronJob.SessionMode`），结果按绑定路由；
  - `send_text`：固定文本；
  - `broadcast`：先生成内容再扇出到订阅组（场景 4，`07 §4`）；
  - `sv_task`：创建总控运行（场景 3 的周报/巡检）。
- 无人值守审批策略默认 `deny-unattended`（`04 §10`）。

### 1.6 IM 中创建（自然语言 → 规则）
- `/remind 工作日 18:00 让 codex-a 汇总今日提交` → 解析器（规则优先，模型兜底）生成 rule + action → **回显确认**（例：今天 2026-10-16 周五 14:30 创建，回显“下次触发：今天 18:00；法定假日不触发，调休上班的周末会触发”）→ 用户回“确认”才保存。

## 2. `/clear`：至少一端新开对话

| 输入端 | 协议动作 | 旧会话 | 证据 |
|---|---|---|---|
| ACP（Claude/Codex/Cursor/OpenClaw） | 若 `sessionCapabilities.close` → `session/close`；然后 `session/new{cwd}` | `fleet_session.status=closed`，写 `session_lineage(reason='clear')`，可 `/resume` | P1 C5、§6 |
| Coze | `POST /v1/conversations/{id}/clear`（新上下文片段，同 conversation） | 记 lineage（同 agent_session_id，generation+1） | P2 §6.2 |
| ZCode（实验） | `session/close` + `session/create` | 进程内会话不可恢复 | P2 §5 |
| CLI 一次性 | 丢弃 resume id，下次不带 `--resume` | 旧 id 仍可 `/resume` | P2 §1–§3 |
| OpenClaw 特例 | `openclaw acp --reset-session` 或 `_meta.resetSession` | — | P2 §4 |

- `/clear` 默认作用于当前 `reply_cursor` 指向的输入端；`/clear codex-a` 指定；`/clear all`（owner）清当前绑定内全部。
- 不把 `/clear` 透传给 Agent（ACP 无此原语；Claude CLI 的 `/clear` 只在其 TUI 内有效），由网关拦截（P4 P7）。
- 回执：`已为 [Codex·repoA] 新开对话（旧会话 F-01J… 可用 /resume 找回）`。

## 3. 两端对话记录查看（按 session / resume ID）

### 3.1 原则
- **网关事件库是唯一事实来源**（P4 P1）：两端（IM 入/出、Agent 入/出）都在流经时落 `event`；Agent 本地历史（Claude JSONL 官方声明为内部格式、勿解析，P2 §1.2）只做**冷导入**，`source='import'`，失败不阻塞。
- 三种 ID 都可查：`fleet_session_id`（网关）、`agent_session_id`（resume ID：Claude session_id / Codex thread_id / Cursor chatId / Coze conversation_id）、`channel_thread_id`（IM 会话）。

### 3.2 查询接口

| 入口 | 用法 | 实现 |
|---|---|---|
| IM | `/history 20`（当前会话最近 20 条）、`/history F-01J…`、`/history resume:9f3c…`、`/search 登录 超时` | 读 `event` / `event_fts`；结果按渠道切分，微信只发摘要 + “在控制台查看全文”链接（受额度约束） |
| Gateway API | `GET /api/sessions?profile=&peer=&status=`；`GET /api/sessions/{fleet_id}/events?cursor=`；`GET /api/sessions/by-agent/{kind}/{agent_session_id}`；`GET /api/search?q=&profile=&since=` | 索引 `ix_fs_agent`、`ix_event_session`、FTS5 trigram |
| 控制台 | 会话列表 + 时间线 + `/clear` 谱系图 + “复制 resume 命令”（如 `claude --resume <id>`、`codex exec resume <id>`，借鉴 ORC `resume_command`） | AFX HistoryPage 扩展 |

### 3.3 冷导入器（只读、可失败）

| 导入器 | 来源 | 去重 | 标签 |
|---|---|---|---|
| ClaudeTranscriptImporter | `~/.claude/projects/<cwd转义>/<id>.jsonl`（默认保留 30 天） | `(kind, agent_session_id, line_hash)` | 部分确认（格式会变） |
| CodexRolloutImporter | `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-*-<id>.jsonl` | `session_id + parent_thread_id`（恢复会写新文件） | 部分确认 |
| OpenClawSqliteImporter | `~/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite` | 树结构 `id+parentId` | 部分确认 |
| ACP `session/load` 回放 | 支持 `loadSession` 的 Agent | 按 `turn` 对齐 | 已确认（协议），预算受限（OpenClaw 16 MiB） |

中文检索：FTS5 `trigram`（本轮实验可命中中文子串，`01 §0.3`）；不足 3 个字的查询退化为 `LIKE`；质量与体积在 PoC-5 评估，备选 jieba 预分词。

## 4. 分身数据 loop（身份数据采集优化，自动更新）

### 4.1 目标
让“你的数字分身”（总控与各员工眼中的“老板偏好”）随使用自动变准：审批口径、技术偏好、沟通风格、常驳回方案、汇报格式。

### 4.2 管线

```
采集(Gateway 事件)          过滤                  Hindsight(persona:<user> bank)        产出                     生效
 ├ IM 指令/需求原文   ──▶  只要：指令、决策、   ──▶ retain(document_id=fleet_session,  ──▶ consolidation  ──▶  mental models    ──▶  画像版本 vN
 ├ 审批与驳回               纠正、驳回、偏好、        tags=[kind,project], timestamp)      → observations        - 技术偏好            (diff 送审)
 ├ 对汇报的纠正             会话总结；                                                    (去重/冲突/证据)      - 审批口径              │用户批准
 ├ /clear 前的会话总结      去掉：心跳、进度、                                                                     - 沟通风格              ▼
 └ 会议中被采纳的意见       工具噪声、密钥                                                                         - 汇报格式      注入：经理提示 / 员工任务包约定
```

- **触发**：Hindsight 中普通 pinned mental model 默认 `refresh_after_consolidation=false`，**必须显式开启**或设 `refresh_cron`（两者互斥）（R5 §5.2，`memory_engine.py:17130,19252-19260`，`已确认` 机制）；bank 需 `enable_observations && enable_auto_consolidation`（默认值 `部分确认`）。
- **生效需审批**：画像新版本生成 diff（参考 Paperclip `agent_instruction_revisions` 版本化）→ 通过 p3 低优先级消息或控制台提示 → 用户批准后才注入；拒绝的条目回写为“纠正”信号。
- **订阅更新事件**：Hindsight webhook `consolidation.completed`（`webhooks/models.py:11`）→ Gateway 记录“画像有 N 条新观察待审”。
- **AFX 衔接**：AFX `core/memory.py` 已有 `record_decision / record_correction / distill_from_report`（按项目 JSON 存储），作为**无 Hindsight 时的降级实现**与采集钩子来源。

### 4.3 隐私与成本
- 默认只采集 owner 本人；群聊/他人消息默认不入库；Memory Defense 开 REDACT（R5 §4）。
- retain 每条都调 LLM：按事件类型过滤 + 每日批量；预算超限即停采并提示。

## 5. 知识库（项目设计 / 目录结构图谱 / 上下文记忆）

### 5.1 bank 规范（Hindsight）

| bank | 内容 | 写入者 | 读取者 |
|---|---|---|---|
| `project:<id>` | 设计文档、ADR、会议纪要与决策、目录图谱快照、会话总结 | Gateway、总控、（可选）官方 coding-agents 钩子 | 总控、员工（MCP `/mcp/project:<id>/`） |
| `persona:<user>` | 分身信号（§4） | Gateway | 总控 |
| `supervisor:<config>` | 公司规范、审批红线（`directives`） | 用户/总控 | 总控 |

**避免重复 retain**：官方 coding-agents 钩子（stop 时回写转录）与 Gateway 回写二选一；默认 Gateway 回写，`document_id=fleet_session_id` 保证幂等（幂等性 `证据不足`，PoC-4 验证）。

### 5.2 项目设计
- 来源：仓库内 `docs/`、`ADR`、`README`、`AGENTS.md`；会议决策记录；用户在 IM 中的设计指示。
- 落地：retain 为 documents；建立 Hindsight knowledge page“项目设计总览”（`/knowledge-base/*`，R5 §2 R9），触发器 `delta + refresh_after_consolidation`（knowledge page 默认即此，R5 §5.2）。

## 6. 5W1H / 追问 / 钢人 / 最终判断

- **What**：五个拓展功能的规则、数据、流程与降级。
- **Why**：需求列为“非必需但更好”；其中调度与 `/clear`、历史是 MVP 体验关键，分身与知识库是长期价值。
- **Where/When**：调度、`/clear`、历史在 V0.2–V0.3；知识与分身在 V0.6。
- **Who**：Gateway owner；记忆层集成 owner；用户（隐私与审批）。
- **How**：§1–§5。
- **What if**：holiday-cn 停更 → 手工维护年表（每年 1 次，约 30 条）+ 国务院公告人工录入；Hindsight 成本过高 → 只保留知识页与 directives，分身改每周批量；Agent 历史格式变 → 导入器失败不影响主流程。

**追问**：“工作日判断真的需要调休？”——是：2026 年有 6 个调休上班的周末（§1.2 数据），只按周一至五会让“工作日 9 点日报”在这 6 天漏发、在放假的工作日误发。反方：用户可能只想要“周一至五”。→ 两种都提供：`weekly days=[1..5]` 与 `workday`，向导里并列并显示未来 30 天预览。

**钢人反方（知识库）**：“自研轻量 KB（SQLite FTS + 向量）就够了。”——支持：轻、同栈。反对：缺 consolidation/去重/证据/版本化 mental model，分身 loop 做不好（R5 §5.3 主张 B）。裁决：Hindsight 为主，自研轻量为降级。

**最终判断**：
1. 结论：调度以“规则引擎 + holiday-cn + 缺年降级”实现；`/clear` 由网关拦截映射到各协议；历史以事件库为准；分身与知识库外接 Hindsight。
2. 依据：§1–§5 引用。
3. 代码证据：ORC `automation-schedules.ts:10-26`、`service.ts:41,233-300`；PPC `routines` schema `:118-119`；CCC `cron.go:23-41`、`timer.go:17`；HDS `memory_engine.py:6899-6901,17130,19214-19260`；AFX `core/memory.py`。
4. 命令证据：holiday-cn API 与 2026.json（`01 §0.3`）；trigram 实验。
5. 前提：Hindsight 可在设备上部署；用户同意分身数据采集范围。
6. 局限：节假日次年发布时间为经验判断；中文检索与召回未评测。
7. 未验证：Hindsight `document_id` 幂等；mental model 刷新时延与成本。
8. 风险：隐私、LLM 成本、数据源停更。
9. 下一步：PoC-4、PoC-5；调度器在 V0.3 交付。
10. 是否进入下一阶段：允许（调度/`/clear`/历史进入 MVP 设计；知识与分身待 PoC-4）。
