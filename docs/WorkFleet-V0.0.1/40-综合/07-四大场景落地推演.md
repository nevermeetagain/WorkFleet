## 1. 场景 1：三个项目、6 个开发工具同时开发，微信 ClawBot 统一接收

### 1.1 配置
- 输入端（AgentProfile，6 个工具 × 3 项目按需组合，示例 8 个）：

| 别名 | 工具 | 协议族 | 项目 | 备注 |
|---|---|---|---|---|
| `claude-a` | Claude Code | acp（`claude-agent-acp`） | 项目 A | |
| `codex-a` | Codex CLI | acp（`codex-acp`） | 项目 A | |
| `cursor-b` | Cursor | acp（`agent acp`） | 项目 B | 需回复 `cursor/ask_question` 等阻塞扩展（P2 §3.1） |
| `oc-b` | OpenClaw | acp（`openclaw acp`） | 项目 B | per-session mcpServers 不支持 |
| `zcode-c` | ZCode | cli-oneshot（`zcode -p`），app-server 实验 | 项目 C | **需关闭 ZCode 自带微信 Bot**，否则争抢同一 ClawBot 绑定（P2 §5.3，部分确认） |
| `coze-ops` | Coze | http-cloud | 运营 | 不能操作本地代码，UI 标注“云端智能体” |
| `claude-c`、`codex-c` | … | acp | 项目 C | |

- 输出端：`wechat:me`（扫码者本人，`multiUserPerBot=false`）；fallback：`feishu:me` 或 `telegram:me`。
- 绑定：`mgmt-wechat`（mode=management，inputs=`tag:all`，outputs=`wechat:me owner primary` + `feishu:me fallback`，reply_target=last-active）。

### 1.2 端到端流程
1. 用户只扫码一次：控制台“输出端→微信”生成二维码，网关成为唯一 ClawBot 持有者；若以前有其他工具绑过，按 supersede 规则旧绑定失效（WCB `app.py:131-161`）。
2. Codex 在项目 A 完成 turn → `turn.end` → Router 命中 `mgmt-wechat` → Renderer：微信只支持纯文本，生成 `[Codex·A] 修复 3 处竞态，测试 42/42 通过。回复 /history 查看` → QuotaGuard（剩余 7→6）→ 发送。
3. Claude 请求执行 `rm -rf build/` → `perm.request(p0)` → 微信渲染 `回复 Y1 允许一次 / N 拒绝`（无按钮渠道）。
4. 用户回 `Y1` → 入站刷新 `context_token`、额度窗口重置 → PermissionBroker 校验 → ACP 回复对应 `optionId`。
5. 用户发 `@cursor-b 把登录页改成深色` → 前缀路由到 cursor-b；回执“已转给 [Cursor·B]”。
6. 用户发 `/clear` → 当前目标（cursor-b）`session/new`，旧会话可 `/resume`。
7. 三个项目同时有 5 条完成消息而微信额度只剩 2 → p3 合并为 1 条摘要；p0 审批占用保留额度；额度耗尽 → p0 走飞书 fallback，p2/p3 排队到下一次用户入站后发送（并在最后一条可送达消息里提示“回复任意字续期”）。

### 1.3 约束与风险
| 约束 | 来源 | 处理 |
|---|---|---|
| 1 微信号 ↔ 1 Bot，仅路由到最新扫码绑定 | P3 §1.3（部分确认） | 网关独占；向导提示关闭其他工具的微信 Bot |
| `context_token` 24h、每入站约 10 条主动消息 | P3 §1.3（部分确认） | QuotaGuard + 合并 + fallback |
| 链接不可点击、无按钮 | P3 §1.3 | 口令审批；长内容只给摘要 + `/history` |
| “斜杠”文本能否送达 | P4 §8（部分确认） | PoC-1 实测；不行则改用中文口令（如“清空”“切换 codex-a”） |
| 多个工具同时请求审批 | — | 审批口令带序号（Y1/Y2…），按 `requestId` 绑定 |

### 1.4 验收标准
- 一次扫码后 7 天内无需重绑；8 个输入端的完成/审批消息都能到达微信或 fallback；`/use`、`@别名`、`/clear`、`/history`、`/resume`、`/stop` 全部可用；任何时候微信侧未出现超过额度的发送失败（失败率 < 1%，被平台限流的已正确降级）。

## 2. 场景 2：飞书数据管理（推广 / 运营 / 销售 → 数据分析部门 + 老板）

### 2.1 配置
- 输入端：`promo-analyst`、`ops-analyst`（Coze 工作流或 ACP Agent 均可）、`sales-summarizer`（汇总销售数据，可为 Codex/Claude 读取本地数据仓或 Coze）。
- 输出端：`feishu:corp`（企业自建应用，长连接），对端：`group:数据分析部`、`user:老板`。
- 绑定（团队模式，扇出 + 过滤）：

| 绑定 | inputs | outputs | filter |
|---|---|---|---|
| `data-dept` | `tag:analytics`（3 个） | `feishu:corp / group:数据分析部` | 全部 `msg.final`、`plan.update`、p0–p3 |
| `boss` | `profile:sales-summarizer`（汇总者） | `feishu:corp / user:老板` | 仅 `msg.final` 且 `prio ≤ p1`，或标记 `report=true` |

- 调度：`workday 18:00` → `sales-summarizer` 拉取三方结果生成日报（`prompt_agent`，`session_mode=new_per_run`）；`weekly [1] 09:00` 周报。

### 2.2 流程
1. 工作日 18:00（法定假日不触发，调休上班日触发）→ 三个分析 Agent 各自产出 → 数据部群收到 3 条卡片（飞书卡片 2.0；长内容流式更新）。
2. 汇总者读取三份结果（经 Fleet MCP `fleet_status`/事件检索）→ 生成老板版（1 屏、结论先行）→ 只发老板私聊。
3. 老板在卡片上点“需要细节” → `card.action.trigger`（3 秒内 ACK）→ 路由到汇总者生成详版。
4. 需要审批的事项（如“申请追加推广预算”）→ 走飞书原生审批实例（`approval/v4/instances`，100 次/分）。

### 2.3 约束
| 约束 | 来源 | 处理 |
|---|---|---|
| 同一用户/同一群 5 QPS；接口 50/s、1000/min；批量 50 万/天 | P3 §2 | 令牌桶预设 |
| 长连接仅企业自建应用；回调 3 秒内处理 | P3 §2 | 先 ACK 后异步 |
| 卡片回调能否走长连接 | P3 §10（证据不足） | PoC-3；不行则经 Hub 提供 HTTPS 回调 |
| 用户须在应用可用范围 | P3 §2 | 安装向导检查 |
| 长连接集群模式（多实例只一个收到） | P3 §9 | Edge 单实例 |

### 2.4 验收
- 工作日 18:00 ± 1 分钟内三条到群、一条到老板；节假日不发；调休上班日发；卡片按钮可回流；老板只收到过滤后的消息。

## 4. 场景 4：大量用户订阅，每天 9:00 推送最新 AI 资讯

### 4.1 渠道结论
| 渠道 | 可行性 | 理由（P3 §7） |
|---|---|---|
| Telegram | ✅ 首选 | 用户 `/start` 后可推；免费 ~30 条/秒（10 万人约 56 分钟），付费广播最高 1000 条/秒（门槛两处官方说法不一致，部分确认） |
| 飞书 | ✅ 企业内 | 批量发送 50 万条/应用/天；接收者须在可用范围 |
| 钉钉 | ✅ 企业内 | batchSend 每次 ≤20 人；工作通知 500 次/用户/天 |
| Discord | ✅ 频道广播 | 一条频道消息即达全体；大规模 DM 不建议 |
| QQ | ⚠️ 有限 | 主动消息配额（新旧文档冲突）且用户可关闭 |
| **微信 ClawBot** | ❌ **不可行** | Bot 与扫码者 1:1，无法服务多人；24h 窗口 + 约 10 条额度 |

### 4.2 配置
- 订阅组 `ai-daily`（opt_in）；入口：TG `/start` + `/sub ai-daily`，飞书/钉钉由管理员按部门导入或员工自助订阅；退订 `/unsub ai-daily`。
- 资讯生成：`news-agent`（可为 Claude/Codex 带检索工具，或 Coze 工作流）。
- 调度：`daily 09:00`，时区按订阅者（默认 Asia/Shanghai）分桶；动作 `broadcast`。
- 部署：订阅者 ≤ 数千 → Edge 可承担；更大规模 → 启用 Hub（Postgres + 多 worker，`FOR UPDATE SKIP LOCKED`）。

### 4.3 流程
1. 08:30 预生成：调度器提前触发 `news-agent` 生成当日内容（避免 9:00 才开始生成导致延迟）；内容进事件库，人工可选审核（`require_review`）。
2. 08:55–09:05 扇出：BroadcastPlanner 按渠道吞吐预算切片，写 `broadcast_delivery` → Outbox → 令牌桶 → 适配器；TG 429 按 `retry_after` 退避。
3. 回执与统计：sent/failed/blocked（用户拉黑或未 `/start`）；失败重试 ≤3 次；`blocked` 自动标记订阅失效。
4. 订阅者回复：进入其独立会话（可交给 FAQ Agent 或忽略），不影响广播。
5. 个性化（可选，V0.6 后）：按订阅者偏好（Hindsight persona，仅在用户同意时）生成少量变体，不做一人一稿。

### 4.4 约束与合规
- 只推送给主动订阅的用户；保存订阅时间与来源；一键退订（法律细节 `证据不足`，需法务确认，尤其中国大陆用户个人信息）。
- 9:00 指订阅者本地时间还是固定时区 → 默认订阅者时区（`subscription.timezone`），可配置。

### 4.5 验收
- 1 万 TG 订阅者在 9:06 前送达 ≥ 99%（未被用户屏蔽的部分）；飞书/钉钉在各自限额内完成；退订即时生效；微信渠道在向导中不可选为该绑定的输出端（能力位 `broadcast.supported=false` 直接拦截）。

## 5. 5W1H / 追问 / 钢人 / 最终判断

- **What**：四个场景在同一套绑定表上分别是管理、团队、总控、通知四种写法。
- **Why**：验证设计不是“为每个场景单独造轮子”。
- **Where/When**：S1 → V0.2；S2 → V0.3；S4 → V0.4；S3 → V0.5（`08`）。
- **Who**：用户（配置与审批）、管理员（飞书/钉钉可用范围）、订阅者。
- **How**：§1–§4。
- **What if**：微信 1:1 约束被证伪（多人可用）→ S4 可加微信，只改能力位；Telegram 在用户所在网络环境不可用 → S4 主渠道换飞书/钉钉（企业内）或 Discord 频道（`待确认`：订阅者群体是谁）。

**追问**：“S4 的‘大量用户’是谁？企业内部员工还是公众？”——这决定渠道（企业内 → 飞书/钉钉；公众 → Telegram/Discord，国内公众渠道受限）。需求未说明 → `待确认`（列入 `08` 开放决策）。

**钢人反方**：“S1 用多个微信 Bot 账号（每工具一个）更稳。”——支持：避开额度与路由复杂度。反对：与“只有一个常用微信”的核心诉求冲突；每个微信号只能有一个 Bot（P3 §8）。裁决：维持单绑定复用。

**最终判断**：
1. 结论：四个场景都可在 `04/05/06` 设计上落地；S4 明确不使用微信。
2. 依据：P3 渠道约束表；`04` 绑定模型。
3. 代码证据：WCB `app.py:131-161`；CCC `cron.go:23-41`（对比）；OCL `cron/types.ts:55-68`（对比）。
4. 命令证据：holiday-cn 数据（调休判定）；`01 §0.3`。
5. 前提：PoC-1/3/6/7 通过。
6. 局限：未真机；吞吐为按官方限额推算。
7. 未验证：微信额度真实值；飞书卡片回调长连接；QQ 主动配额；Telegram 付费广播门槛。
8. 风险：平台政策变化；S4 合规。
9. 下一步：按 `08` 执行 PoC。
10. 是否进入下一阶段：允许。
