## 3. 每类缺口的补充方案要点

### 3.1 G01 单绑定多路复用（核心痛点）
- **连接层**：`ChannelConnectionPool` 以 `(adapter, credential_fingerprint)` 为键，保证一个微信 ClawBot token 只有一条 `getupdates` 长轮询；重复扫码时按 WCB 的 supersede 规则把旧账号置 `expired`。
- **路由层**：入站消息先过 CommandBus（`/use`、`@别名` 前缀），否则按 Binding 的 `reply_target`（`last-active` | `pinned` | `ask`）决定发给哪个输入端；出站消息统一加来源标签 `[Codex·repoA]`。
- **额度层**：微信窗口额度（每入站重置约 10 条、24h 窗口，`部分确认`）由 `quota_state` 管理，长任务只发最终结果；额度不足时合并摘要或走 fallback 渠道。
- **验证**：PoC-1（`08`）。若 iLink 实际允许多 bot 或额度更宽，只改能力位参数，不改架构。

### 3.2 G11 通知/广播
- 订阅是“用户主动加入”的记录：存平台、peer、时区、加入时间、来源、退订时间。
- 一次生成、多次投递：定时任务先让“资讯 Agent”生成一份内容（或按用户画像少量变体），再写入 `broadcast_delivery` 扇出；投递 worker 按渠道令牌桶消费。
- 渠道选择：Telegram（首选）、飞书/钉钉（企业内）、Discord（频道一条即达），QQ 受配额，**微信不承担**。

### 3.3 G16–G19 总控
- 详见 `05-总控模式设计.md`。关键原则：**员工是外部 ACP 会话**（不是内部 LLM 角色，这是与 PentAGI 的根本差别）；会议在网关层编排（ACP 没有 Agent↔Agent 语义，P1 §2）。

### 3.4 G15 调度 / G20–G22 知识与分身
- 详见 `06-拓展功能设计.md`。

## 4. 5W1H（针对“缺口能否在可控成本内补齐”）

- **What**：29 项缺口，约 197–286 人日；其中 7 项“无人实现”（`01 §3.2`）。
- **Why**：根因是各项目的问题域不同（个人助手 / 公司 OS / IDE / 聊天框架），它们共同缺的恰好是 WorkFleet 的差异化价值（单绑定复用、广播、总控、节假日）。
- **Where/When**：G01–G05、G10、G12–G14 是 MVP 前置（管理模式闭环）；G11 依赖 G10；G16–G19 依赖 G03、G12、G14；G20–G22 依赖 G13。
- **Who**：单人开发约 9–13 个月（按 22 人日/月折算，`部分确认`）；两人并行约 5–7 个月。
- **How**：先 PoC 去风险（`08`），再按里程碑交付；借鉴件按许可证规则处理。
- **What if**：
  - Python ACP SDK 不足 → 改用 Node 旁车（官方 TS SDK / acpx），Python 通过 JSON-RPC 调用旁车，G03 +3–5 人日。
  - botpy 不可用 → 自写 QQ 客户端，G07 +3–4 人日。
  - iLink 1:1 不成立 → G01 简化，风险降为中。

## 5. 苏格拉底追问与双向钢人

**主张：“借鉴 + 自研”比“fork 一个底座再补”总成本更低。**
- 凭什么？按缺口表，选 A（cc-connect）能省下 G03、G05–G09 大部分（约 30–45 人日），但必须承担：改 Engine 装配（G01 难度上升）、无 LICENSE 文件的法律不确定、1.77 万行 `engine.go` 的维护、Go 与用户现有 Python 内核/控制台两套技术栈；总控/广播/节假日/事件库/知识库（约 120–170 人日）无论选谁都要自研。
- 反方最强：IM 适配器是“看似简单、细节无穷”的活（限流、重连、卡片、文件、扫码），cc-connect 已踩完坑；自写 6 个通道的真实成本可能翻倍。
- 裁决：反方部分成立 → 在 `08` 中设置**决策闸门**：若 PoC 阶段 6 个通道中有 ≥2 个用 Python SDK 打不通，转为“cc-connect 作为通道旁车（经其 Management API / Bridge）”的混合路线（方案 A′），前提是作者补齐 LICENSE。

1. **结论**：所有缺口都有可行补法；高风险集中在微信约束（G01/G05）与总控质量（G16/G17）。
2. **依据**：§1 表格逐条来源。
3. **代码证据**：见表中文件:行。
4. **命令证据**：§0 GitHub API 元数据。
5. **前提**：采用 `03` 推荐路线；单人或双人开发。
6. **局限**：工作量为经验估算，未做任务拆解到小时；SDK 功能覆盖未实测。
7. **未验证**：Python ACP SDK 对 load/resume/permission 的完整支持；botpy 对 API v2 的支持；飞书卡片回调走长连接。
8. **风险**：平台政策、上游接口漂移、总控效果不达预期。
9. **下一步**：执行 `08` 的 PoC 清单。
10. **是否进入下一阶段**：允许进入架构设计与 PoC；**不允许**在 PoC 前承诺交付日期。
