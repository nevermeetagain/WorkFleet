## 2. 第一轮：5W1H

### What（客观事实）
- 需求核心：多输入（6 类，3 个协议族）× 多输出（6 个 IM）× 4 种模式，外加调度、/clear、历史、分身、知识库。（`00-原始需求.md`）
- 事实 F1：没有候选在统一口径 ≥80%（OCL 68、CCC 65）。`部分确认`（`01 §1`）
- 事实 F2：七项需求无人实现：单绑定复用、订阅广播、节假日调休、会议、强制把关上报、目录图谱、网关级统一事件库。`部分确认`（`01 §3.2`）
- 事实 F3：微信 ClawBot 1 微信号↔1 Bot、只路由到最新扫码绑定、24h `context_token`、每入站约 10 条主动额度。`部分确认`（P3 §1.3；R1 §5 结论 C）
- 事实 F4：六个 IM 都有长连接/长轮询模式，网关可完全在设备上运行，无需公网。`已确认`（P3 §0）
- 事实 F5：ACP v1 为 stdio JSON-RPC；无 `/clear` 原语；v2 草案会移除 `session/load`。`已确认`（P1 C2、C5、C7）
- 事实 F6：用户已有 `aideanew/AideanFleet`：Python + SQLite 单写者内核、事件 outbox、规划器、DAG、门禁、审批、预算、Vue 控制台（:3100）、Windows 安装器，无 IM、无 ACP。`已确认`（文档+目录+grep；未运行）
- 事实 F7：许可证：cc-connect、WechatClawbot 无 LICENSE 文件；AstrBot AGPL；PentAGI 附限制性 EULA；Orca/Paperclip/OpenClaw/acpx/Hindsight MIT；AionCore Apache-2.0；AFX Proprietary。`已确认`

### Why（深层原因）
- 用户痛点的根因不是“缺一个协议”，而是“每个工具各自持有 IM 绑定”+“微信只允许一个绑定”（P1 §10、P3 §1.3）。因此产品价值的**根**是“网关独占绑定 + 多路复用 + 统一事件库”，而这恰好是所有候选都没有的（F2）。
- 只修表面（例如 fork 一个桥再加命令）会留下更深问题：桥的数据模型以“项目/agent”为中心而非“路由”为中心（CCC `main.go:361-421` 每 project 建 N 个 Platform；PPC endpoint↔agent 1:1、conversation↔issue 必绑），改造会触及核心。

### Where / When（边界与时间）
- 运行位置：Edge（用户设备）为主；Hub 只在大规模广播/多设备/需公网回调时启用（P4 §1）。总控必须在 Edge（需求原文）。
- 端口：AFX 已有约定 **Fleet 3100–3200**，控制台 3100（`fleet/core/ports.py`，ADR-005）。需求方法文本中的 Aidean 3000 / AideanBot 3333 属于其他项目（ADR-005 表：Aidean 3000–3100、aideanbot 3300–3400）→ 本项目**不使用** 3000/3333，`待确认`由用户最终拍板。P4 §11 的 3000/3333 暂定被本结论取代。
- 先后顺序：PoC（去风险）→ 管理模式 MVP → 团队模式 → 通知模式 → 总控 → 知识/分身（`08`）。

### Who（主体与责任）
- 平台方：腾讯（微信 iLink、QQ）、字节（飞书）、阿里（钉钉）、Discord、Telegram；Agent 厂商：Anthropic、OpenAI、Cursor、OpenClaw、智谱、字节 Coze。
- 用户：最终决策（技术栈、许可证策略、端口、隐私边界）。
- 上游维护者：cc-connect 作者（LICENSE）、PentAGI（EULA 解释）。

### How（实现路径）
- 见 `04-自研架构设计.md`：Gateway 层（Channel/Input 适配器、Router、CommandBus、PermissionBroker、Outbox+RateLimiter、EventStore、Scheduler）+ Supervisor（复用 AFX 内核）+ Hindsight（外部）。

### What if（前提变化）
| 变化 | 影响 | 应对 |
|---|---|---|
| 腾讯放宽 ClawBot（多用户/更多额度） | 微信可承担通知模式 | 只改能力位（P4 §4 `multiUserPerBot`、配额参数） |
| 腾讯收紧或停服 | 管理模式失去主通道 | 预置 fallback 渠道（飞书/QQ/TG），p0 消息自动降级 |
| Python ACP SDK 不成熟 | G03 受阻 | C2′：Node 旁车承载 ACP（官方 TS SDK 或 acpx），Python 经 JSON-RPC 调用 |
| ACP v2 落地 | 事件处理需改 | 编解码器可插拔（AcpV1Codec/AcpV2Codec），信封不变 |
| 用户要求开源 / 商用闭源 | 决定能否吸收 AGPL 代码 | 默认闭源可用：不拷贝 AGPL/无许可代码 |
| AFX 内核不适合网关高并发 | 性能瓶颈 | Gateway 独立进程、独立 `gateway.db`，与内核只经事件/API 交互 |
| 端口被占 | 启动失败 | 端口唯一定义点 + 启动时报错不漂移（沿用 P4 §11 的“不自动换端口”原则） |
| 用户只要 S1（汇聚） | 总控/广播价值下降 | 里程碑可在 V0.2 停下，已可用 |

## 3. 第二轮：苏格拉底追问（对每个关键结论）

### Q1 “方案 A（cc-connect）最快？”
1. 凭什么？6/6 IM + 通用 ACP 已实现（L1 §2，`已确认`）。
2. 证据来自最新代码？是（`7da94a4`，2026-10-16）。
3. 相反证据？① 同一微信 token 被多个 project 同时长轮询的行为 `证据不足`——这恰是核心痛点；② `CronJob.SessionKey` 单值（本轮复核 `cron.go:23-41`）→ 场景 4 需新建；③ 无 LICENSE 文件（本轮复核）。
4. 是否把表面现象当根因？是的风险：“适配器全”是表面，“路由中心的数据模型”才是根。
5. 结论成立前提：用户接受 Go、作者补 LICENSE、PoC 证明平台单例改造可行。
6. 足以支持“选 A”？**不足**。

### Q2 “方案 B（OpenClaw）路由最成熟？”
1. 凭什么？bindings 分层匹配 + 多账号（L2 §2 `resolve-route.ts:405-424`，`已确认`）。
2. 相反证据：钉钉缺失；微信插件仅单聊且许可证 NOASSERTION；所有消息先经 OpenClaw Agent 运行时（成本与延迟）；源码包 177 MB、日更；单 DM 同时只能绑定一个 agent。
3. 足以支持“选 B”？**不足**；但其路由与会话键设计应借鉴。

### Q3 “方案 D（fork Paperclip）输入侧和总控最强？”
1. 凭什么？12 个适配器（含 ACP 引擎）、org chart、routine、审批（R2 §2）。
2. 相反证据：中文 IM 为 0 且 provider 写死在 TS 常量与 DB CHECK（`chat-channels.ts:9-18`、`chat_channels.ts:123,289`）；endpoint 必须绑一个 agent（`:50`）；主动私信能力几乎全 false（`provider-catalog.ts:17-105`）；PR >16,500 的日更速度。
3. 足以支持？**不足**；R2 自身结论也为“不 fork”。

### Q4 “C1（新 TS 网关）优于 C2（扩展 Python 仓）？”
1. 支持 C1 的理由：ACP 官方 TS SDK 最新（P1 §8）、acpx 可直接 `import`（L5）、Orca/Paperclip/OpenClaw 代码是 TS，移植更省。
2. 相反证据：用户已在 Python 仓投入（约 2.98 万行 Python、契约/迁移/测试/安装器/控制台，F6）；官方 ACP Python SDK 存在且活跃（`agentclientprotocol/python-sdk`，Apache-2.0，2026-10-13 有推送）；飞书/钉钉/Telegram/Discord 都有官方或主流 Python SDK（`02 §0`）；Orca/PentAGI/AionCore 本就只能“设计移植”（Electron/Go/Rust 耦合），TS 的移植优势只体现在少数纯函数模块；Hindsight 本身是 Python。
3. 是否忽略了性能？网关是 I/O 密集，瓶颈在平台限流与 Agent 进程（P4 §3.2、P3），Python asyncio 足够；大规模广播放 Hub，用 Postgres `SKIP LOCKED` 横向扩 worker（R5 §3.5 的同款模式就是 Python）。
4. 结论：C2 更优，**但**保留 C2′（ACP 层 Node 旁车）作为 SDK 风险对冲。

### Q5 “Python 能达到‘高性能’？”
1. 定义：本产品的“高性能”= 低额外延迟（网关内部 p95 ≤ 20ms）+ 不丢消息 + 广播吞吐吃满平台配额，而不是 CPU 密集计算。
2. 证据：各平台限额（Telegram 30/s、飞书 50/s、Discord 50/s，P3）远低于 Python asyncio 单进程可处理的消息量级；真正重的是 Agent 进程（P1 §12 反对④）。
3. 未验证：具体数字需 PoC 压测（`08` P9）。`证据不足`

### Q6 “AFX 内核可以承载总控？”
1. 证据：README/架构文档描述了 `goal/todo/claim/lease/attempt/gate/quota/events`、返工 lineage、needs_user、Planner、Steer（F6）。
2. 相反证据：未运行；执行体是 CLI 无头（非 ACP），会议/旁路对话不存在；`MANAGER_PORT=9900` 与端口约定不一致（`存在缺陷`）。
3. 结论：作为总控的“任务内核”`部分确认`；会议与把关需新增（`05`）。

## 4. 第三轮：双向钢人论证

### 4.1 方案 A：cc-connect 底座
- **支持（最强）**：Go 单二进制，部署和资源最友好；6 个目标 IM、通用 ACP、cron+timer、`/new`、`/history`、`/search`、Web 后台、Management API、Bridge、Webhook、审批卡片全部现成；社区当天有合并。缺的东西（路由、广播、总控、KB）无论选谁都要自研，选 A 至少把“通道细节”这块最脏的活省了（约 30–45 人日）。
- **反对（最强）**：① 数据模型是“project = 1 Agent + N Platform”，单绑定复用要改 Engine 装配，而 `engine.go` 1.77 万行；② 无 LICENSE 文件，商用/闭源法律不确定；③ 用户现有资产是 Python，A 会造成 Go 网关 + Python 内核两套栈、两套控制台；④ 会话、cron、relay 都是 JSON 文件，不适合订阅者与统一事件库；⑤ 微信同 token 多实例行为未验证。
- **已排除**：“输出端覆盖不足”（已核实 6/6）。
- **仍成立**：①②③④⑤。→ **不作为主路线；保留为通道旁车回退（A′）**。

### 4.2 方案 B：OpenClaw 底座
- **支持**：路由一等公民、会话粒度丰富、记忆/cron/UI/ACP 齐全、生态巨大、MIT。
- **反对**：Agent 网关心智（所有消息先过它的 Agent 运行时）；钉钉缺失；微信插件许可证未声明且仅单聊；体量与变更频率高；场景 4 不满足；与用户 Python 资产不同栈。
- **仍成立**：全部。→ **不选；路由设计借鉴**。另：OpenClaw 可作为一个**输入端**（`openclaw acp`）接入 AideanFleet。

### 4.3 方案 C1：新 TS 网关
- **支持**：ACP TS SDK 与 acpx 直接可用；P4 设计已按 TS 写好；Orca/Paperclip 纯逻辑模块可直接移植。
- **反对**：放弃用户现有 Python 资产（内核、控制台、安装器、契约、测试）；需新建第二个仓或第二套运行时；国内 IM 在 TS 侧同样要自写（Paperclip 的 Vercel Chat SDK 不含国内 IM，R2 6.1）。
- **仍成立**：资产浪费与双栈成本。→ **不作主路线；其中“ACP 层”作为 C2′ 的旁车形态保留**。

### 4.4 方案 C2：扩展 AFX（推荐）
- **支持**：① 复用现有内核（单写者、outbox、lease、gate、审批、预算）直接承载总控任务；② 控制台、安装器、端口约定、契约机制、测试体系现成；③ Python 有官方 ACP SDK 与主流 IM SDK（`02 §0`，`已确认` 元数据）；④ Hindsight 同为 Python，集成摩擦小；⑤ 所有“无人实现”的核心件本来就要自研，放在自有仓里最可控；⑥ 闭源（Proprietary）也无许可证冲突，只要遵守“不拷 AGPL/无许可代码”。
- **反对（最强）**：① AFX 只看了文档，未运行，内核质量与可扩展性是假设；② Python ACP SDK 成熟度未知（338★）；③ 6 个 IM 通道细节要自己踩坑（cc-connect 已踩过）；④ QQ 的 `botpy` 两年未更新；⑤ Python 在 Windows 上的 asyncio + 子进程（Proactor）有平台差异；⑥ AFX 版本 0.4.0 已有既定路线（`docs/进度与决策.md`），网关可能与其规划冲突。
- **排除情况**：⑤ 已有 AFX 在 Windows 上的子进程/编码测试（`tests/test_subprocess_encoding.py`、`test_procguard.py` 文件存在，`部分确认`）可作基础；②④ 有降级路径（C2′ 旁车、自写 QQ 客户端）。
- **仍成立**：①③⑥ → 通过 PoC-0/1/2 与用户确认消解。
- **可靠度**：中。

### 4.5 方案 D：fork Paperclip
- **支持**：S3 场景几乎直接可用；输入侧 90%、总控 55%；安全设计强。
- **反对**：中文 IM 需改常量 + DB CHECK + 大量 provider 专属文件；插件 SDK 无聊天通道扩展点；1 endpoint = 1 agent；广播模型冲突；日更上游合并成本极高；与 Python 资产不同栈。
- **仍成立**：全部。→ **不选**；可作为可选“上游输入端”桥接（R2 路线 2），注意其默认端口 3100 与 Fleet 冲突（`01 D7`）。

## 6. 第四轮：最终判断
