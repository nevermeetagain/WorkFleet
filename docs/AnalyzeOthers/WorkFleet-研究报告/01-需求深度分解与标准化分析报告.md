> WorkFleet V0.0.2 ｜ 2026-10-17 ｜ 方法：5W1H 发散 → 苏格拉底收敛 → 双向钢人论证 → 重构终稿

## 第一轮：发散分析（5W1H 全面拆解）

### What —— 客观事实与现象是什么？

**用户陈述的事实**：
1. 用户是开发者，日常**并发使用 5 个以上开发工具**（输入端示例：OpenClaw、Claude Code、Codex CLI、Zcode、Cursor、Coze）。
2. 用户只有一个常用微信，"扫码绑定后解绑，绑完这个绑那个"——即**输出端账号是稀缺资源，而输入端是复数**。
3. 期望产物是一个"多对多的 ACP 工具"。用户语境中 ACP = Agent Client Protocol（智能体客户端协议），泛指"智能体↔客户端"之间的通讯桥梁；在本研究中具体锚定为 Zed 发起、已被主流 coding agent 采纳的 ACP 标准（见报告 02）。
4. 用户指定了 6 个参考项目：WechatClawbot、Paperclip、pentagi、Orca、Hindsight、BettaFish。

**需求拆解为功能清单**（编号贯穿后续所有报告）：

核心需求（必须满足）：

| 编号 | 需求 | 用户原文要点 | 形式化 |
|-----|------|------------|--------|
| F1 | 多对多路由 | 多个输入端 ↔ 多个输出端 | 路由图 G=(I∪O, E)，I=输入端集合，O=输出端集合 |
| F2 | 后台配置管理 | "支持后台配置管理" | Web Admin Console + 持久化配置 |
| F3 | 管理模式 | 输入:输出 = N:1 | f: I → o（汇聚），如"3 项目 6 工具 → 微信 ClawBot 统一接收" |
| F4 | 通知模式 | 输入:输出 = 1:N | f: i → O（扇出/订阅），如"每日 AI 资讯 → 所有订阅用户" |
| F5 | 团队模式 | 输入:输出 = M:N | 按产品线/项目维度的多对多分组路由 |
| F6 | 模式内双向 | "管理模式适合接收，但也需要支持发送" | 输出端 → 输入端的反向指令通道（查询/指挥） |
| F7 | 多输出端覆盖 | 微信 ClawBot / 飞书 / QQ / 钉钉 / Discord / Telegram | 输出端适配器 ≥ 6 类 |
| F8 | 多输入端覆盖 | OpenClaw / ClaudeCode / Codex / Zcode / Cursor / Coze | 输入端适配器 ≥ 6 类，ACP 优先 |

拓展需求（非必需，有更好）：

| 编号 | 需求 | 用户原文要点 |
|-----|------|------------|
| E1 | 定时任务 | 只运行一次 / 工作日 / 休息日 / 每日 / 每周 / 每月 |
| E2 | 任一端新开对话 | 如微信 ClawBot 发 `/clear` 对 ClaudeCode 新开会话 |
| E3 | 双端对话记录查看 | 按 session / resume ID 查询历史 |
| E4 | 身份数据采集优化 | "自动更新分身数据-loop"（智能体画像/人格档案的自我维护循环） |
| E5 | 知识库存储 | 项目设计、目录结构图谱、上下文记忆 |
| E6 | 总控模式 | 本地运行的职业经理人：组织会议、明确需求、分析得失、统一意见、分配任务、把关归纳、非必要信息直接回复 |
| E7 | 总控可自定义模型 | 支持任选 LLM provider |
| E8 | 总控支持 skill 配置 | 技能/工具可插拔 |
| E9 | 总控随时对话不打断任务 | 总控聊天通道与任务执行通道隔离 |

**当前代码已经实现了什么**：无（这是 0→1 的选型+预研任务，WorkFleet 尚不存在代码库）。
**已被证据证明的内容**：见报告 02-09 的实证调研。
**仅是声明尚未证明的内容**：用户场景中"Zcode""Cursor 能否被 ACP 化"——Cursor 是 IDE 形态，其 agent 是否暴露 ACP 需实测【待确认】。

### Why —— 深层原因与动机是什么？

- **直接原因**：单微信号绑定名额有限（各工具的微信通知绑定通常一次一个），多工具并发导致绑定震荡，信息漏接。
- **根本原因**：**缺少一个"会话与通知的中间层"**——现有工具把"账号绑定"和"消息接收"耦合在每个工具内部，没有统一的身份、路由与通道抽象。
- **设计层面的洞察**：用户的本质需求不是"更多绑定"，而是**解耦**：输入端（算力/智能）与输出端（人体感知通道）应当是多对多的可配置映射，而人只维护少量"常驻接收端口"。
- **如果只做表面修补**（比如做个转发脚本）：会话上下文、审批流、历史记录、身份状态无法跨工具一致，很快不可维护。
- **该修改（新建工具）解决什么**：账号稀缺、信息割裂、上下文丢失；**引入什么风险**：单点故障（中枢挂了全断）、安全面扩大（凭证集中）、合规风险（微信通道）。

### Where / When —— 边界条件与时间节点是什么？

- **问题域**：本任务为研究与架构设计，不涉及修改任何现有代码库；产出物为研究报告包。
- **执行顺序**：需求分解（本报告）→ 协议/项目调研（02-09）→ 缺口与方案（10-12）→ 汇总（13）。后续验证依赖用户对路线的选择。
- **端口约定问题**（用户方法模板中提及 Aidean=3000、AideanBot=3333）：本任务为研究性质，不涉及 Aidean/AideanBot 的端口改造，无法也无需验证其端口约束；但在报告 11 的自研方案中，**沿用该约定作为 WorkFleet 的默认端口建议值**（管理控制台 3000 / 通道回调 3333），并标记为【建议值，待确认】。
- **不在范围内**：输出端 App 本身的开发（微信/飞书客户端）、输入端 agent 本身的开发（Claude Code 等）、模型训练。
- **时间节点**：ACP v1 已稳定、v2 草案进行中（报告 02），当前（2026-10）是入场好时机——底层协议收敛完成、中国官方通道（微信 ClawBot 插件 2026-03 上线）刚打开。

### Who —— 涉及主体与责任方是什么？

- **执行者**：本研究 Agent（清言 Agent）。
- **验收者**：用户本人（开发者，既是产品定义者也是唯一初始用户）。
- **涉及的外部主体**：各开源项目维护方、微信/飞书/QQ/钉钉/Discord/Telegram 平台方、Zed（ACP 规范方）、各 LLM provider。
- **责任划分**：需求歧义由用户裁决（见第四节"待确认清单"）；技术选型由本研究给出建议；最终实施由用户或其组织的开发"员工"执行。

### How —— 执行手段与实现路径是什么？

1. **读取真实材料**：实时抓取 6 个参考项目 + 生态候选项目的 GitHub 仓库主页、README、提交记录、语言构成、star/fork 数据；读取 agentclientprotocol.com 官方规范全文。
2. **不猜代码**：所有"执行逻辑"结论均锚定 README 中作者自述的机制（如 WeClaw 的三种 agent 模式表、Paperclip 的心跳执行描述、pentagi 的两阶段流描述）；无法确认的标记【待确认】。
3. **交叉验证**：同一结论至少两个独立来源（仓库 + 官网/文档/媒体报道）才标【已确认】。
4. **形成可复现证据链**：原始 JSON 快照留存于 `tmp/research/`，文件名与报告引用一一对应。

### What if —— 前提变化时结论会怎样？

| 前提变化 | 影响 | 应对 |
|---------|------|------|
| 微信 ClawBot 插件政策收紧（iLink API 限流/收费） | F7 微信通道成本上升 | 输出端适配器抽象层隔离，可切换企微/飞书兜底 |

## 第二轮：收敛与苏格拉底式追问（关键结论逐条拷问）

**Q1：我凭什么断定"没有单一开源项目满足全部需求"？**
证据：报告 09 的 20+ 项目横向扫描 + 报告 03-08 的 6 个深挖项目逐一对照 F1-F8/E1-E9 的覆盖矩阵（报告 13 表 2）。最接近的 WeClaw 只覆盖微信单输出端；OpenClaw 覆盖多通道但绑定单一 assistant 人格而非多输入端路由；Paperclip 覆盖编排但输出端是 Slack/Discord/Telegram 实验性连接器，无中国通道。反面检查：是否存在我没搜到的项目？搜索覆盖了 GitHub topics（clawbot/weixin-clawbot/acp/parallel-agents/distillation）、中英文关键词、官方文档，未发现全功能匹配者。结论成立，置信度高，但保留"小众新项目遗漏"的可能【部分确认】。

**Q2：用户说的 ACP 一定是我锚定的 Zed ACP 吗？**
用户原文："ACP（Agent Client Protocol）：智能体客户端协议"，且输入端示例全是 coding agent/agent 平台。Zed 的 ACP 是当前唯一名为 "Agent Client Protocol" 的公开标准（agentclientprotocol.com，JSON-RPC 2.0），且输入端示例项目（Claude Code、Codex、OpenCode、Gemini CLI、Goose）均已有 ACP 支持路径——锚定成立【已确认】。但存在歧义：用户也可能泛指"agent 与客户端间任意通讯"，故报告 02 同时给出 MCP/A2A 对照，方案设计保持协议无关的适配层。

**Q3："管理模式适合接收信息，不适合发送消息，但也需要支持发送"——这句话的真实含义？**
解读：在 N:1 模式下，6 个工具的**输出流**（进度、结果、报警）汇聚到 1 个微信，这是主链路；反向（人在微信里发话 → 指定某个工具执行）是次链路，需要"寻址"能力（@哪个 agent、哪个 session）。WeClaw 的 `/cc`、`/codex` 前缀命令正是这个模式的存在证明【已确认】。潜在矛盾：无。

**Q4：是否把隐含需求漏了？**
自查后补充 14 项隐含需求（见第三节）。特别自查了：审批流（agent 请求权限时人在 IM 端批/拒）、格式转换（Markdown↔IM 卡片/纯文本）、消息可靠性（重试/去重/断线重连）、凭证安全（集中管理的 API key 加密）、节假日表（"工作日/休息日"定时语义在中国必须含法定节假日+调休）、微信 CDN 媒体上传（图片要先传 CDN 才能发，WeClaw 已实现 AES-128-ECB 上传逻辑【已确认】）。

**Q5：会不会把表面现象（扫码麻烦）误判为根本原因（缺中间层）？**
反向论证：若只是扫码麻烦，做"凭证持久化 + 免重复扫码"即可解决（WechatClawbot 已实现绑定持久化）。但用户明确要求三种模式 + 总控模式 + 定时 + 知识库——说明用户要的是**路由与编排中枢**，扫码只是诱因。幸存结论：中间层定位正确。

## 第三轮：双向钢人论证（对"必须自研 vs 纯拼装"的关键判断）

**支持"纯拼装（不写核心代码）"的最强论证**：
- WeClaw（Go，ACP 客户端）+ LangBot/AstrBot（多通道 IM）+ Hindsight（记忆）+ Paperclip（编排）理论上能拼出全部功能；
- 全部组件都是活跃开源项目，社区维护成本低；
- 用户是开发者，胶水脚本可控。

**反对"纯拼装"的最强论证**：
- 四个组件的**会话模型互不兼容**（WeClaw 的 chat_id、LangBot 的平台会话、Paperclip 的 issue、Hindsight 的 bank），拼接时映射层会变成新的"隐式核心"，且无单一事实源（配置分散在 4 处）；
- LangBot/AstrBot 面向"聊天机器人"而非"agent 网关"，其消息循环假设单一 LLM 应答，流式 ACP update、权限审批、worktree 状态这些 agent 原生事件会丢失或被粗暴折叠；
- 总控模式需要横跨所有输入端的编排权，拼装架构里没有天然宿主；
- 性能与运维：4 个运行时（Go/Python/Python/Node）4 套部署。

**裁决**：反对意见中"会话模型不兼容 + 总控无宿主"两条未被证据排除（各项目 README 均未提供跨系统会话映射抽象）。因此终局结论为**"三段式：先拼装验证 → 再自研收敛"**（报告 10 路线 C），而非二选一。此结论的前提：用户接受 2-4 周的拼装验证期；若用户要求一步到位，可直接进自研（报告 11）。

## 第四轮：重构与终稿

### 3.1 隐含需求清单（用户未明说但执行所必需）

| 编号 | 隐含需求 | 依据 | 优先级 |
|-----|---------|------|-------|
| I1 | 会话映射：IM 会话 ID ↔ ACP sessionId / CLI resume ID | E2/E3 的前提 | Must |
| I2 | 审批转发：ACP `session/request_permission` → IM 按钮 | agent 安全运行的标配 | Must |
| I3 | 格式转换：Markdown/代码块/diff → 各 IM 富文本或纯文本 | 各 IM 格式能力不一 | Must |
| I4 | 流式更新聚合：ACP `session/update` 增量 → IM 消息编辑/分段发送 | 微信不支持无限编辑，需节流合并 | Must |
| I5 | 凭证管理：各 agent 的 API key/订阅凭证集中加密存储 | F8 多输入端必然带来多凭证 | Must |
| I6 | 消息可靠性：去重、幂等、重试、断线重连、离线补推 | IM 长轮询/ webhook 均有抖动 | Must |
| I7 | 每通道限流与背压 | 各平台 API 有频控（飞书/钉钉 QPS 限制） | Must |
| I8 | 节假日表：中国法定节假日 + 调休，支撑"工作日/休息日"定时语义 | E1 明确要求 | Should |
| I9 | 多账号/多设备：同一输出端多人扫码（场景 2 的 A 部门/老板） | 场景示例 2 | Should |
| I10 | 使用量与成本观测：token/消息量按 agent/通道统计 | 高并发多工具必备 | Should |
| I11 | 审计日志：谁在何时让哪个 agent 做了什么 | 治理刚需 | Should |
| I12 | 白名单与安全边界：输出端只信任配置过的用户/群 | 防止任意人指挥 agent | Must |
| I13 | 媒体管道：图片/文件/语音的收发与转存（微信需先上传 CDN） | WeClaw 已验证此必要性 | Should |
| I14 | 探活与自愈：agent 子进程崩溃重启、通道掉线告警 | ACP 子进程模式的固有风险 | Must |

### 3.4 歧义与待确认清单（用户裁决项）

| # | 歧义点 | 影响 | 建议默认解 |
|---|-------|------|-----------|
| Q-1 | "分身数据-loop"的"分身"指：a) 各输入端 agent 的人格画像 b) 用户自己的数字分身 | E4 实现方向差异大 | 按 a) 为主、b) 为辅（Hindsight 知识页机制两者皆可承载） |

| Q-6 | 通知模式的订阅者是"设备上的通道账号"还是"最终用户个人" | 订阅模型 | 订阅目标=输出端绑定（人+端），支持标签分组 |

### 3.5 验收标准草案（供后续开发任务引用）

1. 同时接入 ≥3 个 ACP 输入端（Claude Code、Codex、OpenCode 实测）与 ≥3 个输出端（微信 ClawBot、飞书、Telegram 实测），在三种模式下消息双向可达、会话正确映射。
2. 微信端 `/clear` 可对指定 agent 新开 ACP 会话；历史可按 sessionId 查询回放。
3. 定时任务支持一次/每日/每周/每月/工作日/休息日六种语义，跨节假日正确触发。
4. 中断注入测试：杀 agent 子进程、断网 30s、通道限流——消息不丢（最终送达或明确告警）。
5. 管理后台可热更新路由配置，无需重启核心进程。
6. 性能基线：单机 100 并发会话、消息端到端 P95 < 2s（不含 agent 思考时间）、流式首块转发 < 300ms。
