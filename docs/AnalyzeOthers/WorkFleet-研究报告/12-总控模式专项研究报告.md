# 12 总控模式专项研究报告

> AideanFleet V0.0.2 ｜ 2026-10-17 ｜ 覆盖需求 E6-E9 + 相关隐含需求 ｜ 机制来源：pentagi（编排）+ BettaFish（会议）+ Paperclip（治理）+ Hindsight（记忆/身份）

---

## 1. 概念界定与边界

**用户定义还原**：
- 总控 = "职业经理人"智能体，**必须运行在设备上**（其他模式大概率两端直连）；
- 职责 1（需求侧）：组织各输入端**开会**——各 agent 扮演不同员工分析需求，总控**明确需求、分析得失、统一意见、分配任务**（可单点分配，总控自决）；
- 职责 2（执行侧）：各输入端**每次输出都必须经过总控把关、归纳、回复**；非必要信息总控直接回复；"回复不了的、重大决策的、资源申请的"才上报输出端（用户）；
- 可配置：总控模型自定义 + skill 配置；
- 交互保障：**随时与总控对话，不打断正在执行的任务**（旁路对话）。

**边界澄清**【待确认→建议默认】：
- "运行在设备上" = 用户本机或局域网服务器（ACP stdio 子进程模型天然满足）；
- 总控 ≠ 路由内核：总控是挂在路由内核上的**编排模块**（报告 11 §12 的可选装配）；
- 输出端上报 ≠ 全量转发：总控是唯一对 IM 的发言人（团队+总控模式下），防回复风暴。

## 2. 角色与拓扑

```
 用户(微信/飞书/QQ/...) ──双向── AideanFleet Router
                                   │ (master 模式路由)
                          ┌────────▼────────┐
                          │  总控 Orchestrator │  ← 模型可配置（GLM/Claude/GPT/本地…）
                          │  · 会议主持        │  ← skill 配置（MCP servers + 技能包）
                          │  · 把关/归纳/回复   │
                          │  · 任务分派        │
                          │  · 预算/升级判定    │
                          └────────┬─────────┘
                     会议总线（事件驱动论坛）
                     ┌────────┬────┴─────┬────────┐
                  输入端A   输入端B    输入端C   (N 个 ACP agent = "员工")
```

与 BettaFish ForumEngine 同构：总控=主持人，员工 agent=Query/Media/Insight，论坛=会议总线；差异在于我们的"员工"是任意 coding agent（经 ACP），且总控有明确定义的**升级（escalation）语义**。

## 3. 核心状态机（会议机制）

```
COLLECT ──► SYNTHESIZE ──► ASSIGN ──► EXECUTE ──► REPORT ──► (循环/结束)
 收集意见     总控归纳        分派          执行把关        汇报
```

1. **COLLECT（组织会议）**：新需求 → 总控生成议题 + 指定参会 agent（按 capability 匹配，pentagi 的 enricher 思想：先解析上下文再选人）→ 并行 `session/prompt` 向各 agent 征求分析（限时，如 120s）。
2. **SYNTHESIZE（明确需求/分析得失/统一意见）**：总控汇总各方发言（ForumEngine 的"监控发言→LLM 主持人综合"），产出：需求澄清、方案权衡（得失）、统一结论、分歧备注。**字数预算**控制归纳输出（BettaFish 的 word budget 防跑飞）。
3. **ASSIGN（分派）**：总控把结论转成 N 份 `<task_assignment>` 结构化任务（pentagi 格式：目标+计划+边界+验收点），单点或多点分派自决；每任务原子 checkout + 执行锁（Paperclip 语义，防重复劳动）。
4. **EXECUTE（把关循环）**：员工 agent 的每轮产出 → 总控把关：① 通过→继续/合并；② 偏航→`<task_assignment>` 修订重发；③ **卡死检测**（同方法连续失败 ≥2 次，pentagi 防卡死）→ 换路/升级。
5. **REPORT（统一汇报）**：按通道卡片格式汇报结果；重大决策/资源申请/预算越线 → **升级到输出端用户**（IM 审批按钮，走 approvals 表）。

## 4. 把关与升级判定（职责 2 的实现）

总控对每条 agent 输出执行三段判定（提示词 + 规则混合）：

| 判定 | 规则示例 | 动作 |
|-----|---------|------|
| 直接回复 | 事实询问、进度查询、可自答的小问题 | 总控自答，不打扰用户 |
| 缓报 | 常规进展、非关键告警 | 聚合进周期简报（如每日 21:00，复用 E1 调度） |
| 升级 | 重大决策、花钱/资源申请、越权操作、连续失败、涉及外部发布 | 立即 IM 上报 + 审批流 |

判定规则做成**可配置策略表**（管理台可编辑），而非硬编码——因为"重大"因人而异【设计裁决】。

## 5. 旁路对话（不打断任务）

- 会话隔离：总控维护**两个上下文**——`任务上下文`（会议/分派/把关链）与`旁路上下文`（用户↔总控的即时对话）；旁路 prompt 不进入会议总线，仅注入只读的任务状态摘要；
- 实现：`sessions` 表中旁路会话独立 row，agent_id=总控自身；正在执行的 ACP 会话不受影响；
- 语义对齐 Orca 的"手机上问一句不影响 worktree 任务"（形态验证过）。

## 6. 模型自定义与 Skill 配置（E9）

- **模型自定义**：总控是一个 provider 抽象的 LLM 调用点（OpenAI 兼容网关 / Anthropic / GLM / 本地 Ollama…，参考 Hindsight 的 25+ provider 模式与 pentagi 的多网关）；不同阶段可用不同模型（COLLECT/SYNTHESIZE 用强模型，EXECUTE 把关可用便宜模型——pentagi "planner 对小模型收益最大"的逆向应用）。
- **Skill 配置**：① MCP servers 白名单（复用 AideanFleet 内核 MCP 客户端）；② 技能包=提示词模板+工具集+触发条件（OpenClaw skills 目录形态）；③ 每个总控实例可绑定 persona（immortal-skill 七维模板 + OpenClaw Soul Spec 对齐）。

## 7. 身份数据采集优化——自动更新分身数据 loop（E5）

```
对话/任务流 ─► Hindsight retain(实时) ─► bank 沉淀
                    │
                    ├─► reflect(定时) ─► Observations/Mental Models 固化
                    │
                    └─► 知识页自动重写(后台) ─► identities.seven_dim_json 版本化更新
                                                  │
总控/各 agent 启动/每 N 轮 ◄── 注入最新分身摘要 ──┘
```

- Hindsight 的 knowledge pages 机制**原生就是这个 loop**（报告 07）：从 git 历史+会话自动建 per-repo bank，知识页后台自动重写；
- 分身维度建议（immortal-skill 七维参考）：技术偏好、沟通风格、项目图谱、决策习惯、资源边界、协作历史、当前上下文；
- 版本化：identities.version + 变更 diff 审计（分身"漂移"可回溯）。

## 8. 会议总线设计（高并发重实现 BettaFish 论坛）

- Go channel / Redis Stream 双实现位（单机/多机）；
- 消息类型：`SPEECH`（agent 发言）、`GUIDANCE`（总控指导）、`ASSIGNMENT`、`ESCALATION`、`BUDGET_ALERT`；
- 全量留痕进 meetings/meetings.turns_json + audit_log（可按 meeting ID 回放整场会议）；
- 预算护栏：每会议设 token/费用上限（Paperclip hard-stop 语义），触线自动暂停并升级用户。

## 9. 成本模型与开关

- 已知基准（pentagi 实测）：编排开销 ≈ 2-3× 执行时间与 token，换 2× 质量【已确认】；
- 对策分级：L0 关闭总控（纯路由）；L1 仅把关（无会议，单层过滤，+10-20% token）；L2 会议+分派（复杂任务）；L3 全流程含旁路对话；默认 L1，按任务 `complexity` 启发式自动升档，用户可全局钉死；
- 观测：每会议产出"成本/收益"记录（token 花费 vs 任务完成度），管理台可视化。

## 10. 苏格拉底追问与双向钢人论证

**Q：总控会不会成为单点瓶颈与延迟放大器？**
支持（担忧成立）：所有输出过总控=串行化+LLM 延迟。
反制：① 把关模型可用小而快的模型（GLM-4.5-Air 级）；② 直接回复类走规则短路（不进 LLM）；③ 总控多实例（按 project_key 分片）；④ L0/L1 降档开关。
裁决：默认 L1 起步，把"全量把关"留给用户显式开启【设计裁决】。

**Q：员工 agent 不听话（不接受任务结构）怎么办？**
ACP agent 的 prompt 是自然语言入口——`<task_assignment>` 只是提示词约定，非协议强制。对策：分派前按 agent 能力裁剪指令模板（WeClaw 的 per-agent env 思路）；对 CLI 模式 agent 用其原生 flags。存在不服从风险 → 总控把关环节兜底【存在缺陷：无法协议级强制，只能语义级约束】。

**Q：会议会不会空转（agent 互相附和、循环不收敛）？**
BettaFish 的多轮循环 + 主持人机制本身有轮次上限；pentagi 的防卡死（换方法提示）+ Paperclip 的 watchdog/恢复动作提供三层保险；再加预算硬停。收敛判定标准（意见一致度/方案完整度）写进 SYNTHESIZE 的输出 schema【设计裁决】。

**Q：总控自己也是 LLM，谁来监督总控？**
① 升级机制（重大事项必须到人）；② 审计全量留痕；③ 预算硬停；④ 管理台可一键降级/暂停总控；⑤ 总控操作白名单（不可直接执行写操作，只能分派给带审批的 agent）。

## 11. 验收标准（M4 专用）

1. 三 agent 并发会议：给定需求 → COLLECT→REPORT 全流程 ≤5 分钟（不含长任务执行）；
2. 旁路对话在 EXECUTE 进行中可即时互答（互不阻塞，延迟 <2s）；
3. 升级判定准确率：人工标注 50 条 agent 输出，升级/缓报/直回复分级准确率 ≥90%；
4. 预算硬停：超限会议自动暂停且用户收到审批请求；
5. 分身 loop：连续使用 7 天后 identities 有 ≥1 次版本更新且 diff 可读、可回滚。

## 12. 结论

总控模式在 2026-10 的生态中**没有现成整装实现，但全部机制都有开源蓝本**：会议（BettaFish ForumEngine）、编排与防卡死（pentagi）、治理与预算（Paperclip）、记忆与身份 loop（Hindsight）、旁路对话形态（Orca）。自研工作量集中在**会议总线 + 升级策略表 + 双上下文隔离**三个原创点，其余为模式移植。建议按 L1→L3 渐进启用，成本护栏先行。
