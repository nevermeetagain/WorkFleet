# 09 生态候选项目横向扫描报告

> AideanFleet V0.0.2 ｜ 2026-10-17 ｜ 除标注外均为实时检索/抓取证据；用于补齐 6 个指定项目未覆盖的生态位

---

## 1. 扫描结论总览

2026 年 10 月的生态呈现清晰的**三层结构**：

| 层 | 生态位 | 代表项目 | 成熟度 |
|----|-------|---------|--------|
| 输入端工作台层 | 管理/驱动多个 coding agent | Orca（94.5k★）、Paperclip（103.2k★）、OpenClaw | 极高 |
| 通道路由层 | 多 IM 平台 ↔ AI 后端 | LangBot、AstrBot、chatgpt-on-wechat、WeClaw、OpenClaw 通道插件 | 中-高 |
| 能力层 | 记忆/编排/网关 | Hindsight（50.5k★）、pentagi（30.8k★）、claude-code-router、Omnara、acp-bridge | 高 |

**用户要的"多对多 ACP 工具"横跨三层：ACP 客户端（输入）+ IM 通道（输出）+ 路由/编排（核心）——没有任何单一项目同时占据，但每一层都有可拼装件。**

## 2. 重点候选项目逐一扫描

### 2.1 OpenClaw（openclaw/openclaw）——最接近"输出端网关"的底座
- 定位："The AI that really does things. Any OS"——自托管个人 AI 助手，跑在自己设备上，通过 Gateway 接入你已有的聊天工具【已确认】。
- **通道矩阵**【已确认 docs.openclaw.ai + 官方插件】：Discord、iMessage、Slack、Teams、Telegram、WhatsApp、Matrix、Signal、QQBot、QQ、企业微信、钉钉、飞书（官方插件 `@openclaw/feishu`：Bot 私信/群聊/**流式卡片回复**/飞书文档/wiki/云盘/多维表格工具）、**微信（官方 ClawBot 插件 `@tencent-weixin/openclaw-weixin`，2026-03 上线，iOS 微信 8.0.70+）**。
- 架构：Node.js Gateway（本地）+ 可视化管理面板 + 插件体系（channels 以 npm 插件形态装载）+ cron + 记忆 + 技能（skills）。
- 附加标准：**OpenClaw Soul Spec**——分身/人格规范（见 2.8 immortal-skill 对齐）。
- 对 AideanFleet：① 微信/飞书/钉钉/QQ 的通道工程可直接借用其插件契约；② 但 OpenClaw 的核心是"单一助理 × 多通道"，**没有多 agent 多对多路由语义**（WeClaw 作者正是因此另起炉灶，其 README 明言 inspired by 官方微信插件）【已确认因果】。

### 2.2 WeClaw（fastclaw-ai/weclaw，1.7k★）——微信侧 ACP 客户端（详见报告 03 对照节）
- Go 单二进制；ACP/CLI/HTTP 三模 agent；多微信账号；主动推送 API；媒体管道（微信 CDN AES 上传）；`/cc /cx /gm /oc` 别名寻址。
- 对 AideanFleet：Phase 1 唯一"开箱即用"的管理模式半成品；也是 Go 语言路线的工程参照。

### 2.3 LangBot（langbot-app/LangBot）——多平台 IM × 多 AI Runner 的"通道层"标杆
- 定位：生产级多平台智能机器人开发平台（原 RockChinQ/LangBot）【已确认】。
- 平台：QQ（NapCat/OneBot）、微信、企业微信、公众号、飞书、钉钉、Discord、Telegram、Slack、LINE【已确认多源】。
- AI Runner：**Dify、Coze、n8n、Langflow** + 直连 LLM 供应商——即"输入端"被抽象为可插拔 runner【已确认】。
- 能力：Agent/知识库编排、插件系统、WebUI。
- 对 AideanFleet：**输出端通道抽象的最佳参考**；其 runner 抽象证明了"1 个 LLM 后端 × N 平台"的可行，缺的是"N 个 ACP agent"这一 runner 类型——给 LangBot 写一个 ACP runner 是低改造路线 B 的核心工作（报告 10）。

### 2.4 AstrBot（AstrBotDevs/AstrBot）——松耦合异步多平台框架
- 定位：松耦合、异步、多消息平台、插件生态、LLM 接入的聊天机器人开发框架【已确认】。
- 平台覆盖与 LangBot 类似（QQ/微信/Telegram/飞书/钉钉/Discord 等）；插件市场 + WebUI。
- 对 AideanFleet：与 LangBot 二选一的备胎；Python 技术栈（若团队 Python 强则优先）。

### 2.5 chatgpt-on-wechat（zhayujie 系）——老牌多通道样例
- 30k+★ 级中文项目；channel 抽象（微信/企微/公众号/飞书/钉钉/Telegram/QQ…）+ 插件体系。
- 对 AideanFleet：channel 抽象接口的历史验证（证明"通道适配器"模式在中文 IM 生态长期有效）【部分确认：未逐项核对 2026 现状，快照级证据】。

### 2.6 Omnara（omnara-ai/omnara）——"从手机管理 agent"的审批/通知形态
- 定位：开源 managed agent 平台——"run AI agents on any model and any machine, with tools, secrets, permissions"；自托管的 Claude Managed Agents / OpenAI 同类替代【已确认】。
- 形态：Dashboard + CLI + REST API + TypeScript SDK；移动端推送与**权限审批**（agent 请求 → 手机批准/拒绝）。
- 对 AideanFleet：审批转发的产品形态参考（ACP `session/request_permission` → IM 按钮的 UX 先例）【已确认形态】。

### 2.7 claude-code-router（musistudio/claude-code-router）——本地 agent 控制平面
- 定位："One local control plane for coding agents"——本地模型网关与统一控制平面【已确认】。
- 覆盖：Claude Code、Claude Design、Codex、Grok CLI、Kimi CLI、Kilo Code、OpenCode、Pi、**ZCode** 等（与用户输入端清单高度重合）。
- 对 AideanFleet：证明"多 agent 统一入口"有独立生态位；其 provider 路由规则（按上下文/任务切模型）可借鉴到"按消息路由 agent"的规则引擎【已确认】。

### 2.8 agenmod/immortal-skill（1.1k★）——数字分身蒸馏（E5 的镜像项目）
- 定位："开源数字永生框架——从聊天记录蒸馏任何人的七维数字分身；微信/飞书/iMessage/Telegram 等 12+ 平台；7 种角色模板；**对齐 OpenClaw Soul Spec 标准**"【已确认快照】。
- 对 AideanFleet：E5"身份数据采集优化（自动更新分身数据-loop）"的成品参考：聊天记录 → 分身画像（七维）→ 角色模板 → 标准化人格描述。可与 Hindsight 组合：immortal-skill 负责人格 schema，Hindsight 负责记忆底座。

### 2.9 allvegetable/acp-bridge——ACP 多 agent 编排器
- 定位："Manages coding agents (Codex, Claude, Gemini, OpenCode) via ACP with parallel tasks, dependency chains, and diagnostics"【已确认快照】。
- 小型项目，但证明"ACP 客户端 + 并行任务 + 依赖链"编排层的可行性与最小形态；可作 AideanFleet 编排内核的代码级参考（注意核对其许可【待确认】）。

### 2.10 Coze / Dify / n8n——商业与低代码编排器（用户输入端之一：Coze）
- Coze 作为输入端：经 OpenAI 兼容 HTTP 接入（WechatClawbot 已示范 COZE_API_URL + COZE_AUTH_TOKEN 解耦模式）【已确认】。
- Dify/n8n 作为编排器：LangBot 已把两者作为 AI Runner 支撑——AideanFleet 的通知模式（定时资讯推送）可直接复用 n8n cron 工作流，或自建轻量调度【设计选项】。

## 4. 苏格拉底追问与钢人论证

**Q：既然 OpenClaw 通道这么全，为什么不直接基于 OpenClaw 二开？**
支持：通道工程量最小（微信/飞书/钉钉/QQ 全有官方或成熟插件）、社区巨大。
反对：① 其内核语义是"一个助理、多通道"，多对多路由需改其消息分发内核（gateway 核心改造，深度二开）；② 插件契约面向"助理技能"而非"agent 会话映射"（sessionId 语义不对齐）；③ Node.js 单线程网关对"高并发多 agent 流式聚合"有上限（可水平扩展但复杂）；④ 深度二开 = 跟随上游节奏的长期税。
裁决：**通道层借用、内核不绑定**。若走"OpenClaw 插件"路线，等于把 AideanFleet 做成 OpenClaw 的一个 channel+agent 混合插件——可行但天花板受限；若自研内核，通道协议照抄其插件契约（npm 插件接口是公开文档）【设计裁决，报告 10/11 展开】。

**Q：LangBot/AstrBot 加一个 ACP runner 是不是比重写更划算？**
支持：10 平台通道 + WebUI + 插件体系白拿。
反对：① Python 异步框架的进程管理模型与"ACP 子进程池 + 长会话"的贴合度需验证；② 其消息管道以"对话轮"为单位，ACP 的"流式通知 + 权限请求"事件模型需在管道内新开事件通路（改动不小）；③ 三种模式的路由语义仍要自写。
裁决：作为**路线 B**保留（适合快速验证、接受 Python 栈的团队）；与自研路线 A 并行评估，最终按 PoC 数据决策【待确认：需 1-2 周 PoC 验证 runner 可行性】。

## 5. 扫描结论

1. **不存在**覆盖"多对多 ACP 路由"全需求的开源项目（研究方法第 2 条的答案是否定的）【已确认】。
2. 生态三层齐备，拼装材料充足：ACP 客户端（WeClaw/acp-bridge）、通道（OpenClaw 插件契约/LangBot）、记忆（Hindsight）、编排（pentagi/BettaFish/Paperclip）、审批形态（Omnara）、分身（immortal-skill）。
3. 自研的核心工作量被生态压缩到：**路由内核 + 会话映射 + 三模式引擎 + 总控**（其余皆可借力）——这直接决定报告 11 的架构与工作量估算。
