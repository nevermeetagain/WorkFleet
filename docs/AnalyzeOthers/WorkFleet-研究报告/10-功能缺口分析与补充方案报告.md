## 3. 三条总体路线（成本/风险/收益对比）

### 路线 A：自研内核 + 生态拼装（推荐）★
- 做法：自研"路由内核 + 三模式引擎 + 总控"（Go 或 Rust），通道层直接实现 OpenClaw 插件契约兼容的适配器 + 移植 WeClaw 微信工程；记忆外挂 Hindsight；调度内置轻量版。
- 成本：内核 ~6-10 周PoC→MVP；通道逐个 ~1-2 周/个。
- 收益：需求 100% 定制度、性能上限高（用户"高性能高拓展"目标）、无 GPL 传染、不被上游绑架。
- 风险：工程量集中；需自担兼容性。
- 详见报告 11。

### 路线 B：LangBot/AstrBot + ACP Runner（快速验证）
- 做法：给 LangBot 写 ACP/CLI Runner 插件 + 模式路由插件 + Hindsight 插件。
- 成本：~2-4 周可得可用系统。
- 收益：10 平台通道白拿；社区维护。
- 风险：Python 框架的进程/流式模型贴合度未验证【待确认 PoC】；深度定制受限；性能天花板。
- 适用：想 2 周内解决"扫码绑定打架"的燃眉之急。

### 路线 C：Paperclip 插件化（重型公司治理路线）
- 做法：以 Paperclip 为底座，写中国 IM 连接器插件 + ACP 适配器。
- 成本：中-高（需深入其 Identity/Issue/心跳体系）。
- 收益：治理/预算/审批/例程全部白拿；MIT。
- 风险：形态是"公司管理台"而非"IM 路由器"；Node 栈；概念错配的长期摩擦。
- 适用：如果用户真实诉求偏向 E6-E9 总控治理而非轻快路由。

**裁决**：A 为主（满足高性能高拓展的明示目标），B 作为并行 PoC（两周内可先跑起来验证需求真伪），C 仅当总控需求膨胀为企业级治理时再启用【设计裁决】。

## 4. 苏格拉底追问与钢人论证

**Q：评分矩阵会不会主观？**
是人工评分（基于 README 级证据，非逐源码验证），存在 ±1 分级误差；但量级差异（如 F8 通道：OpenClaw=5 vs Paperclip=2）远超误差带，矩阵结论（无全cover项目、三足鼎立）对此稳健。若需更强证据，可对前 3 名做源码级验证【待确认：后续任务】。

**Q：路线 A"自研"是否违背用户"先找开源"的意图？**
不违背：用户第 5 条明确"如果没有找到符合要求的开源项目，就考虑自行开发的方案"。且路线 A 不是从零造轮子——通道/记忆/参考实现全部借力开源，自研的只是生态中确实空缺的"路由内核"【已确认空缺】。

**Q：三条路线能否混合？**
可以且建议：Phase 1 用 B 快速止血 → Phase 2 切 A 内核（B 期间沉淀的配置/规则可迁移）→ Phase 3 视总控复杂度决定是否引入 C 的治理模块（或借鉴其设计）。
