## 一、研究任务定义

**用户核心诉求**：一个"多对多 ACP 工具"——把 N 个输入端（CLI/智能体：OpenClaw、Claude Code、Codex CLI、Zcode、Cursor、Coze 等）与 M 个输出端（通信工具：微信 ClawBot、飞书、QQ、钉钉、Discord、Telegram 等）全联通，支持后台配置管理，具备三种路由模式（管理 N:1 / 通知 1:N / 团队 M:N）与可选的"总控模式"（本地职业经理人智能体）。

**痛点根源**：单一微信账号在多个开发工具间反复"扫码绑定→解绑→再绑定"，信息接收被割裂。

## 四、核心结论（TL;DR）

1. **【已确认】没有任何单一开源项目同时满足"多对多 + 三种路由模式 + 总控模式"**。最接近的是 WeClaw（微信↔多 Agent 的 ACP 桥，Go，1.7k★），但它只有微信一个输出端、无定时任务、无知识库、无总控。
2. **【已确认】技术路线已收敛**：ACP（JSON-RPC 2.0 over stdio）已事实上成为 coding agent 客户端协议标准（Zed 发起，Claude Code/Codex/Gemini CLI/Goose/OpenCode 均已支持），"输入端适配"应直接以 ACP 客户端身份实现，而非逐个 CLI 适配。
3. **【已确认】输出端在中国生态已可合规打通**：微信官方 ClawBot 插件（2026-03 上线，基于 iLink API）+ 飞书/钉钉/QQ 官方 Bot API，不再依赖封号风险高的个人号 Hook。
4. **【部分确认】总控模式有可直接借鉴的成熟机制**：BettaFish 的 ForumEngine（LLM 主持人 + agent 论坛多轮辩论）、pentagi 的 Orchestrator/Adviser 两阶段编排、Paperclip 的心跳唤醒 + 预算硬停 + 治理审批、Hindsight 的记忆三操作（retain/recall/reflect）与知识页自动重写（天然就是"分身数据-loop"）。
5. **【建议】推荐路线：三段式**。Phase 1 用 WeClaw + LangBot/AstrBot 快速拼出"管理+通知"两模式验证价值；Phase 2 自研 AideanFleet 核心（推荐 Go，备选 Rust）统一三模式；Phase 3 叠加总控模式（复用 Hindsight 作记忆层）。详见报告 10/11/12。

## 七、全局风险提示（各报告展开）

1. **协议演进风险**：ACP v2 草案已在制定中（Prompt Lifecycle 变更），自研需预留版本协商与适配层【已确认存在 v2Draft】。
2. **合规风险**：微信个人号非官方协议（wechaty puppet 等）有封号风险；本研究所有方案均基于官方 ClawBot/iLink 或企业通道【已确认官方插件存在】。
3. **许可风险**：BettaFish 为 GPL-2.0，直接抄代码会传染许可；只借鉴机制、不抄实现【已确认】。
4. **成本风险**：总控模式多轮会议会放大 token 消耗（pentagi 实测编排开销 2-3 倍执行时间/token，换 2 倍结果质量）【已确认】。
