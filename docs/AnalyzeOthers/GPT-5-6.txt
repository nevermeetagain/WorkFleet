# WorkFleet V0.0.2：开源项目深度研究与架构选型

本次研究的目标不是简单地把几个机器人接在一起，而是为 WorkFleet 找到一条能够承载多 CLI / 智能体并发执行、多消息平台接收、跨项目路由、任务编排、会话恢复与统一总控的可实施技术路线。

研究的首要发现是：现有项目通常分别解决智能体编排、消息平台接入、会话管理或知识库记忆中的某一部分。不能因为某个项目支持多个智能体或多个聊天平台，就直接认定它满足你的多对多通信需求。

另一个关键问题是协议名称。官方的 Agent Client Protocol (ACP) 主要标准化代码编辑器与编码智能体之间的通信，并非专门为微信、飞书、QQ 等消息接收端与多个 CLI 的多对多调度设计。

## 研究得出的关键结论

第一优先级验证 CountBot

功能覆盖面与需求相近，但官方 README 明确表示作者近期不会主动维护。适合先验证、考虑自行接管维护，不建议未经完整验收便直接投入生产。

GitHub



消息层、总控层与 CLI 层分开设计

LangBot 的统一消息事件和平台适配架构、Paperclip 的 Adapter 与任务控制面、OpenClaw 的路由和会话模型，分别能提供不同层面的参考。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub

+2



不要让 ACP 承担全部产品职责

ACP 可以作为编码智能体的会话与执行通信接口，但多对多路由、项目隔离、消息扇出、外部平台投递等仍然需要 WorkFleet 自己定义的业务契约。

## 研究范围与验证限制

压缩包已通过完整性检查。需要明确的是：本次完成的是基于官方仓库、架构文档、协议文档及部分可访问源代码的研究，不是对所有项目的最新完整源码进行本地构建和运行验收。

由于未能成功拉取完整仓库，本轮没有完成全部项目的固定 commit 源码审计、自动化测试、真实微信/飞书端到端验证，也没有核实 WorkFleet V0.0.2 自身的代码实现。报告已把这些内容列为待核实项，没有把项目说明直接认定为实现证据。

建议下一阶段首先冻结候选仓库的 commit，核验 CountBot 的 M×N 路由、消息回流、session 恢复、总控对话与任务隔离、持久化投递及 Windows 部署。这些关键项通过后，再决定以它为基础改造，还是采用模块化自研 Fleet Core。
