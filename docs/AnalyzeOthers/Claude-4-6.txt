# 00 — 深度需求分析（三轮推理）

## 第一轮：5W1H 发散分析

### What — 客观事实与现象

**用户的核心痛点**，精确描述如下：

| 痛点编号 | 现象 | 影响 |
|---|---|---|
| P-01 | 5+个开发工具同时运行，但只有1个微信账号 | 无法同时绑定多个Bot（WeChat ClawBot 1:1约束） |
| P-02 | 频繁扫码绑定/解绑 | 信息遗漏、工作流中断 |
| P-03 | 缺少统一的多输入→多输出路由层 | 没有多对多的ACP调度平台 |
| P-04 | 无法按产品线/项目分流消息到不同输出端 | 微信/QQ/飞书无法智能分离消息流 |
| P-05 | 缺少总控"职业经理人"智能体 | 所有输入端消息未经过滤直达用户，噪音大 |

**已确认的关键技术约束**：
`WeChat ClawBot` 的硬约束：每个微信账号只能创建一个Bot，且该Bot与创建者的微信账号一一绑定（1:1），多人无法共用同一个Bot。

**已确认的ACP协议性质**：
ACP是一个用于编辑器/IDE与编码智能体之间通讯的开放协议，而非通用的公司编排协议。它基于JSON-RPC、面向Session、具备能力协商机制，在实践中提供连接/初始化、会话新建与加载、提示轮次、流式更新事件、结构化工具调用事件等能力，目前主要采用stdio传输，Streamable HTTP仍在草稿阶段。

---

### Why — 深层原因与动机

**直接原因**：ACP生态（ClaudeCode、Codex CLI等）天然是1:1单向连接设计，没有内置的多路由、多输出端管理层。

**根本原因**：ACP协议定位是"运行时/会话协议"而非"控制平面协议"。应将ACP视为执行运行时协议，而不是控制平面协议——让各工具在内部使用ACP，上层平台保持解耦，通过网关层与各工具通讯。

**动机**：用户需要在ACP层之上，构建一个**路由控制平面（Routing Control Plane）**，实现：
- 多输入（N个CLI工具）→ 路由层 → 多输出（M个通讯平台）
- 路由层本身还需具备智能调度（总控模式）能力

---

### Where / When — 边界条件

| 边界 | 说明 |
|---|---|
| **输入端约束** | ACP协议（stdio JSON-RPC）、HTTP API、CLI spawn三种通讯模式 |
| **输出端约束** | 微信iLink API、飞书OpenAPI、QQ机器人API、钉钉API、Discord/Telegram Bot API |
| **WeChat 1:1约束** | 必须通过网关层管理多个Bot账号，每个Bot对应一个微信账号 |
| **部署约束** | 总控模式必须运行在本地设备（用户设备）；其他模式可两端直连或云端 |
| **端口约束** | Aidean默认3000端口；AideanBot默认3333端口（待确认，标记为⚠️待确认） |
| **时序约束** | 定时任务最小粒度：分钟级；支持工作日/休息日判断 |

### How — 执行手段与路径

核心实现路径分为三层：

**Layer 1：协议适配层**（对接各输入端ACP/CLI/HTTP）
**Layer 2：路由控制平面**（管理模式/通知模式/团队模式/总控模式）
**Layer 3：输出端适配层**（对接各通讯平台API）

### What If — 变化情景分析

| 前提变化 | 影响 | 应对方案 |
|---|---|---|
| WeChat iLink API变更 | 微信输出端失效 | 适配层隔离，单独更新Adapter |
| ACP协议升级（HTTP Transport正式发布） | stdio传输可被HTTP替换 | 传输层抽象，支持多Transport |
| 用户新增第4个产品线 | 路由规则需扩展 | 路由规则数据库化，支持热更新 |
| 总控模型响应超时 | 任务积压，用户无响应 | 总控模式设超时熔断，降级直通 |
| 微信Bot扫码失效（二维码过期） | 输出端断连 | 自动重登录循环（Loop机制） |
| 某输入端进程崩溃 | 该通道消息丢失 | 进程守护+消息队列持久化 |

## 第二轮：苏格拉底式追问

### 核心结论1：必须构建路由控制平面

**追问**：是否真的没有现成开源项目能满足"多对多路由"需求？

**证据核实**：

- nightsailer/wechat-clawbot 是"支持多用户、多端点网关的AI后端SDK"，但其设计是多Bot路由到多AI后端，**方向相反**（多输入→1输出），不支持1输入→多输出。
- wechat-acp 是将微信消息桥接到任意ACP兼容智能体的桥接工具，它登录iLink Bot API，轮询消息，转发给ACP智能体，再将回复发送回微信。是纯1:1桥接，**无路由能力**。
- Orca运行一个编码智能体舰队并行工作，Hindsight给智能体提供随时间改进的记忆能力。两者均不涉及多输出端通讯路由。

**结论**：**已确认** — 现有开源项目均不具备完整的多对多路由控制平面能力，需要自研或深度整合。

---

### 核心结论2：总控模式与现有多Agent框架的关系

**追问**：Paperclip 和 Pentagi 的多Agent编排能否直接复用为"总控模式"？

**Paperclip的org-chart模型分析**：
Paperclip的Agent数据模型包含：id, company_id, name, role, reports_to（组织树边），capabilities，adapter_type（claude_local/codex_local/http），adapter_config，runtime_config，context_mode（thin/fat），budget等字段。这是一个完整的"职业经理人"层级结构原型！

当心跳触发时，Paperclip的适配器作为编排层与智能体运行时之间的桥梁，每个适配器知道如何调用特定类型的AI智能体并捕获其结果。

**Pentagi的编排模型分析**：
PentAGI围绕任务层级和专业化团队组织工作。一个编排器智能体位于工作流顶层，接收用户的自然语言目标，维护整体状态，并向下委派工作；研究员智能体收集情报，开发者智能体制定策略，执行器智能体在沙盒中执行命令并向上汇报结果。

**双向钢人论证**：

| 维度 | Paperclip 复用 | Pentagi 复用 |
|---|---|---|
| **支持论** | org-chart天然映射"总控→各输入端"层级；适配器架构可扩展到通讯平台输出端 | 多层Agent编排成熟；专业化角色分工清晰 |
| **反对论** | Paperclip是任务管理平台，不是通讯路由平台；无输出端（微信/飞书）适配器 | PentAGI专为安全测试设计，领域耦合深；无通讯平台集成 |
| **结论** | **部分复用** — 可借鉴其heartbeat协议和adapter架构 | **部分复用** — 可借鉴其多层Agent编排和内存系统 |

---

## 第三轮：双向钢人论证 — 自研 vs 深度整合

### 支持自研的最强论证

1. 没有任何现有项目同时覆盖：多输入ACP适配 + 多对多路由 + 多输出端适配 + 总控编排 + 定时任务
2. 现有项目（Paperclip/Pentagi）架构复杂，引入后的技术债超过自研成本
3. 用户需要统一的后台配置管理界面，现有项目均无此设计

### 支持深度整合的最强论证

1. ACP协议对接层（wechat-acp/weclaw）已经相当成熟，直接复用可节省大量时间
2. Hindsight的记忆系统可直接解决"知识库存储"需求
3. Orca的并行Agent管理经验可指导总控模式设计

### 最终判断：**混合策略**

```
自研：路由控制平面（核心） + 配置管理后台 + 总控模式调度器
复用：
  - wechat-acp/weclaw → 微信iLink协议对接（输出端适配）
  - Paperclip Adapter架构 → 输入端ACP适配器设计模式
  - Pentagi流程编排 → 总控Agent编排参考
  - Hindsight → 知识库/长期记忆模块
  - BettaFish → Agent"论坛"协作机制（总控模式参考）
```

# 01 — ACP协议底层技术解析

## 1.1 协议定位

ACP最准确的理解是：一个用于交互式编码智能体的运行时/会话协议，通常客户端具备文件系统/终端/编辑器能力。它不内置任务管理、组织结构、审批、预算、公司范围审计日志等能力。

## 1.2 三种通讯模式对比

ACP支持三种通讯模式：**ACP模式**（长驻子进程，JSON-RPC over stdio，最快，复用进程和Session）、**CLI模式**（每条消息spawn新进程，支持通过--resume恢复Session）、**HTTP模式**（OpenAI兼容的Chat Completions API）。自动检测时优先选择ACP模式。

## 1.3 Session管理机制

消息队列管理是关键：同一Session的消息必须排队，每条消息获得独立回复，否则在上一条回复到达前发送新消息会导致中断或"空响应"错误。

## 1.4 /clear 新对话命令机制

对于Claude，推荐使用ACP模式：`npm i -g @agentclientprotocol/claude-agent-acp`，并查阅ACP Session选项文档。

新对话命令（如`/clear`）在不同Agent中的实现：

| Agent | 新对话命令 | 协议层操作 |
|---|---|---|
| ClaudeCode (ACP) | `/new` 或 `/clear` | `session/new` JSON-RPC call |
| Codex (ACP) | `/new` | `session/new`（早期版本有bug，已修复） |
| ClaudeCode (CLI) | 终止进程+新spawn | `--resume <session-id>` 可恢复 |

## 02-B：Paperclip

> 项目：paperclipai/paperclip

### 技术架构深度穿透

Paperclip在智能体运行时上刻意保持无偏见，通过适配器连接智能体——这些适配器是可插拔模块，桥接Paperclip编排层与智能体实际运行的执行环境。

**Heartbeat协议**（核心调度机制）：

每个智能体在每次唤醒时都遵循相同的心跳流程，这是智能体与Paperclip之间的核心契约。

适配器接口定义为：`interface AgentAdapter { invoke(agent, context): Promise<InvokeResult>; status(run): Promise<RunStatus>; cancel(run): Promise<void>; }`，支持thin（仅传ID）和fat（含完整上下文）两种上下文交付模式。

**最新特性**（v2026.1012.0）：

AgentMail成为默认连接，Neon加入目录支持OAuth或API-key登录，AI账号获得"检查用量"动作。

连接可携带可编辑的使用说明，并在每次授权的智能体轮次中送达。

## 02-C：Pentagi

> 项目：vxcontrol/pentagi（MIT License）

### 技术架构深度穿透

Pentagi是一个monorepo：backend（Go REST + GraphQL API服务器）+ frontend（React + TypeScript Web UI）+ observability（可选监控栈）。

核心Agent角色：Primary Agent（协调所有其他Agent的主编排器）、Generator Agent（将任务分解为有序Subtask列表，最多15个）、Refiner Agent（每个Subtask完成后审查并更新计划）、Reporter Agent（生成最终报告）、Coder Agent（为特定需求编写代码）。

**13种专业化System Prompt**：

PentAGI实现了13种Agent类型的System Prompt：Primary Agent（团队编排+委派）、Assistant（交互模式）、专业化智能体（Pentester/Coder/Installer/Searcher/Memorist/Adviser）、元智能体（Generator/Refiner/Reporter/Enricher/Reflector/Summarizer）。

**知识图谱集成**：

PentAGI集成了Graphiti（由Neo4j驱动的时序知识图谱系统），提供高级语义理解和关系追踪能力。

**技术栈**：

核心服务：React+TypeScript前端、Go+GraphQL后端、PostgreSQL+pgvector向量存储、异步任务队列、多Agent系统；知识图谱：Graphiti API + Neo4j图数据库；监控：Grafana + VictoriaMetrics + Jaeger。

## 4.2 核心数据模型

### 输入端（Input Endpoint）

```sql
CREATE TABLE input_endpoints (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name        TEXT NOT NULL,
    type        TEXT NOT NULL,  -- acp_stdio | acp_http | cli | http_openai
    agent_name  TEXT NOT NULL,  -- claude | codex | cursor | coze | custom
    command     TEXT,           -- 启动命令（ACP/CLI模式）
    endpoint    TEXT,           -- HTTP模式端点
    api_key     TEXT,           -- 加密存储
    env_vars    JSONB DEFAULT '{}'::jsonb,
    cwd         TEXT,           -- 工作目录
    project_id  UUID REFERENCES projects(id),
    status      TEXT DEFAULT 'idle', -- idle | running | error | paused
    created_at  TIMESTAMPTZ DEFAULT NOW(),
    updated_at  TIMESTAMPTZ DEFAULT NOW()
);
```

### 输出端（Output Endpoint）

```sql
CREATE TABLE output_endpoints (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name            TEXT NOT NULL,
    platform        TEXT NOT NULL,  -- wechat | feishu | qq | dingtalk | discord | telegram
    credentials     JSONB NOT NULL, -- 加密存储（token/bot_token/app_id等）
    bot_qr_data     TEXT,           -- 微信QR登录凭证
    status          TEXT DEFAULT 'disconnected',
    last_heartbeat  TIMESTAMPTZ,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);
```

### 路由规则（Routing Rule）

```sql
CREATE TABLE routing_rules (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name            TEXT NOT NULL,
    mode            TEXT NOT NULL,  -- management | notification | team | master_control
    -- 管理模式：多输入→1输出
    -- 通知模式：1输入→多输出
    -- 团队模式：多输入↔多输出
    -- 总控模式：团队模式+职业经理人Agent
    input_ids       UUID[],         -- 输入端ID列表
    output_ids      UUID[],         -- 输出端ID列表
    project_id      UUID REFERENCES projects(id),
    filter_rules    JSONB DEFAULT '{}'::jsonb,  -- 消息过滤规则
    priority        INT DEFAULT 0,
    enabled         BOOLEAN DEFAULT TRUE,
    master_config   JSONB,          -- 总控模式配置（模型/skill/prompt）
    created_at      TIMESTAMPTZ DEFAULT NOW()
);
```

### Session管理

```sql
CREATE TABLE sessions (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    session_key     TEXT UNIQUE NOT NULL,   -- ACP session_id 或 CLI resume_id
    input_id        UUID REFERENCES input_endpoints(id),
    output_id       UUID REFERENCES output_endpoints(id),
    routing_rule_id UUID REFERENCES routing_rules(id),
    status          TEXT DEFAULT 'active',  -- active | completed | error
    message_count   INT DEFAULT 0,
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    last_active     TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE messages (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    session_id      UUID REFERENCES sessions(id),
    direction       TEXT NOT NULL,   -- input→router | router→output | output→router | router→input
    content         TEXT NOT NULL,
    content_type    TEXT DEFAULT 'text',  -- text | image | file | audio | video
    metadata        JSONB DEFAULT '{}'::jsonb,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);
```

### 定时任务

```sql
CREATE TABLE scheduled_tasks (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name            TEXT NOT NULL,
    cron_expr       TEXT,               -- cron表达式（工作日/休息日扩展语法）
    schedule_type   TEXT NOT NULL,      -- once | daily | weekly | monthly | workday | weekend
    next_run        TIMESTAMPTZ,
    last_run        TIMESTAMPTZ,
    action_type     TEXT NOT NULL,      -- send_message | trigger_agent | new_session
    action_config   JSONB NOT NULL,
    routing_rule_id UUID REFERENCES routing_rules(id),
    enabled         BOOLEAN DEFAULT TRUE,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);
```

## 4.3 技术栈选型

| 层级 | 技术选型 | 理由 |
|---|---|---|
| **核心后端** | Go 1.23+ | 高并发goroutine；参考weclaw/Pentagi验证；ACP stdio管理天然适合 |
| **API层** | GraphQL (gqlgen) + REST | 实时订阅（WebSocket）+ 管理操作 |
| **消息队列** | Redis Streams | 消息持久化、路由队列、Session缓存 |
| **主数据库** | PostgreSQL 16 + pgvector | 路由规则、Session、消息历史、向量知识库 |
| **知识图谱** | Neo4j + Graphiti (可选) | 高阶知识关系追踪（参考Pentagi） |
| **知识库** | Hindsight（集成） | 长期记忆，会学习的记忆系统 |
| **定时任务** | robfig/cron v3 | Go原生cron，支持扩展语法 |
| **前端** | React 18 + TypeScript + Tailwind | 参考Paperclip/Pentagi UI设计 |
| **部署** | Docker Compose | MIT自托管，一键启动 |
| **进程管理** | Go os/exec + supervisord思路 | ACP Agent进程生命周期管理 |

# 05 — 四种模式详细设计

## 5.1 管理模式（Management Mode）

```
输入端(N) ──┐
输入端(N) ──┼──▶ [路由层] ──▶ 单一输出端(1)
输入端(N) ──┘
```

**核心特性**：
- 所有输入端的消息聚合到同一输出端
- 输出端可向特定输入端发送消息（通过`@input_name`或路由命令）
- 适合：ClawBot统一接收多个开发工具的消息
- 消息标注来源：`[ClaudeCode] 任务完成：PR #123已创建`

**执行流程**：
```
InputAdapter(N) → MessageBus → AggregationRouter → OutputAdapter(1)
                               ↑
                       消息标注来源端名称
                       支持反向路由：output→指定input
```

## 5.2 通知模式（Notification Mode）

```
单一输入端(1) ──▶ [路由层] ──┬──▶ 输出端A
                             ├──▶ 输出端B
                             └──▶ 输出端N
```

**核心特性**：
- 1个输入端群发到多个输出端
- 每个输出端可有独立的消息格式化模板
- 支持接收不同用户的回复（汇聚到同一输入端）
- 适合：AI日报定时9点推送到所有订阅用户

**定时推送集成**：
```
Scheduler(9:00 daily) → TriggerInputAdapter → BroadcastRouter → OutputAdapter(M)
```

## 5.3 团队模式（Team Mode）

```
输入端A ──┬──▶ [路由层] ──┬──▶ 输出端X（产品线1）
输入端B ──┤             ├──▶ 输出端Y（产品线2）
输入端C ──┤             └──▶ 输出端Z（管理端）
输入端D ──┘
```

**核心特性**：
- 多输入端 ↔ 多输出端，基于路由规则矩阵
- 路由规则支持：按输入端标签、消息类型、项目ID、关键词
- 场景示例：
  - 开发工具消息 → 微信（产品线A）
  - 运营工具消息 → QQ（产品线B）
  - 审批/管理消息 → 飞书

**路由规则矩阵**：

```json
{
  "mode": "team",
  "routing_matrix": [
    {
      "input_tags": ["dev", "monitor"],
      "output_ids": ["wechat-bot-1"],
      "project": "product-line-A"
    },
    {
      "input_tags": ["ops", "analytics"],
      "output_ids": ["qq-bot-1"],
      "project": "product-line-B"
    },
    {
      "input_tags": ["management", "approval"],
      "output_ids": ["feishu-bot-1"]
    }
  ]
}
```

## 5.4 总控模式（Master Control Mode）

> **最复杂也是最核心的差异化功能**

```
┌─────────────────────────────────────────────────┐
│              总控模式（Master Control）            │
│                                                  │
│  ┌──────────────────────────────────────────┐   │
│  │         职业经理人 (Chief Manager Agent)   │   │
│  │                                          │   │
│  │  ·自定义LLM模型                           │   │
│  │  ·可配置Skills（分析/决策/分发/汇报）      │   │
│  │  ·随时接受用户直接对话                     │   │
│  │  ·不中断正在执行的任务                     │   │
│  └────────────┬─────────────────────────────┘   │
│               │  委派/汇报                        │
│    ┌──────────▼──────────────────────────────┐  │
│    │         输入端团队（员工）                 │  │
│    │  ClaudeCode  Codex  Cursor  OpenClaw    │  │
│    │  （开发）  （分析）（推广） （运营）        │  │
│    └────────────────────────┬────────────────┘  │
│                             │  结果/汇报         │
│    ┌────────────────────────▼────────────────┐  │
│    │         输出端（汇报接收）                 │  │
│    │  微信（日常） | 飞书（管理） | QQ（备用）  │  │
│    └─────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

### 总控模式两种子模式：

**子模式A：会议模式（需求分析）**
```
用户提出需求 → 总控Agent组织会议 → 各输入端扮演员工分析
→ 总控明确需求、分析得失、统一意见 → 分配任务给指定输入端
→ 输入端执行 → 结果回报总控 → 总控汇总后向输出端报告
```

**子模式B：把关模式（日常运行）**
```
各输入端消息到达 → 总控Agent接收 → 判断：
  ├── 可直接回复 → 总控直接回复，不推送给输出端
  ├── 需用户决策/重大事项 → 推送给输出端
  └── 资源申请/审批 → 发送带审批卡片的消息到输出端
```

### 总控Agent配置

```json
{
  "master_config": {
    "model": "claude-3-5-sonnet-20241022",  // 可自定义
    "provider": "anthropic",
    "system_prompt": "你是一名经验丰富的职业经理人...",
    "skills": [
      "task_decomposition",    // 任务拆解
      "consensus_building",    // 共识建立
      "priority_assessment",   // 优先级评估
      "escalation_decision",   // 升级决策
      "report_generation"      // 汇报生成
    ],
    "escalation_rules": {
      "keywords": ["严重", "紧急", "资源申请", "需要确认"],
      "auto_reply_threshold": 0.8,  // 置信度阈值
      "max_auto_handle_complexity": "medium"
    },
    "concurrent_sessions": true,  // 允许任务执行时随时对话
    "timeout_fallback": "direct_passthrough"  // 超时降级直通
  }
}
```
