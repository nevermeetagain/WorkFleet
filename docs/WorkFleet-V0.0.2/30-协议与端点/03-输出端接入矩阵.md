## 0. 一页结论

| 渠道 | 收消息机制 | 是否需公网 | 发送主限额（官方） | 主动推送（无用户先发言） | 富消息 | 一对多广播可行性 | 多账号/多 Bot |
|---|---|---|---|---|---|---|---|
| **微信 ClawBot（iLink）** | HTTP **长轮询** `getupdates`（~35s） | 否 | 未公开；社区实测 + 官方 issue：**context_token 24h 失效、每次入站后约 10 条主动消息额度** | ❌ 基本不可（必须有 24h 内入站带来的 `context_token`） | 文本/图片/语音/文件/视频（插件 2.4.x）；链接不可点击 | ❌ **不可**（Bot 1:1 绑定到扫码者本人） | 每个微信号 1 个 Bot；一个网关可托管多个微信号的 Bot |
| **飞书/Lark** | **长连接 WebSocket**（仅企业自建应用）或 Webhook | 长连接否 | 同一用户/同一群 **5 QPS**；接口 1000 次/分 & 50 次/秒；批量发送 **50 万条/应用/天** | ✅（用户在应用可用范围内） | 文本/富文本/卡片 2.0/文件/图片；**卡片流式更新**；卡片回调；审批 API | ✅ 租户内可行（批量发送接口） | 每个应用一个 Bot，可建多个应用；长连接每应用最多 50 连接 |
| **QQ 官方机器人** | WebSocket 或 Webhook（控制台切换） | WebSocket 否 | 单聊主动：Bot 10/qps（认证）、单关系 20/qpm、**1000 条/用户/天**；群：60/qpm、1000 条/群/天 | ⚠️ 有，但用户可关闭；早期文档写"每月 4 条"——**文档冲突** | 文本/Markdown（需权限）/富媒体/Ark；流式单聊消息 | ⚠️ 受用户开关与配额约束，不适合营销式群发 | 每个机器人一个 AppID；可多个 |
| **钉钉** | **Stream 模式**（WebSocket）或 HTTP | Stream 否 | 批量单聊每次 ≤20 人；自定义群机器人 20 条/分（超限限流 10 分钟）；工作通知 500 次/用户/天（企业内部应用） | ✅（企业内部） | 文本/Markdown/ActionCard/互动卡片/**AI 卡片流式更新** | ✅ 企业内可行 | 每应用一个机器人；可多个 |
| **Discord** | **Gateway WebSocket**（或 HTTP Interactions 端点） | Gateway 否 | 全局 **50 请求/秒**；Gateway 发送 120 事件/60 秒；IDENTIFY 1000 次/24h | ✅ 频道消息；DM 条件 `证据不足` | 文本 ≤2000 字符、Embed ≤10、组件/按钮、Slash 命令 | ✅ 频道广播；大规模 DM 不建议 | 多个 Bot 应用；单 Bot 需分片 |
| **Telegram** | `getUpdates` 长轮询 **或** `setWebhook`（二选一） | 长轮询否 | 单聊 ~1 条/秒；群 20 条/分；广播 ~30 条/秒；付费广播至 1000 条/秒（0.1 Stars/条） | ❌ 用户须先 `/start`（社区观测） | 文本/Markdown/HTML/文件/Inline Keyboard | ✅ **最适合**大规模订阅推送 | 多个 Bot token（BotFather） |

**三条硬约束（直接决定产品形态）**：
1. **微信 ClawBot 不能做"通知模式/群发"**：Bot 与扫码者 1:1 绑定，且主动发送依赖 24h 内的入站 `context_token`。它只适合"管理模式：我一个人收所有工具的消息"。`部分确认`
2. **"每天 9:00 推送给大量用户"只能落在 Telegram / 飞书（租户内）/ 钉钉（企业内）/ Discord 频道**；QQ 受用户开关与配额限制；微信 ClawBot 不可行。`已确认`（各平台限额）
3. **长连接/长轮询类渠道（飞书长连接、钉钉 Stream、QQ WS、Discord Gateway、Telegram getUpdates、微信 getupdates）全部无需公网 IP**——这意味着 WorkFleet 可以**完全运行在用户设备上**，与需求中"总控必须运行在设备上"一致。`已确认`

## 1. 微信 ClawBot（腾讯 iLink Bot API）

### 1.1 它是什么
- 2026-03 腾讯在微信（iOS 8.0.70+ 起灰度）上线 "ClawBot 插件"，官方渠道插件 `@tencent-weixin/openclaw-weixin`（https://github.com/Tencent/openclaw-weixin ，npm 2.4.10）把 OpenClaw Gateway 接入微信；底层协议 iLink，域名 `https://ilinkai.weixin.qq.com`，媒体 CDN `novac2c.cdn.weixin.qq.com/c2c`。`已确认`（官方仓库 `docs/protocol.md`，本地克隆 `/workspace/work/refs/openclaw-weixin` commit `874637a`，2026-10-13）
- 微信开放文档另有 "clawbot 相关接口"（https://developers.weixin.qq.com/doc/aispeech/knowledge/openapi/Clawbotrelated.html ）：`POST /api/v1/wechat/qrcode`、`/qrcode/status`，确认后返回 `bot_token`、`ilink_bot_id`、`ilink_user_id`、`baseurl`。`已确认`
- 协议本身是通用 HTTP/JSON，不绑定 OpenClaw——用户提供的参考项目 `CodingHeader/WechatClawbot`（Python/FastAPI）即直接对接 iLink。`已确认`

### 1.2 接口（官方 `docs/protocol.md` + 参考实现 `src/wechat_clawbot/wechat/*.py`）
| 接口 | 作用 | 要点 |
|---|---|---|
| `GET ilink/bot/get_bot_qrcode?bot_type=3` | 取登录二维码 | `bot_type` 含义未文档化 |
| `GET ilink/bot/get_qrcode_status?qrcode=` | 轮询扫码状态 | wait/scaned/confirmed/expired |
| `POST ilink/bot/getupdates` | **长轮询收消息** | 请求带 `get_updates_buf` 游标；客户端超时返回空即正常；`ret/errcode = -14` → 账号会话暂停 1 小时 |
| `POST ilink/bot/sendmessage` | 发消息 | `msg.to_user_id`、`msg.context_token`（**回传入站带来的 token**）、`item_list[{type:1,text_item}]`；非 0 `ret` 视为失败 |
| `POST ilink/bot/sendtyping` / `getconfig` | 输入中状态 / 取 `typing_ticket` | |
| `POST ilink/bot/getuploadurl` + CDN | 媒体上传 | AES-128 + filekey |
| `notifyStart` / `notifyStop` | 生命周期 | |

请求头：`AuthorizationType: ilink_bot_token`、`Authorization: Bearer <bot_token>`、`X-WECHAT-UIN: base64(随机uint32)`（每次新生成）。`已确认`

### 1.3 限制（本产品痛点的根源）
| 限制 | 证据 | 标签 |
|---|---|---|
| **每个微信号只能创建一个 Bot，且 Bot 与创建者 1:1 绑定，不能多人共享** | 社区网关 nightsailer/wechat-clawbot README；Chihao Li 协议分析 "Each ClawBot binds to one WeChat user, connecting only one agent instance" | 部分确认（官方文档未明文，但多方一致） |
| **context_token 24 小时失效**，用户 24h 无交互则 Bot 无法主动触达 | Tencent/openclaw-weixin issue #202（维护者回复"已催促产品重新评估"）；OpeniLink 文档 | 部分确认 |
| **每次有效会话内主动消息约 10 条上限** | 同上 issue #202；社区项目 clawock 提交"数腾讯「每条入站约 10 条」的推送额度" | 部分确认 |
| 缺失/过期 token 发送失败（`ret=-2`），可能静默丢失 | cc-connect issue #1176；官方 protocol.md 称缺 token 时客户端仅告警仍发送 | 部分确认 |
| OpenClaw 官方渠道文档：插件**只声明私聊**，不声明群聊；协议消息体有 `group_id` 字段 | https://docs.openclaw.ai/channels/wechat ；protocol.md 消息模型 | 已确认 |
| 无历史消息查询 API；速率限制未公开；腾讯可单方面限制频率/终止服务 | nightsailer `docs/ilink-protocol.md`（转述服务条款） | 部分确认 |
| 消息中链接不可点击 | 同上 | 部分确认 |

**对需求的直接回答**："只有一个常用微信，绑完这个绑那个"——根因正是 **1 微信号 ↔ 1 Bot ↔ 1 个后端实例**。解法：**只让 WorkFleet 网关持有这唯一的 ClawBot 绑定**，再由网关把消息路由到多个 Agent。这是本产品在微信侧唯一合理的形态。`部分确认`（依赖 1:1 约束成立）

**设计应对**：
- "保活"：网关每次收到入站即刷新 token；临近 24h 或额度剩 ≤3 条时，在最后一条可送达消息中提示"回复任意字以续期"（clawock 已采用同思路）。
- 额度预算器：按 (bot, user) 维护 `remaining_proactive` 计数，超出则**降级到其它渠道**（如飞书/Telegram）或合并为一条摘要。
- 绝不跨账号复用 `context_token`（社区插件文档明确禁止）。

## 7. 广播（一对多）与合规专题 —— 场景 4 "每天 9:00 推送 AI 资讯给大量订阅用户"

| 渠道 | 可行性 | 吞吐估算（按官方限额） | 合规/产品前提 |
|---|---|---|---|
| Telegram | ✅ 首选 | 免费 ~30 条/秒 ≈ 10 万用户约 56 分钟；付费 1000 条/秒 ≈ 100 秒 | 用户主动 `/start` 订阅；提供 `/stop` 退订 |
| 飞书 | ✅ 仅租户内 | 批量接口 50 万条/天/应用 | 接收者须在应用可用范围（企业内部员工/授权用户） |
| 钉钉 | ✅ 仅企业内 | batchSend 每次 20 人，配合 QPS 与 `flowControlledStaffIdList` 重试 | 企业内部应用；工作通知 500 次/用户/天 |
| Discord | ✅ 频道广播 | 一条频道消息即达全体成员 | 用户加入服务器 |
| QQ | ⚠️ 有限 | 每用户 1000 条/天（新版）但用户可关闭 | 公域机器人需审核；避免营销 |
| 微信 ClawBot | ❌ 不可行 | Bot 1:1 绑定 + 24h token + ~10 条额度 | 条款保留频率控制；参考项目自述"不做群发营销" |

合规要点：
- 只向**主动订阅**的用户推送，保存订阅时间与来源，提供一键退订（各平台政策普遍要求避免骚扰；具体法律条款 `证据不足`，需法务确认，尤其涉及中国大陆用户个人信息时）。
- 9:00 是"用户当地时间"还是固定时区？订阅表必须存时区（默认 Asia/Shanghai），调度器按时区分桶。
- 大批量推送必须**令牌桶 + 分批 + 429 退避 + 失败重试队列**，并避免 9:00 整点尖峰（可在 8:55–9:05 平滑，或按用户分桶错峰）。

## 9. 5W1H

- **What**：六个渠道的收发机制、限额、富消息与广播能力差异极大；微信是限制最严的一个，偏偏是用户最常用的。
- **Why**：用户的根本痛点 = 微信 ClawBot 的 1:1 绑定 + 每个工具都想独占它。WorkFleet 的价值主张成立的前提是"**网关独占绑定、多路复用**"。
- **Where/When**：所有渠道连接器可在设备上运行（均有长连接/长轮询模式）；飞书长连接仅企业自建应用；Telegram webhook/轮询二选一；QQ 切换回调方式即时生效。
- **Who**：平台方（腾讯微信/QQ、字节飞书、阿里钉钉、Discord、Telegram）；用户（扫码者/订阅者）；企业管理员（飞书/钉钉可用范围）。
- **How**：每个渠道一个 OutputAdapter，声明 capability flags（见 04），由路由器按能力降级（卡片→Markdown→纯文本；主动推送不可用→切换渠道或排队等待入站）。
- **What if**：
  - 微信放宽限制（issue #202 若被采纳）→ 只需调额度预算器参数，无需改架构。
  - 微信收紧/终止服务 → 管理模式自动切换到 QQ/飞书/Telegram 备用渠道（用户需预先绑定）。
  - 飞书长连接多实例部署 → 集群模式只有一个实例收到，状态必须外置（共享存储），否则会话错乱。
  - QQ 主动配额以"每月 4 条"为准 → QQ 降级为"仅被动回复"渠道。

## 10. 苏格拉底追问 & 钢人论证

**结论 X：微信 ClawBot 不能用于通知/群发。**
- 凭什么？1:1 绑定（社区多方一致）+ 24h/10 条（官方仓库 issue，维护者回应）。
- 相反证据？OpenClaw 文档提到 broadcast groups，但那是 OpenClaw 内部概念，不改变 iLink 限制；协议消息含 `group_id` 字段，但官方插件只声明私聊。
- 前提不成立会怎样？若腾讯开放多用户 Bot，通知模式可加入微信——架构上只需把微信 Adapter 的 `multiUser` 能力位打开。
- 钢人反方：官方文档并未白纸黑字写"1:1"，可能是灰度期限制。→ 接受，标为 `部分确认`，以能力位而非硬编码表达。

**结论 Y：设备上运行即可，无需公网。**
- 反方最强论点：飞书卡片回调 `card.action.trigger` 的"Delivery Method"标为 Webhook——长连接是否能收卡片回调？→ 飞书长连接文档说明 SDK 可接收事件与回调（示例为事件），但卡片回调能否走长连接**未在本次读到的原文中确认** → `证据不足`，需实测；兜底方案是 Hub（云中继）提供 HTTPS 回调。

## 11. 最终判断

- **结论**：微信 = 个人管理通道（单用户、强限额）；飞书/钉钉 = 组织内通知与审批；QQ = 个人/小群被动交互；Telegram = 大规模订阅推送首选；Discord = 社区/频道广播。
- **依据**：§1–§6 官方文档与官方仓库。
- **前提**：限额以 2026-10 文档为准；微信限制来自官方仓库 issue 与社区实测。
- **局限**：未对任何渠道做实测；QQ 主动配额、Telegram 付费广播门槛存在官方自相矛盾；飞书卡片回调走长连接未确认；Discord DM 条件未核。
- **风险**：平台政策变更；微信额度耗尽导致关键告警丢失（必须有备用渠道）。
- **下一步**：①用测试账号逐渠道实测"入站→回复→主动推送→额度耗尽"；②确认飞书卡片回调可否走长连接；③在控制台核对 QQ 主动消息配额。
- **是否进入下一阶段**：允许，以能力位+降级策略吸收不确定性。
