## 0. 一页结论

| # | 结论 | 标签 |
|---|---|---|
| 1 | 六个项目**没有一个是“多对多 ACP↔IM 网关”**：WCB 是“微信接入层 + 单 LLM”，Paperclip 是“任务中心的 AI 公司 OS”，PentAGI 是“单主控 LLM 的渗透测试流水线”，Orca 是“并行 Agent IDE + 监督式编排”，Hindsight 是“记忆服务”，BettaFish 是“单任务多 Agent 舆情流水线”。 | 已确认（11–16 §0） |
| 3 | 数据层：“**数据库表即队列**”是共同成熟模式——Paperclip PG + LISTEN/NOTIFY、Hindsight PG `FOR UPDATE SKIP LOCKED`、Orca SQLite 邮箱 + ack 批重放；WCB 与 BettaFish 的“内存/日志文件”是反例（重启丢 context_token、forum.log 被清空）。 | 已确认（12 §5、15 §4、14 §4、11 §5、16 §0） |
| 4 | 扩展机制：Orca“新 ACP agent = 一行 spec + dialect”、Paperclip“进程外插件 + manifest + 能力门控”、Hindsight“`MODULE:Class` 扩展装载 + webhook”最可借鉴；PentAGI“新 provider 改 9 处 + DB enum”、BettaFish“新 Agent 改 6 处硬编码”、Paperclip“聊天通道写死常量与 DB CHECK”是必须规避的反模式。 | 已确认 |
| 5 | 实现路线共同规律：**ACP 是最后才抽象出来的通用层**（Paperclip 2026-07-08 设为本地默认引擎；Orca 2026-10-05 才独立 ACP 层），而它们都在**向“控制面 / 执行面分离”演进**（Paperclip Runner/PRP、Orca orcad、Hindsight worker）。→ WorkFleet 以 **ACP 为长期输入契约**、网关为控制面、Agent 进程为执行面。 | 部分确认（12 §11、14 §10 的演进归纳） |
| 6 | 对总控最有价值的四块拼图：PentAGI（Waiting/ask 屏障、三道护栏、Assistant 旁路五工具）、Orca（Run/Task/Dispatch/Mailbox/Gate schema + held 投递）、BettaFish（主持人四段式纪要 + 阈值/轮次触发 + 纪要注入）、Hindsight（persona MM：delta + `full_refresh_cron`）。会议协议仍需自研组合。 | 部分确认 |
| 7 | 许可证决定复用深度：Paperclip/Orca/Hindsight（MIT）可移植代码或直接依赖；PentAGI（MIT+EULA）、BettaFish（GPL-2.0+禁止商用）、WCB（无 LICENSE）**只能 clean-room 借鉴设计**。 | 已确认（各 §许可证） |

## 2. 进程 / 并发模型

| 项目 | 进程拓扑 | 并发单元 | 队列/背压 | 崩溃恢复 | 对 WorkFleet 的含义 | 出处 |
|---|---|---|---|---|---|---|
| WCB | 单进程 | 每账号 1 协程 + 1 httpx 客户端 | **账号内串行 await**；无队列 | 401/403→expired；网络错 2s/30s 退避；context_token 内存 LRU 重启丢 | 必须“入站落库→立即回执→异步回发”；凭据/游标/context_token 全部持久化 | 11 §5 |
| Paperclip | 单 Node 控制面 + 嵌入式 PG（54329，supervisor 守护）+ 每 run 子进程/ACP runtime + 每插件 fork 子进程 | 事件循环 + 多 `setInterval`（heartbeat 默认 30s） | PG 表权威 + LISTEN/NOTIFY 唤醒；行锁、幂等键、乐观抢占 `nextRunAt`；endpoint `burst/queue/debounce/drop/concurrent` | ACP run coordinator 管 6 类资源，固定“启动→回合→结算→复现”顺序；插件有界退避重启 | **持久化投递账本 + 唤醒信号**模式可在 SQLite 上以“轮询 + 内存 Event”复刻 | 12 §5 |
| PentAGI | 单 Go 进程 + pgvector + scraper 容器 + 每 flow Kali 沙箱 | 每 flow 一 goroutine + 无缓冲 input chan；assistant 独立 goroutine | **无队列、无并发上限**（RFC 提出持久化队列四原则，未实现） | `LoadFlows` 启动续跑 | 总控必须并发派工（DAG），并按 RFC 四原则建持久化队列 | 13 §5 |
| Orca | 宿主 + PTY 守护（可比宿主长寿）+ 每 agent 子进程 + 会话扫描子进程 | coordinator 单线程 tick 2s；派工并发默认 4；每 tick 最多新建 1 终端 | SQLite 邮箱 durable enqueue + 尽力唤醒；批 ≤50 + ack 前重放；同邮箱 in-flight 去重；**有待答权限时 held** | orcad 单实例锁（跨机不抢、陈旧可回收）、`serve --supervise` | “durable enqueue ≠ 已处理”的回执语义；held 策略直接迁移到 IM 侧 | 14 §4、§2.2 |
| Hindsight | API（默认 1 worker）+ 内嵌或独立 worker + maintenance 循环 | asyncio + uvloop/winloop；worker 槽位 10（consolidation 预留 2） | PG 表即队列 `FOR UPDATE SKIP LOCKED`，轮询 500ms，重试 3 次退避 60s | 任务可重试；maintenance 对账 | 广播/定时队列在 Hub(PG) 上直接用 SKIP LOCKED；Edge(SQLite) 用单写者 + 状态机 | 15 §4 |
| BettaFish | Flask 主进程 + 3 个 Streamlit 子进程 + LogMonitor 线程 | 引擎间进程并行、引擎内段落串行；主持人在监控线程**同步**执行 | 无队列；ReportEngine 全局单任务锁 | 引擎重启删旧日志；论坛 2h 无增长结束 | 反例：会议必须结构化事件 + 每会议锁，不得用日志抓取 | 16 §0、§3 |
