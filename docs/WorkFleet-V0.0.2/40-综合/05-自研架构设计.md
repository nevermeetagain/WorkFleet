## 4. ACP 作为长期契约（新增章节）

### 4.1 为什么是“长期契约”
| 证据 | 来源 | 标签 |
|---|---|---|
| Paperclip 2026-07-08 把 ACP 设为本地默认执行引擎；后续执行面向 Runner/PRP 外移 | `10-参考项目/12 §11` | 已确认 |
| Orca 2026-10-05 才把 ACP 独立成层（new/load/resume/auth、dialect、managedRuntime） | `10-参考项目/14 §10` | 已确认 |
| ACP v1.12.0 + schema-v1.26.0（2026-10-16），v1 稳定方法集无破坏性变更；v2 schema 2.0.0-alpha.9 | `20-同类开源/refs-commits-V0.0.2.md` | 已确认 |
| claude-agent-acp 0.93.0 已升级 ACP SDK 1.9.0 并采纳 v2 澄清 | 同上 | 已确认 |
| Python SDK 0.12.1 的 `ClientSideConnection` 含 initialize/new/load/resume/list/fork/close/cancel/prompt/set_session_mode/set_config_option，`Client` 含 request_permission/session_update/fs/terminal/elicitation | 本轮 introspection（E5） | 已确认（API 面）/ 端到端未测 |
| 反证：ZCode 官方无 ACP（README 无），Coze 为云 API | `30/02 §5–§6`、本轮 README grep | 部分确认 |

→ 结论：**输入层以 ACP v1 为唯一“一等协议”**；非 ACP 族（ZCode/Coze/Webhook/CLI）作为过渡适配器，接口形状与 ACP 对齐（session/new、prompt、cancel、update 事件），未来官方提供 ACP 时只换 codec 不动上层。`部分确认`

### 4.2 契约分层
```
InputAdapter（稳定接口：start/new_session/prompt/cancel/close/list/resume/load/answer_permission/events）
   └─ Codec：AcpV1Codec（默认）| AcpV2Codec（feature flag，跟随 schema-v2 正式版）| ZCodeAppServerCodec（实验）| CozeV3Codec | WebhookCodec | CliOneshotCodec
        └─ Transport：stdio NDJSON（ACP）| HTTP(S) | 子进程一次性
```
- **能力协商落库**：`agent_profile.caps_json` 存最近一次 `initialize` 结果（`loadSession`、`sessionCapabilities{list,resume,fork,close}`、`promptCapabilities`），控制台显示“支持/降级”。
- **恢复策略**（借 Orca session setup + Paperclip resume→fresh 回退思路）：`resume` > `load`（回放）> 新开并在 IM 提示。
- **/clear**：ACP 无原语 → `session/close`（若支持）+ `session/new`，写 `session_lineage(reason='clear')`。
- **版本锁**：`launch_json.pin_version` + `install_policy`（`managedRuntime` 思路：按需安装、钉版、回收）；升级前跑冒烟 `initialize→new→prompt→cancel`，结果入 `agent_version_check`；失败自动回滚。（G34）
- **v2 迁移**：信封 `Envelope` 不变；v2 的 replay ID / foreground work / 取消语义在 AcpV2Codec 内映射为同一组 `kind`。

### 6.2 关键表摘录（完整见 `05-gateway-schema-v002.sql`）

```sql
CREATE TABLE turn_queue (
  id TEXT PRIMARY KEY, fleet_session_id TEXT NOT NULL REFERENCES fleet_session(id), envelope_id TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'queued' CHECK (status IN ('queued','running','done','cancelled','failed')),
  position INTEGER NOT NULL, enqueued_at TEXT NOT NULL, started_at TEXT, ended_at TEXT);
CREATE UNIQUE INDEX ux_turn_running ON turn_queue(fleet_session_id) WHERE status='running';

CREATE TRIGGER event_ai AFTER INSERT ON event BEGIN
  INSERT INTO event_fts(rowid, text_digest) VALUES (new.rowid, new.text_digest); END;
CREATE TRIGGER event_au AFTER UPDATE OF text_digest ON event BEGIN
  INSERT INTO event_fts(event_fts, rowid, text_digest) VALUES ('delete', old.rowid, old.text_digest);
  INSERT INTO event_fts(rowid, text_digest) VALUES (new.rowid, new.text_digest); END;

CREATE TABLE outbox ( ...,
  status TEXT NOT NULL DEFAULT 'queued' CHECK (status IN ('queued','sending','sent','failed','expired','deferred','held','merged','cancelled')),
  hold_reason TEXT CHECK (hold_reason IS NULL OR hold_reason IN ('quota_exhausted','pending_gate','pending_permission','quiet_hours','merge_window')),
  merged_into TEXT REFERENCES outbox(id), ...,
  CHECK ((status='held') = (hold_reason IS NOT NULL)));

CREATE TABLE sv_meeting_event (
  meeting_id TEXT NOT NULL REFERENCES sv_meeting(id), seq INTEGER NOT NULL,
  type TEXT NOT NULL CHECK (type IN ('opened','round_started','statement','statement_invalid','timeout','round_complete',
       'host_digest','divergence','decision','gate_opened','gate_resolved','dispatched','closed','aborted','side_note')),
  actor TEXT NOT NULL, payload_json TEXT NOT NULL CHECK (json_valid(payload_json)), ts TEXT NOT NULL,
  PRIMARY KEY (meeting_id, seq));

CREATE TABLE memory_bank_link ( ...,
  mm_trigger_json TEXT NOT NULL DEFAULT '{"mode":"delta","refresh_after_consolidation":true,"full_refresh_cron":"0 3 * * 1"}' ...);
```

### 6.4 FTS 微基准（E5，非 K 指标验收）
`50-附录/DDL实测/fts_bench.py`：20 万条合成中文事件（20 个词随机拼接），单事务批量写入含 FTS 触发器 **13.0s（约 15.4k 行/秒）**；`MATCH` 计数 30 次 **p50 0.7ms / p95 1.7ms**；结果与 `LIKE` 全表扫描一致（5421 条，45.3ms）；top-20 + bm25 排序 7–8ms；库 62.6MB。→ K-34“100 万事件 FTS p95 ≤200ms”在 20 万合成数据下有约两个数量级余量，`部分确认`（合成文本、非真实分布、未测 100 万与并发写）。

## 8. 出站流水线、限流、配额与 held（V0.0.1 §8 + 变更）

1. Renderer：`card → markdown → plain` 降级；Fleet-IR → 渠道渲染（飞书卡片 2.0、钉钉卡片、TG MarkdownV2、Discord embed、微信纯文本 + “回复 /history N 查看全文”）。
2. Outbox 状态机：`queued → sending → sent | failed | expired`；`deferred`（等待令牌桶）；**`held`（有原因，可见、可取消）**；`merged`（p3 合并进摘要，`merged_into` 指向摘要）；`cancelled`（管理员/用户撤销）。
3. **held 规则**（借 Orca #28540 的“接收方有待答权限时不投递”，移植到 IM 侧与员工侧）：

| 场景 | 条件 | 动作 | 释放 |
|---|---|---|---|
| 员工侧（sv_message） | 目标员工有待答 `permission` 或当前 turn running | `held=1, held_reason=pending_permission/turn_running` | 权限决议或 turn 结束后，按创建序投递 |
| IM 侧额度 | 微信 `quota_state.remaining ≤ reserved_p0` 且消息 ≥p2 | `held(quota_exhausted)` | 下一次用户入站重置窗口 |
| IM 侧待决 gate | 该 peer 有未决 `sv_gate` 且新消息为 p3 进度 | `held(pending_gate)`，避免把决策请求淹没 | gate 决议后合并发送 |
| 静默时段 | 用户配置 quiet hours（R-913 可选） | `held(quiet_hours)`（p0 例外） | 时段结束 |
| 合并窗口 | 同 peer 60s 内多条 p3 | `held(merge_window)` → 生成 1 条摘要，原条 `merged` | 窗口到期 |

4. RateLimiter 三级令牌桶（adapter→account→peer）每 5s 落库；429 → `frozen_until`。
5. QuotaGuard：微信 `inbound_window` capacity=10（`部分确认`，可配）、`reserved_p0=2`；QQ `daily`。
