## 3. 第二轮：苏格拉底追问

### Q1 “Paperclip 档 A 第一，为什么不 fork（D）？”
1. 凭什么第一？工程维度强：D04 数据 4、D16 安全 4、D20 可靠 4、D06/D07 4（`01 §3.1`，E4@0528cc7e）。
2. 证据来自最新代码？是（V0.0.2 SHA）。
3. 相反证据：P0 覆盖仅 47.4%；**中文 IM 为 0 且通道不能插件化**——provider 写死在 TS 常量与 DB CHECK；endpoint 必须绑一个 agent（`chat_channels.ts:50`）；conversation 必绑 issue；主动私信能力几乎全 false（`provider-catalog.ts:17-105`）；日更 + 正向 Runner/PRP 迁移；Node≥24.11 + 嵌入式 PG（D15=2）；默认端口 3100 与 Fleet 段冲突。
4. 表面 vs 根因：“工程质量高”是表面，“任务中心模型 vs 路由中心模型”是根因。
5. 足以支持 D？**不足**。可借其接口/会话/投递账本设计（MIT）。

### Q2 “cc-connect（A）通道最全最快？”
1. 凭什么？6/6 目标 IM + 通用 ACP（E4），P0 覆盖最高 60.5%。
2. 相反证据：**无 LICENSE（2026-10-17 复核）→ G1 一票否决**；同 token 多 project 并发 `证据不足`（核心痛点）；`CronJob.SessionKey` 单值；JSON 文件存储；Go 与 Python 资产双栈。
3. 足以支持 A？**不足**（许可证硬门槛）。

### Q3 “OpenClaw（B）路由最成熟？”
1. 证据：分层 bindings（`resolve-route.ts:405-424`，新 HEAD md5 未变）。
2. 相反：钉钉缺失（新 HEAD extensions 复核仍无）；微信插件 NOASSERTION 仅单聊；所有消息过其 Agent 运行时；+894 提交/日的漂移；D24=2。
3. 足以支持 B？**不足**；路由设计借鉴。

### Q4 “C1（新 TS 网关）优于 C2？”
1. 支持 C1：TS 侧 ACP SDK 1.9.0 领先、acpx 可直接 import、Orca/Paperclip 移植省转写。
> 〔此处原引用旧内部项目代码或其实测数据，已于 V0.0.3 按用户要求移除〕
3. 结论：C2 更优；**但**“复用资产”权重归零（新仓）时 C2=C1（78.8），即 C2 的优势**完全来自 A-10 同仓前提**——必须由用户确认。

### Q5 “C2 在 V0.0.1 的四个前提今天还成立吗？”
| 前提 | V0.0.1 | V0.0.2 证据 | 状态 |
|---|---|---|---|
| PoC-1 微信单绑定复用 | 未验证 | 无新证据 | 待确认（PoC） |
| PoC-2 Python ACP SDK | 元数据 | API 面完整（E5 introspection），端到端未测；代差 0.12 vs 1.9 | 部分确认 |
| Python 主栈 | 现有仓即 Python | 不变 | 已确认（事实）/ 待确认（用户 A-47） |

### Q6 “Python 能达到高性能？”
- 定义（`01-需求分解与分析规划/05`）：网关内部路由 p95 ≤20ms（K-01）、静默丢失 0（K-17）、广播达平台上限 ≥90%（K-14）、常驻 ≤150MB（K-24）。瓶颈在平台限流与 Agent 进程，Python asyncio 足够（P3 限额：TG 30/s、飞书 50/s）。`证据不足`（PoC-9 压测）。

## 4. 第三轮：双向钢人

### 4.1 A cc-connect 底座
- **支持（最强）**：Go 单二进制（D15=4）、通道最全（D19=4）、通用 ACP、cron/timer/`/new`/`/history`/`/search`/Web/Management API/Bridge 全现成、日更；省下约 30–45 人日通道工作。
- **反对（最强）**：①**无 LICENSE → 闭源下不能拷代码**（G1）；②project 中心装配，单绑定复用需改 `engine.go`（1.77 万行，本轮 +9 提交仍在改）；③JSON 存储不适合订阅与统一事件库；④Go/Python 双栈双控制台；⑤微信同 token 多实例行为未验证。
- **已排除**：“通道不全”。**仍成立**：①–⑤ → **不选；A′（通道旁车）只在作者补 LICENSE 后可用**。

### 4.2 B OpenClaw 底座
- **支持**：路由一等公民、会话粒度丰富、记忆/cron/UI/ACP 齐、MIT、生态最大。
- **反对**：Agent 网关心智；钉钉缺失；微信插件许可未声明且仅单聊；S4 不满足；极高变更频率；不同栈。
- **仍成立**：全部 → **不选**；OpenClaw 可作为**输入端**（`openclaw acp`）。

### 4.3 C1 新建 TS 网关
- **支持**：ACP TS 生态领先；acpx/Orca/Paperclip 可直接复用或少转写。
> 〔此处原引用旧内部项目代码或其实测数据，已于 V0.0.3 按用户要求移除〕
- **仍成立**：资产浪费 → 不作主路线；**ACP 层以 C2′ 旁车形式保留**。
