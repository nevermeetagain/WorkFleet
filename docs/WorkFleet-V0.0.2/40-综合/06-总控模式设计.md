# 40-综合 · 06 总控模式设计（职业经理人 Supervisor，V0.0.2）

> 撰写：2026-10-17（Asia/Shanghai）。基线：`_V0.0.1基线/40-综合/05`（决定 D1–D8、状态机、把关分类、旁路工具全部继承）。本版重点：**轮次制会议协议**（收齐全部回复 → 主持人四段总结 → 决策步骤 → 派工 → 把关与分级上报 → 旁路对话），吸收 **BettaFish ForumEngine** 的主持人模式并修正其缺陷（clean-room，GPL-2.0 + 严禁商用），并接入 **Orca held 规则**与 **PentAGI 持久化队列原则**。
> 需求：R-601–R-612（P1；R-612 P2）；歧义默认：A-05（进程与状态在本机，推理可云）、A-07（对用户呈现为多对一）、A-08（P1，V0.5 Alpha）、A-30（员工 = 外部 ACP 会话）、A-31（skill = 提示词+工具+MCP；员工带能力标签）、A-32（规则表优先 + LLM 兜底）、A-33（任一 IM `/ask` + 控制台）。
> 表结构：`05-gateway-schema-v002.sql` 的 `sv_*`（已 sqlite3 实测，`05 §6.3`）；任务复用 AFX `kernel.db`。

## 2. 运行状态机（V0.0.1 §2 继承，补会议子状态）

```
intake → clarify ⇄（上报澄清 p1，等用户）
   │ 复杂度评分 ≥ 阈值 或 用户 "/ask 开会"          │ 否
   ▼                                                ▼
meeting{ open → round_running → collecting → synthesizing →（分歧？下一轮 : deciding）→ closed }
   ▼
decide（需用户拍板 → decision gate；否则直接）→ plan（写 AFX kernel）→ execute（派工/把关/返工）→ report → done
                                     ↘ paused（预算/用户）   ↘ cancelled / failed
```
- 任务级复用 AFX：`open → claimed → running → verifying → done | blocked | needs_user | superseded`；`needs_user → sv_gate`；连续 blocked/attempt 超限 → `circuit_broken`（参考 Orca 3 次熔断）。
- 派工级：`pending → dispatched → working → (asked ⇄ answered)* → done | failed | stale | circuit_broken`；“absence ≠ death”：员工进程断开先 `session/resume`。

## 3. 轮次制会议协议（核心）

### 3.1 参数（`sv_config.meeting_json`，默认值）

| 参数 | 默认 | 上限/约束 | 说明 |
|---|---|---|---|
| `participants` | 经理按 skill 标签挑选 ≤5；或 `/ask 开会 @claude-main @codex-a` | 5 | 少于 2 人不开会 |
| `quorum` | `all`（收齐全部） | `all` \| `majority`（用户可改） | D9：默认必须收齐或明确缺席 |
| `rounds_max` | 2 | DB CHECK 1–4（`rounds_cap`=4，OCL `maxRounds≤4`） | 第 2 轮只讨论分歧点 |
| `timeout_s` | 300/轮/人 | — | 超时记 `timeout`；连续 2 轮超时记 `absent` |
| `host_policy` | `on_round_complete` | `every_n_turns`（N≥参与人数，按参与者**轮转公平取样**）/ `on_conflict` | 改造 BettaFish“满 5 条触发” |
| `mode` | 只读/plan：ACP `session/set_mode`（python-sdk 有 `set_session_mode`）；不支持则提示约束 + 写工具一律 deny | — | 会议期间不改文件 |
| `turn_budget` | 每人每轮 1 turn；`max_tokens`、时长上限 | 会议总预算（token/金额/分钟） | 超预算 → 经理单人决策 + 上报说明 |
| `share_policy` | 下一轮只注入“最新纪要 + 与你相关的分歧点” | — | D11 |
| `persona` | 角色卡（架构师/后端/前端/测试/产品…） | — | 来自 `sv_worker.persona` 或 skill |

### 3.2 流程（每一步写 `sv_meeting_event`）

| 步 | 动作 | 事件 type | 数据表 | 失败/边界 |
|---|---|---|---|---|
| 0 | **议题包**：经理把澄清后的需求整理为目标、约束、验收、已知风险、相关知识（recall Top-K） | `opened` | `sv_meeting.agenda_json` | 信息不足 → 回 clarify |
| 1 | **开轮**：对每位参与者并行 `session/prompt`（议题包 + 角色卡 + 结构化发言 schema）；消息经 `sv_message(type=meeting_ask)`，**若员工 held（有待答权限/turn 运行中）则排队**（D13） | `round_started` | `sv_meeting_turn(status=asked)` | — |
| 2 | **收集**：员工返回结构化发言（§3.3）；解析失败 → 格式闸要求重答 1 次（`retries ≤1`，DB CHECK）→ 仍失败记 `invalid` | `statement` / `statement_invalid` / `timeout` | `sv_meeting_turn.statement_json` | 超时记 `timeout` |
| 3 | **法定人数判定**：`quorum=all` → 全部为 `answered/invalid/timeout/absent` 才进入总结（**收齐全部回复**）；有效发言 <2 → 中止会议，经理单人决策并上报 | `round_complete` | `sv_meeting.status=synthesizing` | — |
| 4 | **主持人四段总结**（§3.4，summarizer 模型，Fleet-IR） | `host_digest` | `digest(purpose=meeting_minutes)` | IR 校验失败 → 修复 1 次 → 降级纯文本 |
| 5 | **分歧判定**：生成分歧矩阵（议题点 × 员工立场 × 严重度）；关键点全一致或分歧不影响决策 → 进入决策；否则若 `round < rounds_max` → 第 2 轮只问分歧点（注入“最新纪要 + 你的分歧点”） | `divergence` | `sv_meeting.divergence_json` | 达上限仍分歧 → 决策时列为“需用户拍板” |
| 6 | **决策**（§3.5） | `decision` | `sv_meeting.decision_json` | 需用户拍板 → `gate_opened` |
| 7 | **派工**（§4） | `dispatched` | `sv_dispatch`、AFX todos | — |
| 8 | **关闭**：纪要 + 决策记录入事件库（FTS），可选 retain 到 Hindsight `project:<id>` | `closed` | — | `aborted`（用户取消/预算） |

### 3.3 结构化发言 schema（员工 → 经理）
```json
{"stance":"支持|有条件支持|反对","understanding":"…","proposal":"…",
 "pros":["…"],"cons":["…"],
 "risks":[{"desc":"…","severity":"low|med|high"}],
 "dependencies":["…"],"needs":["资源/权限/信息"],
 "estimate_hours":6,"can_own":["子任务A"],"questions":["…"],
 "confidence":0.0}
```

### 3.4 主持人四段总结（MeetingDigest，Fleet-IR 子集）
| 段 | 内容 | 来源模式 |
|---|---|---|
| ① 需求与共识 | 一句话目标；所有人一致的理解与约束；与原始需求的差异 | BettaFish 段 1“事件梳理/共识” |
| ② 方案对比与分歧 | 方案 A/B/C 的得失（来自 pros/cons）；分歧矩阵（谁、在哪点、为什么） | BettaFish 段 2“观点整合与对比” |
| ③ 风险、依赖与资源 | 合并 risks/dependencies/needs，按严重度排序；资源申请草案 | BettaFish 段 3“深层次分析/趋势” |
| ④ 待决与分工建议 | 待决问题（是否需用户拍板 + 推荐项）；分工建议（谁拥有哪个子任务，依据 can_own/skill/空闲度） | BettaFish 段 4“问题引导/下一步”（**新增分工与上报判定**） |
- 约束：每段 ≤N 条要点；必须引用发言者别名（可追溯）；IR 校验（结构、引用存在、无空段）失败 → 修复 1 次（借 BettaFish ReportEngine 校验-修复思路，clean-room）。
- 渲染：控制台完整版；飞书卡片（四段折叠）；微信纯文本只发“①一句话 + ④待决”并附 `/meeting` 查看全文（额度约束）。

### 3.5 决策步骤（DecisionMaker）
1. **候选方案收敛**：取四段纪要②中的方案，按准则打分（验收可达、风险、工时、对既定决策/directives 的符合度）。
2. **一致性检查**：与 `supervisor:<cfg>` directives（Hindsight，可选）及已批准计划比对；偏离 → 需用户拍板。
3. **上报判定**（规则表 `sv_policy` 优先）：命中“决策词表”（架构变更、对外接口变化、数据迁移、删除、发布）、存在未决分歧、资源申请、预算超 80% → `sv_gate(category=decision|resource)`；否则经理自决。
4. **决策记录**：采纳方案、理由、放弃方案及原因、风险缓解、需用户拍板事项、有效期；写 `sv_meeting.decision_json` + 事件库。
5. **决策门渲染**：一句结论 + ≤4 选项 + 推荐项 + 影响 + 回复口令（K-40）；IM 按钮或 `D1/D2/…` 口令；超时（默认 24h）→ 采用推荐项？**否**：默认**不自动执行**，保持 paused 并每日提醒（保守，R-910 精神）。

### 3.6 会议成本与质量控制
- 会议可选：复杂度评分（文件范围、跨仓、预计工时、风险词）低于阈值 → 单员工执行。
- 预算闸：会议总 token/金额/时长上限；BettaFish 单次运行推算 120–150 次 LLM 调用（`06 §3.5`，部分确认）是“不设预算”的反例。
- 质量：K-38 A/B（PoC-8：3 个真实需求，有会议 vs 无会议）。`证据不足`

## 4. 派工（Dispatch）

| 步骤 | 做法 | 复用 / 来源 |
|---|---|---|
| 拆解 | 计划 JSON（id、title、role、depends_on、allowed_files、verify、done_when、assignee_hint） | AFX Planner 计划 schema + 硬校验 |
| 写入 | `kernel.create_goal_with_plan` | AFX |
| 选员工 | `assignee_hint`（来自纪要④）> skill/角色匹配 > 空闲度 > `sv_worker_stats` 成功率 | Paperclip org chart 思路 |
| 晋升 | **只有调度器**把 `sv_dispatch.pending → dispatched`（D14 显式晋升）；全局并发默认 4（`sv_config.concurrency`）；`allowed_files` 顶层目录不相交才并行；每任务一个 git worktree | AFX allowed_files；Orca `MAX_CONCURRENT_DEFAULT=4` |
| 下发 | 任务包（AFX `packet_for`）→ ACP `session/prompt`；若员工 held → 排队（D13） | AFX packet；`sv_message.held` |
| 可见/可管理 | 控制台显示队列位次；`/sv cancel <todo>`、`/sv prio <todo> high` | D14 |
| 回收 | `fleet_done{outcome, summary≤3句, evidence}` 或 turn 结束后 gate 跑 verify | Orca worker_done；AFX gate |
| 返工 | gate 失败 → successor todo；超限 → needs_user → `sv_gate(blocked)` | AFX |

## 5. 把关（Gating）与分级上报（Escalation）

### 5.1 所有员工输出必经总控
`mode=supervisor` 绑定下，员工 `turn.end / perm.request / error / msg.final` 一律进 `Supervisor.review()`，**不直接发 IM**（`05 §7`）；每次把关写 `sv_review(decided_by=rule|model|human, policy_id, rationale)`。

### 5.2 分级（规则优先，LLM 兜底）

| 类别 | 判定 | 动作 | 优先级 | 渠道约束 |
|---|---|---|---|---|
| `auto_reply` | 员工提问可由知识库/既定决策/上下文回答（检索命中且置信度 ≥ 阈值） | 经理直接回复员工 | — | 不打扰用户 |
| `digest` | 普通进度、成功完成、低风险变更 | 合并进阶段汇报/日报（Fleet-IR） | p3 | 微信额度紧张时 `held(merge_window)` |
| `decision` | 决策词表、未决分歧、偏离计划 | `sv_gate` + 推荐 | p1 | — |
| `resource` | 新账号/密钥/付费 API/额度/机器/人手 | 上报 + 预估成本 | p1 | — |
| `risk` | 高风险工具审批、密钥外泄迹象、测试大面积失败、预算将超 | 立即上报 | **p0** | 永不 held；额度耗尽走 fallback（K-21） |
| `blocked` | 熔断、反复 needs_user、无心跳 | 上报 + 已尝试措施 | p0/p1 | — |

- **审批类**（ACP `request_permission`）：低风险 + 已有 `permission_rule` → 经理代批并记录；中风险 → 按策略代批或上报；高风险 → 一律上报 owner（K-44：不可“总是允许”）。
- **held 与上报的关系**：员工在等待权限时，经理的其他消息对其 held（D13）；用户侧若有未决 gate，新的 p3 进度对用户 held（`05 §8`），避免把决策请求淹没。
- **复盘**：每周控制台列出“被归为 digest 的事项”供抽查；K-36 召回 ≥95%、K-37 打扰率 ≤20%（需 ≥200 条标注样本）。

## 6. 自定义模型、Skill 与旁路对话

### 6.1 模型（按角色，PentAGI `pconfig` 思路）
| 角色 | 用途 | 建议 |
|---|---|---|
| `manager` | 澄清、主持决策、拆解 | 强推理模型；或 ACP Agent（只读） |
| `summarizer` | 会议四段纪要、日报、IR | 中等模型 |
| `classifier` | 把关兜底分类 | 便宜/本地模型 |
| `side_chat` | 旁路对话 | 同 manager 或中等 |
配置：provider、model、base_url、secret_ref、temperature、max_tokens、预算、回退链；复用 AFX `fleet/models`。

### 6.2 Skill（A-31）
- 形态：`skills/<name>/SKILL.md` + 可选 `templates/`、`policies.yaml`、MCP 服务器声明；作用域 manager / worker。
- 员工能力标签（`sv_worker.skills_json`）用于派工与会议选人。
- 写入员工工作区约定文件（`AGENTS.md`/`CLAUDE.md`）**须用户确认**；版本化（`sv_skill.version/sha256`）。

### 6.3 旁路对话（R-608，随时对话不打断执行）
- `/ask …`（任一绑定 IM，A-33）或控制台 → 独立 `sv_side_session`，与执行流的锁、队列完全分离（K-07 首字 ≤3s；K-08 心跳不中断、完成时长变化 ≤5%）。
- 受控工具（PentAGI 五工具思路 + 本版扩展）：

| 工具 | 作用 | 约束 |
|---|---|---|
| `sv_status(run?)` | 读运行/任务/员工/会议状态 | 只读 |
| `sv_meeting(run?)` | 读当前会议进度与最新纪要 | 只读（新增） |
| `sv_send_input(todo, text)` | 给某员工追加说明 | 走 `sv_message`，员工 held 时排队（D13）；不打断当前 turn |
| `sv_patch_plan(diff)` | 修改未开始任务 | 运行中不可改；PlanDiff 需用户确认 |
| `sv_pause/sv_resume(run)` | 暂停/恢复派工 | 不杀进行中 turn |
| `sv_stop(todo|run)` | 停止 | 二次确认，`session/cancel` |
| `sv_wait(run, timeout)` | 等待完成 | ≤1h（PentAGI `waitFlowMaxTimeout`） |

## 9. 四轮收口

- **5W1H**：What——设备端经理：复用 AFX 内核做任务，新增轮次制会议（收齐 → 四段纪要 → 分歧轮 → 决策 → 派工）、把关分级、held、持久化队列、旁路对话；Why——需求要求“开会统一意见、分配任务、所有输出必经总控、只上报重大事项、随时对话不打断”，现有项目只有零件（PentAGI 无会议、Orca 无会议原语且外部上报为空钩子 `coordinator.ts:226`、BettaFish 有主持但无派工/把关）；Where/When——Edge，V0.5 Alpha（A-08）；Who——总控 owner、用户（策略/技能/拍板）；How——§2–§7；What if——经理模型弱 → 会议可关、阈值可调、换 ACP 经理；员工不支持只读模式 → 提示约束 + 写工具 deny；成本超限 → BudgetGuard 暂停上报；AFX 内核不适配 → 回落 `sv_task` 独立表。
- **苏格拉底追问**：①“收齐全部回复会不会被一个慢员工拖死？”——每人每轮 300s 超时、连续 2 轮超时记 absent、有效发言 <2 中止；`quorum` 可改 majority。②“四段纪要凭什么比自由总结好？”——BettaFish 的四段式在其 2 年迭代中保留（`llm_host.py:133-204`），且第④段直接对接决策/派工；但质量仍无数据（K-38 待测）。③“held 会不会让紧急指令到不了员工？”——`sv_stop` 走 `session/cancel` 不经 held；held 仅对普通 dispatch/meeting_ask/send_input 生效。
- **双向钢人**：支持——每个机制都有出处与反例修正，DB 约束已实测；反对——会议链路无任何先例端到端验证，结构化发言依赖员工遵守 schema；ACP 只读模式各 Agent 支持度未知。处置——PoC-8 A/B；格式闸 + 重答 1 次 + invalid 记录；只读不支持时 deny 写工具。
- **最终判断**：1 结论：按本设计实现总控；会议与把关自研，任务内核复用 AFX；2 依据：§0 决定表；3 代码证据：PTG `flow.go:1288-1406`、`task.go:341-382`、`assistant.go:421-431`、`provider.go:892-905`；ORC `coordinator.ts:36,146,226`、`structured-mailbox-pointer-*`（#28540）；BF `llm_host.py:133-204`、`monitor.py:50,524-559,640-648`、`forum_reader.py:11-51`（模式，GPL）；AION `mailbox.rs`、`task_board.rs`、`mcp/tools.rs:29`；AFX `docs/架构.md §2–§4`；4 命令证据：`05 §6.3` DDL 实测（T10/T11）、AFX pytest、python-sdk `set_session_mode` API 面；5 前提：Gateway V0.2–V0.4 交付、PoC-0 通过；6 局限：会议效果/分类准确率无数据；7 未验证：各 Agent 只读模式、AFX planner 对外部 ACP 员工的适配；8 风险：成本、误报漏报、单人约 40–60 人日（G16–G19）；9 下一步：PoC-8；建立 ≥200 条上报标注样本（K-36 前置）；10 是否进入下一阶段：**允许进入详细设计**；实施排在管理/团队/通知之后（A-08）。
