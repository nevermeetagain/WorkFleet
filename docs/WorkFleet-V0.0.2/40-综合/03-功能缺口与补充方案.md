## 3. 重点缺口的补充方案要点

### 3.1 G01/G05 单绑定多路复用（核心痛点）
- **连接层**：`ChannelConnectionPool` 保证一个 ClawBot token 只有一条 `getupdates`；第二个进程启动时检测设备级锁（借 Orca `orcad-instance-lock` 思路）拒绝并告警（R-309、R-062）。
- **路由层**：入站先过 CommandBus（`/use`、`@别名`），再按 `reply_cursor`；出站首行 `[Codex·项目A]`。
- **额度层**：`quota_state(inbound_window, capacity=10)`；剩余 ≤3 只发 p0/p1 + 续期提示；耗尽走 fallback（A-34 默认飞书私聊/Telegram）。
- **持久化**：`context_token` 加密落 `im_principal.ctx_json`（修复 WCB 内存 LRU 缺陷）。
- **验证**：PoC-1（K-22：48h 零重扫码）。

### 3.2 G17 会议协议（BettaFish × Orca × PentAGI 组合）
| BettaFish 机制（GPL，只学模式） | 缺陷（06 §3.4 实测） | WorkFleet 改造 |
|---|---|---|
| 日志尾随抽取 SummaryNode 输出 | 依赖日志措辞，改词即断链 | 员工经 ACP 返回**结构化发言 JSON**（格式闸，失败重答 1 次） |
| 满 5 条发言触发主持 | FIFO 不分来源 → 某员工刷屏则主持只听一方 | `HostPolicy.on_round_complete`（默认）；可选 `every_n_turns` 但**按参与者轮转公平取样** |
| 主持在监控线程同步生成 | 生成期间尾随暂停 | 每会议 `asyncio.Lock`，不阻塞其他会议与消息路由 |
| 四段式主持发言 | 无“分配” | `MeetingDigest` 四段：①需求与共识；②方案对比与分歧矩阵；③风险/依赖/资源；④待决问题、分工建议、是否需用户拍板（→ decision gate） |
| 只注入最新 HOST | 全员同一份 | 下一轮议题包携带“最新纪要 + **与你相关的分歧点**” |
| forum.log 每会话清空 | 不可追溯 | `sv_meeting_*` 表 + FTS，SSE 序号化事件 |
- 预算：人数 ≤5、轮数 2（上限 4，OCL `maxRounds≤4`）、token/时长上限；BettaFish 单次运行推算 120–150 次 LLM 调用（`部分确认`）是“不设预算”的反例。
- 详见 `06-总控模式设计.md §3`。

### 3.3 G31/G32 S4 内容与汇报
- 08:30（Asia/Shanghai）采集 → 去重/打标/摘要 → `DigestComposer` 生成 Fleet-IR → 09:00 广播渲染（TG Markdown、飞书卡片、钉钉卡片、Discord 频道）。可选 BettaFish 作为**独立容器**的 ContentSource（仅舆情日报，经 CLI/HTTP 边界；MediaCrawler 不得商用，`暂不执行` 直到法务确认）。
- 详见 `08-四大场景落地推演.md §4`。

### 3.4 G34 适配器版本漂移
- `claude-agent-acp` 2026-10-15 → 10-17 发布 0.91.0、0.92.0、0.93.0（`refs-commits-V0.0.2.md`）。设计：`agent_profile.launch_json.pin_version`；控制台“升级”按钮先跑冒烟（K-05/K-33 子集）通过才切换；保留上一版本回滚。
