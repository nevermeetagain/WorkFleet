### 1.2 端到端流程（继承 + held）
1. 一次扫码：控制台二维码 → 网关独占；旧绑定按 supersede 失效（WCB `app.py:131-161` 行为）；网关单实例锁防止第二进程再轮询（R-309）。
2. `turn.end` → Router → 类别 `complete`（p3）→ 进入**合并窗口**（`held(merge_window)`，见 §1.5）。
3. Claude `request_permission`（`rm -rf build/`）→ p0 → 微信 `回复 Y1 允许一次 / N 拒绝`。
4. 用户回 `Y1` → **该入站同时刷新 `context_token` 与额度窗口** → PermissionBroker 校验 → ACP `optionId`。
5. `@cursor-b 把登录页改成深色` → 前缀路由；回执“已转给 [Cursor·B]（排队第 1 位）”（turn_queue 可见）。
6. `/clear` → 当前目标 `session/close+new`，旧会话可 `/resume`。
7. 额度紧张 → p3 合并；p0 占保留额度；耗尽 → p0 走飞书 fallback（K-21 ≤30s），其余 `held(quota_exhausted)` 到下次入站释放。

### 1.4 微信额度容量计算（新增）

**假设（判断性，PoC-1 替换为实测）**：8 个输入端；每个每天 6 个完成 turn；每个每天 1 次审批；失败率 10%；每天 2 条阻塞/提问；工作时段 10 小时；窗口容量 10 条/入站（保留 p0 2 条 → 可用 8 条）。

| 策略 | 日消息量 | 需要的用户入站次数（每次可用 8 条） | 结论 |
|---|---|---|---|
| 朴素（每个 turn 都推） | 48 完成 + 8 审批 + 5 失败 = **61** | **8 次/天** | 不可持续：用户需每 1–2 小时主动发消息；夜间必然耗尽 |
| 本设计（A-38：审批/失败/阻塞逐条，完成按小时合并） | 8 审批 + 5 失败 + 2 提问 + 10 摘要 = **25** | **4 次/天** | 可持续 |
| 关键自增益 | 8 次审批回复（Y1/N）本身就是入站 → 每次重置窗口 | 理论额度 8×10 = 80 条/天 | 审批越多，额度反而越宽裕 |
| 静默期（夜间 8h 无回复） | 8 条完成 → 1 条合并摘要 | 剩余 7 条（含 p0 保留 2） | 夜间只推 p0 + 1 条摘要；07:00 后首条入站释放 held |
| 24h 无任何入站 | `context_token` 失效 → 微信不可推 | — | 全部降级 fallback；最后一条可送达消息附“回复任意字续期” |

> 计算脚本：`50-附录/评分底稿/wechat_capacity.py`（输出：naive 61/8 次、designed 25/4 次、审批回复 80 条容量）。`部分确认`（假设参数未经实测）。

**K-22（48h 零重扫码）的隐含前提**：用户 24h 内至少有一次入站。设计上用“剩余 ≤3 条时附续期提示 + 每日 09:00 若 20h 无入站则 fallback 渠道提醒回微信发一个字”保障。

### 1.5 摘要设计（新增）
| 项 | 规则 |
|---|---|
| 合并窗口 | 同 peer 的 p3 `complete/progress` 进入 `held(merge_window)`：满 60 分钟或累计 ≥5 条或额度剩余 ≤3 时出一条摘要；被合并条目 `outbox.status=merged, merged_into=<摘要>` |
| 永不合并 | p0（审批、高风险、密钥外泄迹象）、p1（失败、阻塞、提问、决策门） |
| 排序 | 失败 > 阻塞 > 完成；同类按项目分组 |
| 长度 | ≤ 600 字（微信纯文本；超长截断并提示 `/digest` 全文） |
| 可操作 | 每条带序号；`展开 2` → 发第 2 条全文（消耗 1 条额度）；`/history codex-a` |
| 额度提示 | 剩余 ≤3：尾部追加“⚠ 本窗口还可发 N 条，回复任意字续期” |
| 夜间 | quiet hours 内只 p0；到点出“夜间摘要” |
示例（纯文本）：
```
【Fleet 摘要 10:00–11:00】完成 4 · 失败 1 · 待审批 0
❌ [Codex·A] 单测 3 处失败（auth_test）→ 回复 展开1
✅ [Claude·A] 修复竞态，42/42 通过
✅ [Cursor·B] 登录页改深色，已提交 a1b2c3
✅ [OpenClaw·B] 更新依赖 2 个
✅ [ZCode·C] 生成接口文档
回复 /history 别名 查看；⚠ 本窗口还可发 3 条，回复任意字续期
```

### 1.6 验收（K 映射）
K-22（48h 零重扫码，失败 100% 可归类）、K-17（静默丢失 0）、K-21（p0 降级 ≤30s）、K-33（`/clear` 100%）、K-34（三种 ID 查同一会话）、K-02（回执 ≤1s，有 typing 渠道）、K-03（长任务不阻塞）；8 个输入端的完成/审批都到达微信或 fallback；`/use`、`@别名`、`/clear`、`/history`、`/resume`、`/stop`、`/queue` 全部可用。

- 员工：`claude-main`（架构/评审）、`codex-subA`、`cursor-subB`、可选 `oc-ops`；账号通用（A-18：凭据引用共用）。

- 绑定 `sv-main`：mode=supervisor，inputs=`tag:projectX`，outputs=`feishu:me owner`（主）+ `wechat:me`（**仅 p0/p1 副本**）。

### 3.2 流程（详见 `06 §3、§8`）
`intake → clarify（≤2 问）→ meeting（R1 并行征询、收齐全部回复 → 主持人四段纪要 → R2 只议分歧）→ decide（决策门）→ plan（AFX kernel DAG）→ execute（并发 ≤4、worktree、held 规则）→ review（自答/归纳/上报）→ report（Fleet-IR 里程碑汇报）`；随时 `/ask` 旁路。

### 3.3 约束与风险
| 项 | 处理 |
|---|---|
| “所有需求已分解完毕” | 允许跳过会议：导入用户分解（JSON/Markdown）→ Planner 硬校验 → 派工 |
| 多项目共享工作区 | allowed_files 顶层互斥 + worktree |
| 微信额度 | 汇报走飞书；微信只收 p0/p1（每天预计 ≤5 条，§1.4 可用额度内） |
| 成本 | 会议预算 + BudgetGuard（80% 提醒、100% 暂停，K-39） |
| 质量 | PoC-8 A/B（K-38）；`sv_review` 复盘 |

### 3.4 验收

## 4. S4：大量订阅者每天 9:00 推送最新 AI 资讯

### 4.1 渠道结论（继承）

### 4.2 内容生产流水线（新增，G31/G32；借 BettaFish 模式，clean-room）
| 阶段 | 时刻（Asia/Shanghai） | 动作 | 借鉴（只学模式） | 表 |
|---|---|---|---|---|
| 采集 | 07:30 | `content_collect`：RSS、官方博客 API、GitHub Trending、arXiv 列表等 ContentSource 插件；记录来源条款与健康度 | BettaFish MindSpider `BroadTopicExtraction`（日采集 → 话题提取）的**数据模型思路**；**不使用 newsnow（来源合规不明）与 MediaCrawler（非商业许可）** | `content_source`、`content_item`（hash 去重） |
| 筛选与摘要 | 08:00 | `news-agent`（ACP Agent 带检索，或 Coze 工作流）去重/打标/打分/摘要 | BettaFish 三引擎“检索 → 反思 → 段落总结”节点流水线（思路） | `digest_item(rank)` |

### 4.5 验收
