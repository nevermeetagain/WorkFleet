## 0. 结论先行

1. **没有一个开源项目能单独满足 AideanFleet 的"大部分"需求**（我们把"大部分"定为加权匹配 ≥80%）。入围项目最高大约 **68%（OpenClaw）**，其次 **65%（cc-connect）**。`部分确认`
2. 这个赛道已经分化成四类，它们各自只覆盖需求的一段：
   - **A. Coding CLI ↔ IM 桥**：cc-connect、Claude-to-IM、botmux、golembot、wechat-acp 等。强项是"输入端 + 输出端 + /new + 会话"；弱项是 1 对多广播、真正的多对多路由表、总控、知识库。
   - **B. 个人 Agent 网关**：OpenClaw、Hermes Agent、nanobot、CowAgent。渠道、路由、cron、记忆都很强，但它本身就是一个"Agent"，Coding CLI 只能以子 harness（ACP）的形式接入。
   - **C. 聊天机器人框架**：AstrBot、LangBot、Koishi、NoneBot。输出端最全，有知识库，但没有 Coding CLI 或 ACP 输入（只能接 Coze/Dify 这类 API 型 Agent）。
   - **D. 组件**：ACP 适配器和客户端（acpx、claude-agent-acp、codex-acp）、通知扇出（Apprise、n8n）、多智能体编排（CrewAI、AutoGen、LangGraph、MetaGPT、AionCore Team）。
3. 推荐路线：**以 cc-connect 为底座**（Go 单二进制，6 个目标 IM 全覆盖，原生支持通用 ACP Agent，带 cron、/new、会话、Web 后台），或以 **OpenClaw 为底座**（路由和插件体系最成熟，但体量巨大，Agent 心智也更重）。在底座之上自建三样东西：路由层（模式和路由表）、扇出层（广播和订阅）、总控层（参考 AionCore Team 或 LangGraph）。理由见 §3 和各深度分析。

## 3. 入围（Shortlist）与理由

| 排名 | 项目 | 加权匹配* | 入围理由 | 主要短板 |
|---|---|---|---|---|
| 1 | **OpenClaw**（含 acpx 插件） | ≈68% | 路由最成熟（bindings 按 peer/guild/team/account/channel 分层，`src/routing/resolve-route.ts:405-424`）；多账号；cron 支持 at/every/cron+时区；有记忆插件；有 Control UI；ACP harness 完整 | 体量巨大，Agent 心智重；钉钉缺失；微信插件只支持单聊且许可证未声明；没有"1→N 订阅广播" |
| 2 | **cc-connect** | ≈65% | 6 个目标 IM 全覆盖；通用 ACP Agent；Go 单二进制，性能和部署友好；cron、timer、/new、/history、/search、Web 后台、Management API、Bridge WS、Webhook 都有 | 模型是"项目 = 1 Agent + N 平台实例"，没有路由表和广播；没有知识库和总控；LICENSE 文件缺失 |
| 3 | **AionUi + AionCore** | ≈60% | ACP 后端最全；**Team 模式（Leader + Mailbox + TaskBoard）是最接近"总控"的现成实现**；Rust 后端 + SQLite | 每个渠道只绑一个 Agent；没有 QQ；cron 结果不推送到 IM；以桌面应用为主 |
| 4 | **AstrBot** | ≈64% 原始分，**输入端硬门槛不过** | 输出端最全（含微信 iLink 和 QQ 官方）；知识库（FAISS + BM25 融合检索）；UMO 路由；主动消息；Coze Runner | 没有 Coding CLI / ACP 输入；AGPL-3.0 |
| 5 | **acpx** | ≈24%（组件） | 最完整的 ACP 客户端运行时和 Agent 注册表，可以当 AideanFleet 的"输入端驱动层" | 不是网关 |

\* 加权口径：IN 15、OUT 15、M1 10、M2 10、M3 10、UI 10、CR 5、NS 5、HI 5、KB 5、M4 5、LP 5，合计 100。打分细则见各深度分析的 §需求匹配。这是我的判断性打分，不是客观度量。

没有入围的原因：
- botmux、lark-bridge、wechat-acp：单一 IM。
- Claude-to-IM、golembot：需求面相近，但体量小、活跃度低，且只看了 README。
- Hermes、nanobot、CowAgent：自带 Agent，没有 Coding CLI 输入。
- LangBot、Koishi、NoneBot：与 AstrBot 同类，AstrBot 的输出端和微信 iLink 支持更贴近需求。
- 编排框架：只能补总控，不能做底座。

## 4. 苏格拉底追问与双向钢人（针对"没有项目满足大部分需求"）

- **我凭什么这么说？** 依据是 5 个入围项目的源码实读（commit 见各报告），以及其余 20 个项目的 README 和 API 元数据。
- **反方最强论证**：cc-connect 用"多个 project 共享同一组 IM 凭证"再配合 relay，或者 OpenClaw 用 bindings 加多账号，**已经能做出"团队模式"**；"通知模式"可以靠 cron 加多个 session_key 拼出来。所以它们实际已覆盖 80%。
- **反驳**：
  1. cc-connect 在启动时为每个 project 各自 `CreatePlatform`（`cmd/cc-connect/main.go:385-396`）。同一个微信 iLink 账号被多个 project 同时长轮询是否会冲突，**证据不足**。这恰恰是用户最核心的痛点（"只有一个微信"）。
  2. 两者的 cron 投递目标都是单个（cc-connect `CronJob.SessionKey` 见 `core/cron.go:26`；OpenClaw `CronDelivery.to` 见 `src/cron/types.ts:55-68`），没有订阅列表和扇出，场景 4（"大量用户每天 9 点推送"）不满足。
  3. 总控（会议、把关、随时对话不打断任务）在两者中都不存在；OpenClaw 的 broadcast groups 是"多 Agent 回复同一条入站消息"，有轮次和预算上限（`docs/channels/broadcast-groups.md`），和总控是两回事。
- **仍然成立的反对意见**：如果用户接受"每个工具一个 bot 账号"，cc-connect 的覆盖率会明显上升。这需要用户确认。`待确认`
- **结论可靠度**：中高。前提是"大部分"按加权 80% 计算，且场景 4 和总控被视为重要需求。
