# 05 · 验收标准与指标（WorkFleet V0.0.2）

> 撰写：2026-10-17（Asia/Shanghai）。R 编号见 `01`。
> **重要**：本文所有目标值都是**设计目标（未实测）**。来源分三类：①沿用 V0.0.1 `_V0.0.1基线/40-综合/04 §17`（同样未实测，原定由 PoC-9 回填）；②平台官方限额（`30-协议与端点/03`，下称 P3）推出的上限；③本轮新增，标“新增·判断性”。原文未给出任何数值（A-46），用户给出数值后以用户为准。
> 标签沿用：`已确认 / 部分确认 / 证据不足 / 待确认`；本表中“目标”一律视为 `待确认`，“依据”列标注其来源标签。

## 0. 测量通用约定

| 项 | 约定 |
|---|---|
| 计量边界 | “网关”= WorkFleet Gateway 进程（含 Router、适配器、调度器、事件库）；**不含** Agent 子进程（Claude/Codex 等）与总控所调用的远程模型 |
| 时间源 | 网关内部用单调时钟；端到端用 NTP 校准后的墙钟；所有报告时间写 Asia/Shanghai |
| 统计口径 | 延迟报 p50/p95/p99 与样本数；吞吐报持续 10 分钟的平均值与最低 1 分钟窗口；资源报稳态 30 分钟均值与峰值 |
| 打点 | 信封每跳打时间戳：`t_in_recv`（适配器收到）→ `t_in_persist`（入库）→ `t_route`（路由完成）→ `t_out_enqueue`（出站入队）→ `t_out_sent`（平台 API 返回）；Agent 侧：`t_prompt_sent` → `t_first_chunk` → `t_turn_end` |
| 工具 | 合成负载脚本（Python asyncio）+ 模拟适配器（mock IM/mock ACP Agent）；真机测试用测试账号；`/metrics`（Prometheus 格式）导出；`psutil` 采样资源 |
| 证据 | 每项测量保存原始数据 CSV + 脚本 + 命令 + 环境信息到 `50-附录/评测/`；按 `03 §4` 属 E5 |

## 4. 四轮收口

- **5W1H**：What——49 项指标（K-01~K-49）+ 4 个场景清单；Why——原文目标“高性能、高拓展”无数值，需要可测量的验收口径；Where/When——设备端网关，按里程碑逐步达标；Who——研究方给初值，用户确认（A-46），PoC 实测回填；How——统一打点、mock 与真机结合、原始数据入库；What if——参考机与用户实际设备差异大时，K-24/K-25/K-12 需按实测重定；若 A-05 选本地模型推理，K-24 不再适用于“含总控”的进程，需另设总控资源指标。
- **苏格拉底追问**：“≤150 MB、p95 ≤20 ms 凭什么？”——来自 V0.0.1 设计目标，未实测；相反证据：无（也无支持实测）→ 只能作为 PoC-9 的假设检验对象，不作为承诺。“99.5% 送达率是否合理？”——平台侧失败与用户侧拒收已分开统计，99.5% 只约束网关可控部分；若平台本身不稳定（如微信 `-14` 暂停），由 K-21 降级指标兜底。“上报召回 95% 能测吗？”——前提是标注集，目前不存在 → 已列为 K-36 前置条件。
