## 9. 四轮分析收口（针对“需求分解”本身的关键结论）

### 9.1 第一轮：5W1H
- **What**：§3 列出显式需求约 45 项、隐含需求约 25 项；§4–§6 列出前置 10 项、边界 23 项、依赖/回归 15 项；§7 建议补充 24 项。现有仓已有编排内核/控制台/审批/预算/邮件通知，**缺 IM、缺 ACP、缺订阅广播、缺节假日调度、缺总控会议**（E6/E7 + V0.0.1 `01 §3.2`）。
- **Why**：根本动机是“**一个 IM 身份被多个 Agent 复用**”（R-002）；其余模式与拓展是同一路由内核的不同策略。若只是“多开几个 Bot”，痛点不解决（微信 1 号 1 Bot）。
- **Where/When**：全部运行在用户设备（R-024、R-602）；端口 3100–3200；MVP 先管理模式（S1），其次团队/通道/调度，再通知，再总控（V0.0.1 `08 §1`）。
- **Who**：用户（决策 U1–U11、`02` 的 A-01~A-46）、研究主笔（本文）、外部平台（腾讯/飞书/QQ/钉钉/Discord/Telegram 规则方）、Agent 厂商（适配器版本）。
- **How**：以 R 编号作为后续所有报告的唯一引用口径；验收以 `05` 指标和场景 R-701~704 为准；不确定项进 `02`。
- **What if**：①若微信单绑定复用不可行（PoC-1 失败）→ R-002 降级为“微信只收 p0”，S1 主渠道换飞书/QQ（DG1）；②若用户不要求调休 → R-502 降为普通 cron；③若总控必须本地模型推理 → R-602 资源需求跃升（GPU/大内存），`05` 资源指标需重定；④若 V0.0.2 要求推翻 V0.0.1 结论重新选型 → R-802~805 工作量增加，但本分解仍有效；⑤若配置缺失/依赖服务不可用/端口被占用 → 分别由 R-112、R-310/R-907、R-060 覆盖。

### 9.2 第二轮：苏格拉底追问（每个关键结论）
1. **“R-002 是 P0”凭什么？** 证据来自原文“背景”段唯一的痛点陈述；相反证据：需求正文未直接写“单绑定复用”。是否把现象当根因？根因是平台 1:1 绑定约束（`30/03 §1.3`，部分确认）。前提：约束成立；若腾讯放开多 Bot，痛点减弱但多对 1 汇聚仍有价值 → 结论仍成立，但需 PoC-1 证实。
2. **“总控定为 P1 而非 P2”？** 原文把它列在“非必需”里，但场景 3 写“最好用总控模式”。反证：用户可能只是举例。→ 结论依赖 A-08 用户确认；确认前不影响 MVP 范围（MVP 不含总控）。
3. **“输出端不是 ACP”是否可能误判？** 证据为 ACP 规范只定义 Client↔Agent（`30/01 §2`），IM 平台文档均为自有协议（`30/03`）。未找到相反证据 → `已确认`。
4. **建议补充是否越界？** 每条都可追溯到原文场景或已知缺陷（R-901 ← WCB 明文 token；R-903 ← IM 远程操控本机）；但范围扩大会推高工作量 → 全部标“建议补充”，待用户裁剪。
5. **验收标准是否真的可测？** 部分标准依赖真机（微信）、依赖标注集（R-605）；标注集尚不存在 → 在 `05` 中列为“需先建评测集”。
6. **证据是否来自最新代码？** 现有仓：是（E1 ls-remote 与本地 SHA 一致）。V0.0.1 的协议/渠道结论：来自 2026-10-16 快照，距今 1 天，但 E12 显示适配器已发新版 → 渠道限额类结论仍可用，版本类结论必须重核。

### 9.3 第三轮：双向钢人论证
- **支持**：分解覆盖原文每一句（引用列逐句对应）；与 V0.0.1 的 37 项编码一一对应且更细；每项有可测试验收；不一致项（X1–X9）全部显式列出；边界项均给出了来源。
- **反对**：①原文多处措辞含糊（“直连”“默认呈现的多对一”“分身”），分解中的解释可能与用户本意不符；②验收阈值（如 95% 召回、≤1s 回执）是设计目标而非用户给定；③未运行现有仓测试，回归项部分基于文档；④BettaFish 只读了 README；⑤E12 为搜索摘录，未打开 release 正文。
- **处置**：①→全部进 `02`，以“推荐默认 + 影响”形式待确认（已排除：无）；②→`05` 明确标注“设计目标/未实测”（已排除风险：阈值被误当承诺）；③④⑤→列为后续步骤（PoC P0、第 3/8 步源码分析）的前置任务，不作为“已完成”（仍成立，需后续任务处理）。

### 9.4 第四轮：最终判断
