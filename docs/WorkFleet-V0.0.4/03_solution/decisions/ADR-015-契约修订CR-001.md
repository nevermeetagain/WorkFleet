# ADR-015：契约修订 CR-001

## 1. Context
六路并行写卡/设计的分析师在只读契约的前提下共报告约 60 条缺口（汇总于本文 §4）。规划指令 §4.4：任一契约自检为否 → 不得并行。

## 2. Problem
契约冻结前必须闭合会阻塞切片的缺口，否则执行 CLI 只能猜。

## 3. Options
A 开工前一次性修订并重新冻结；B 留给各任务卡标 blocked，开工后逐个改契约。

## 4. Decision
选 A。修订后契约版本仍为 v1（尚无实现，无兼容负担）。迁移新增 `0002_contract_revision_cr001.sql`（两侧），与 0001 一起冻结。

## 5. Rationale
B 会在 S0–S2 产生多个“改契约”任务，违反“Contract 不与实现并行改”。

## 6. Consequences
### Positive
协议、API、数据三方闭合；任务卡中标注的相关 blocked 项改为“已由 CR-001 解决”（执行者按本文对照）。
### Negative
部分任务卡正文仍描述了写卡时的权宜方案；以本文与契约为准。
### Risks
仍有未闭合项（§5），已登记为非阻塞。

## 7. Status
accepted（2026-10-17）。

## 5. 未闭合（非阻塞，已登记）
- `/mirror` 指令推迟 v2（BL-012）。
- 节点不保存路由只读副本（architecture §7 已更正为“只同步 supervised 集合”）。
- 中转 metrics 端口：中转只经 `GET /api/v1/health` 与内部 127.0.0.1:5104 暴露，不对公网。
- 渠道能力的“输入中提示/被动回复窗口/流式编辑方式”留给各渠道任务实测后再扩 schema（需新 CR）。
