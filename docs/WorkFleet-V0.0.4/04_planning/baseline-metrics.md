# 基线指标

## 0. 铁律
1. **没有基线前禁止优化任务。** 任何以“更快 / 更省 / 更少”为目标的任务（性能调优、缓存、合并请求、换库等），必须先有本表对应指标的首次测量值，并在任务卡写明“基线值 → 目标值 → 测量方法”；否则该任务不得进入 ready。
2. 当前仓库没有任何业务代码（`08_knowledge/fact-baseline.md`），因此**所有首次测量值 = 尚无基线**。首次测量由 **TASK-210**（v1 验收回归与基线指标测量）完成，结果写入 `06_validation/evidence/EVD-210/` 并回填本表。
3. 在 TASK-210 之前，各切片 E2E 可以顺带记录数值作参考，但**不算基线**（环境、规模不一致），只能用于发现回归，不能作为优化依据。
4. 指标口径一经首次测量即冻结；改口径 = 新指标 ID，旧值保留。

## 1. 核心操作与指标
选取 5 个用户最常做、最能感到快慢的操作。

| ID | 用户核心操作 | 指标 | 为什么这个指标下降，用户耗时也下降 | 测量方法 | v1 目标（出处） | 首次测量值 |
|---|---|---|---|---|---|---|
| BM-01 | **在 IM 里给智能体发一句话，等它“收到”** | 入站 → 回执时延 p50 / p95（渠道支持回执时） | 用户发完消息到确认“已收到”之间是纯等待；回执越快，用户越早放下手机或继续下一条，时延下降 = 等待时间下降 | 以 trace_id 贯穿：中转入站事件时间戳（持久化时刻）与回执发送成功时间戳之差；FakeChannel 回放 ≥200 条取分位数；真机（微信/飞书）各 ≥20 条抽样 | p95 ≤ 3 s（REQ-NF-001） | 尚无基线（TASK-210） |
| BM-02 | **在网页上发一句话，到电脑上的智能体开始处理** | Web 发送 → 节点收到 `agent.prompt` 时延 p50 / p95；分同城 / 跨境 | 这段是“人等系统转发”的时间，智能体本身的思考时间不计；转发越快，用户看到第一段回复越早 | Playwright 记录点击发送时刻；节点日志记录收到帧时刻（同一 trace_id）；中转放香港，节点分别在大陆与海外各测 ≥100 条 | 同城 ≤ 1 s、跨境 ≤ 2 s（REQ-NF-001，跨境部分确认） | 尚无基线（TASK-210） |
| BM-03 | **把话发给另一个工具（切换目标）** | 完成一次切换所需的用户操作步数与扫码次数 | 旧方式是“解绑 → 打开另一个工具 → 扫码 → 等待生效”，每多一步就多一段手动时间；步数与扫码次数下降直接等于手动操作时间下降 | 按 `01_product/user-guide.md` 第六节脚本，由独立验证者在真机上计数（步数 = 用户输入的消息条数 + 点击/扫码次数），并用秒表记录从“决定切换”到“目标工具回执”的总时长 | 1 条消息、0 次扫码（REQ-F-016/018，SM-01/02） | 尚无基线（TASK-210） |
| BM-04 | **审批一次智能体的权限请求** | 审批请求产生 → 通知到达用户（IM 或 Web Push）时延；用户决策 → 智能体收到决定时延 | 智能体在等审批时整个任务停着；通知越早到、决定越快回传，任务停摆时间越短，用户等结果的总时间越短 | FakeAgent 触发权限请求，记录 `approval.request` 帧时间、渠道/推送送达回执时间、`approval.decision` 到达节点时间；IM 与 Web Push 各 ≥30 次 | 未在需求中给数字 → **待基线后定**（相关：REQ-F-020、REQ-F-030 的 60 s 健康告警） | 尚无基线（TASK-210） |
| BM-05 | **按会话 ID 查历史记录** | `/history` 或 `GET /api/v1/history/search` 返回时延 p95（中转侧检索；含 / 不含节点转录拉取分开计） | 查记录时用户在等结果；返回越快，回溯问题的时间越短 | 预置 10 万条消息的测试库（规模为测量口径，非容量承诺），按 displayId、nativeSessionId、FTS 关键词三类各 ≥100 次 | 未在需求中给数字 → **待基线后定**（相关：REQ-F-019） | 尚无基线（TASK-210） |

## 2. 辅助观测（不作为优化目标，用于解释核心指标）
