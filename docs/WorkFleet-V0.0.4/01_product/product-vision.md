# 产品愿景

## 1. 为什么存在
> “我是一个开发者，日常会使用5个以上的开发工具协同、并发的辅助我。但我只有一个常用微信，老是扫码绑定后解绑，绑完这个绑哪个，根本忙不过来，还影响接收信息。”
> —— 用户原始设计说明书（REQ-INBOX-20261017-001，逐字）

问题不是“少一个聊天机器人”，而是**多个智能体与少数几个沟通入口之间缺一层多对多的调度**：每个工具都想独占一个 IM 授权，人只能来回换绑；消息又多又杂，重要的审批和结果被噪音淹没。

## 2. 愿景陈述
**一个入口，指挥所有智能体；一个经理人，替你把关和汇报。**

WorkFleet 让一个人（以及他的朋友、老板、部门）只通过一个入口——默认是网页控制台，也可以是自己习惯的任一主流通讯软件——与分布在多台电脑上的任意多个 ACP 智能体对话、审批、查记录；需要时由跑在自己电脑上的“总控（职业经理人）”统一把关、开会、分派、汇报。

## 3. 目标用户
| 画像 | 说明 | 依据 |
|---|---|---|
| P1 开发者本人 | 微信 + 本机多个开发 CLI（Claude Code、Codex、Cursor、ZCode…） | DEC-035、QA-06 |
| P2 朋友 | 飞书 + 外部智能体（首个 OpenClaw） | DEC-035、QA-06 |
| 公司成员 | 老板、多个部门、运营同时使用（场景 2 真实存在） | DEC-047、QA-19 |
| 不接 IM 的用户 | 只用网页控制台（可装到手机桌面并收推送） | DEC-057、QA-26 |

## 4. 坚持的原则（不随版本改变）
1. **代码、工具凭据、模型 Key 不离开用户自己的电脑**；服务器只做消息中转（DEC-037/044）。
2. **一个 Bot 身份只有一个消费者**，不再“谁最后扫码谁生效”（DEC-034）。
3. **消息发到哪由绑定决定，不由大模型决定**（DEC-005）；团队模式不默认广播（DEC-006）。
4. **只推该推的**：默认只推完成、失败、审批、阻塞，过程合并（DEC-017）。
5. **开源、可自建**：Apache-2.0；公司可以把中转部署在自己的服务器（DEC-033/048）。
6. **总控每次都把关**：总控模式下每条智能体输出都先过总控，不可关闭（DEC-018）。

## 5. 不是什么
- 不是在服务器上替你跑智能体的云 IDE（RJ-001、DEC-056 注）。
- 不是面向公众的大规模群发工具（DEC-046）。
- 不是另一个“单个大脑对多个 IM”的机器人（V0.0.3 QA-02 结论：OpenClaw 等不能整体实现本项目的多对多场景）。

## 6. 长期方向
见 `04_planning/roadmap.md`：v1 打通全部主流 IM 与 ACP 智能体 + 总控；v2 定时任务与推送团队；v3 总控 AGENTS.md/Skills 与知识库；v4+ 分身学习 loop。
